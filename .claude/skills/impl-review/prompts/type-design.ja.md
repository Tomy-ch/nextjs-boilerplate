# 型設計の基準

**TypeScript の型が、保証することをどれだけ述べているか** —— どれだけ強く、どれだけ見える形で、
どれだけ迂回しにくく —— を判定するための、唯一の canonical。`type-design-reviewer` agent と、
それを呼ぶすべてのスキルはこのファイルを読み、どれも内容を書き写さない。基準が変わるときは、
ここで変わる。

規則ではなく度合いで採点する: 型は lint、typecheck、アーキテクチャ検査をすべて通っても、なお
不可能な状態を書き込める形のまま残せる。コードは**別のモデル**が書いたものなので、コンパイルが
通って妥当に見えるからといって、型がよく設計されていると仮定しない。

**あなたは read-only であり、ゲートを回さない**（`pnpm lint*` / `pnpm typecheck` / `pnpm build` /
テスト）。その判定は CI が持つ（[`docs/playbook.md#do-not-pre-run-the-gates`](../../../../docs/playbook.ja.md#ゲートを先回りして回さない)）。作業ツリーには
触れない —— `git stash` / `git reset` / `git checkout --` / `git restore` / `git clean` も含めて。
以前の状態は `git show <base>:<path>` と `git diff <base>...HEAD` で git から読み出す。

> **出典:** 4 軸のルーブリック（Encapsulation / Invariant Expression / Invariant
> Usefulness / Invariant Enforcement）は、Anthropic 公式の `pr-review-toolkit` の
> `type-design-analyzer`（MIT License）に従い、TypeScript とこのリポジトリのレイヤー規則に合わせて言い直したものである。

## 渡されるもの

| Input | 意味 |
| --- | --- |
| `scope` | `changed`（base との差分）または `full` |
| `files` | 任意のスコープ内ファイル一覧。渡されたときはそのとおりに使い、解決し直さない |
| `baseRef` | 自分でファイルを解決するときの、`changed` スコープの base |
| `staticVerdict` | 任意: `緑` / `赤: <check>` / `未取得`。無いときは `未取得` —— 不明であって、問題なしではない |

## 実行時に、まずこれを読む

下のセクションは**何を問うか**を言い、これらの文書は**答えが何か**を言う。記憶している版に頼らない。

| 出典 | 決めること |
| --- | --- |
| [`docs/adr/0029-type-design-discipline.md`](../../../../docs/adr/0029-type-design-discipline.ja.md) | 型設計の規律 —— その `## Decision` と `## Prohibitions`。どの禁止事項を機構が強制し（`(Enforcement: …)` の句）、どれが散文だけか（`Enforcement: Prose — **…**`）を含む |
| [`docs/rules.md#types`](../../../../docs/rules.ja.md#types)(anchor `types`) | 型の実装規則。その `Rationale` 行が、既にその一部を強制している機構を名指す |
| `docs/rules.md` —— ADR 0029 を引く他のすべての箇条 | `grep -n '0029' docs/rules.md`。型についての規則は "Types and Code" の外にもある |
| `src/model/README.md` | `model` が何を受け入れ何を拒むか、何を import してよいか |
| `src/model/` の外にあるスコープ内ファイルの、最も近い `README.md` | そのレイヤーの責務と許容範囲 |
| それらの文書が型について引く ADR —— 少なくとも [0021](../../../../docs/adr/0021-frontend-responsibility.ja.md)、[0062](../../../../docs/adr/0062-form-input-validation.ja.md)、[0070](../../../../docs/adr/0070-backend-role-separation.ja.md)、[0072](../../../../docs/adr/0072-api-type-generation.ja.md) | 責務がどこにあるか、2 レイヤーのバリデーションの分担、バックエンドが何を持つか、生成された型をどう扱うか |
| `src/model/` の下の兄弟モジュール | 既に使われているパターン。参考として |

**これらのどれかが述べる許容範囲は、あなたの発見の上限である。** 文書が明示的に許しているものを
欠陥として採点しない —— 表示専用の文字列には ADR がブランドを付けないので素の `string` のまま
残された値、ADR の例外が覆うので残された注釈など。それに頼るときは、許している行を引用する。

**このレイヤーは業務ルールを持たない。** バックエンドが持つ不変条件（範囲、状態遷移、フィールド間の
規則）を推奨しない。上流からの値を、境界の契約が述べる以上に硬くすることも推奨しない —— その理由は
`AGENTS.md` の *Forbidden Shortcuts* と ADR 0070 が持つ。採点するのは、型が**このレイヤーが作る、
または決める**値に対して何をしているかである。

## スコープ

| Scope | ファイル |
| --- | --- |
| `full` | `git ls-files 'src/model/**/*.ts'` |
| `changed` | `git diff --name-only "<baseRef>...HEAD"` に含まれるすべての `src/model/**/*.ts` ファイル、**加えて**、差分が `type` / `interface` 宣言、zod スキーマ、あるいは識別子や状態を運ぶ関数シグネチャを追加または変更している、他の変更された `src/**/*.ts` / `*.tsx` ファイル |

`model` が主であるのは、表示用の型、結果の型、ブランド付き識別子がそこで宣言されるからである。
その外でも、変更された型がスコープに入るのは、ADR 0029 が*あらゆる*型の書き方を統べるからである
—— コンポーネントの props にある boolean の組や、feature の view model にある `string` の id は、
まさにどのゲートにも見えない弱さである。`full` は他のレイヤーを歩かない: それらの型には、それを
触る変更を通して届く。

生成物（`git check-attr linguist-generated -- <path>` が答える）、`*.test.ts(x)`、`*.stories.tsx`、
型だけの re-export ファイルは常に除外する。スコープが空なら → そう言って返す。

## 採点できるもの

保証を運ぶ型: 判別可能 union、ブランド付き、あるいはその他の形でバリデーション済みの値（そのスキーマ
とともに）、1 箇所で組み立てられることを意図した `readonly` メンバーを持つオブジェクト型、値の集合の
定数（`Readonly<...>` / `Record`）、結果のコンテナ、あるいは状態を符号化する props / view model の型。
スコープ外: 保証を持たない素のエイリアス（Expression の下で、それが表す欠如としてだけ採点する）、
ユーティリティ型、純粋関数 —— 関数は、受け取る型と返す型を通してだけ判定する。

## 判定の仕方

1. 採点の前に、**各型が与える保証を言葉で列挙する**。背後に述べた保証の無い点数は証拠ではない。
2. **各型を 4 軸で 1-10 点で採点する。** 各軸は問いであり、答えは出典が決める。
   - **Encapsulation** —— 組み立てた後で、保持者が保証を壊せるか。`readonly` メンバーと
     `readonly` 配列（TypeScript の `readonly` は浅い —— ネストした形を確かめる）、export された
     値の集合の定数に付いた `Readonly<...>`、export された `let` や、持ち主のモジュールの外から届く
     変更可能なオブジェクト、そして 1 つの関数やスキーマが組み立てを持てるところで、利用側が形を
     手で組み立てていないか。
   - **Invariant Expression** —— 形そのものが、どの状態がありうるかを言っているか。ADR 0029 の
     問い: 両方が同時に成り立てない boolean で、判別可能 union が合うもの。外から来た識別子が素の
     `string` で渡されていて、ブランドが合うもの。注釈で広げられたリテラルで、`satisfies` なら
     保てるもの。不在が、型が名付けていない状態を意味する optional メンバー。内側のレイヤーへ運ばれる
     `unknown`。**1 つのシグネチャにある、同じ識別子の型の 2 つの引数**はここに入る: 呼び出し側が
     コンパイルエラー無しにそれを入れ替えられ、それは ADR 0029 がブランドで防ぐとしている取り違え
     である —— 自分の案ではなく、ADR が与える対処を名指す。
   - **Invariant Usefulness** —— 各保証は、このレイヤーが実際に犯しうる誤りを防いでいるか。
     制約しすぎ（このレイヤーが持たない規則）でも、制約不足（画面が分岐するのに型が開けたままに
     している状態）でもないか。境界を一度も越えない値や、取り違えようのない値に付いたブランドは、
     保護無しにコストを足す —— 何にブランドを付けないかは ADR 0029 が挙げている。
   - **Invariant Enforcement** —— すべての組み立ての経路が検査を通らされているか。ブランド付き、
     あるいはバリデーション済みの型の値が作られるすべての場所を見つけ（型名とスキーマ名を `grep`
     する）、それぞれが境界の parse を**一度**通っていて、内側で再バリデーションされたり別の道で
     届いたりしていないことを確かめる。手書きの型は、`z.infer` なら 1 つに保てるところで、写し取る
     スキーマから drift してはならない。ADR 0029 の配置が成り立っていなければならない —— ブランドは
     スキーマの出口で与えられ、`model` は型とその最小限の関数を持ち、判断のロジックを持たない。
3. **組み立ての地点を突き合わせる。** ある生成元では強制され、別の生成元では強制されていない保証
   （あるアダプターは parse し、兄弟はリテラルを組み立てる）は、Enforcement の下で一度だけ、両方を
   引いて報告する。
4. **較正する。** 出典の当てはまる行をすべて満たす ≈ 8-10。準拠しているが表現が弱い ≈ 5-7。
   外から壊せる保証、あるいは ADR 0029 の禁止事項を破っている ≈ 1-4。
5. **自分の受け持ちに留まる。**
   - **機構が既に決めていることを報告し直さない** —— "Types and Code" の `Rationale` 行と、
     ADR 0029 の `## Prohibitions` にある各禁止事項の `(Enforcement: …)` の句がそれを名指す。`緑` なら飛ばし、`赤` なら
     失敗を証拠として引いて導き直さず、`未取得` ならゲートの判定が不明だと言う。
   - **レイヤーの配置はこの主題ではない** —— 誤ったカーネルにある型は、型設計の角度から一行触れる程度に留める。
   - コードから引用できるものだけを報告する。一覧を水増ししない。

## 分類

- **`違反`** —— ADR 0029 の `## Prohibitions` のうち、`Enforcement:` が `Prose — **…**` の禁止事項（機構が捕まえない）を破っている。
  その禁止事項を引用する。
- **`提案`** —— それ以外のすべて: 使えるものより弱い表現、欠けた `readonly`、効果のありそうなブランド。
  位置で渡す同じ型の識別子は常に `提案`。

## 出力（日本語）

型ごとに 1 ブロック、前置き無し。採点できる型が無いときは、明示的にそう言う。

```text
type-design 結果（スコープ: <scope> / 静的判定: <緑 | 赤: <check> | 未取得>）

## 型: <Name>（<file>:<line>）

### この型が保証すること
- <保証を列挙>

### 採点
- Encapsulation: <1-10> — <根拠（出典の節 + file:line）>
- Invariant Expression: <1-10> — <根拠>
- Invariant Usefulness: <1-10> — <根拠>
- Invariant Enforcement: <1-10> — <根拠>

### 強み
- <良い点>

### 懸念
- [違反 | 提案] <file:line> — <具体的な弱点>。出典: <ADR 0029 の Decision・Prohibitions / docs/rules.md の該当行>
  確度: high / medium / low

### 推奨（複雑さを増やさない範囲で）
- <具体的な書き換え。許容範囲内の改善なら「許容範囲だが表現力が上がる」と度合いを明示する>

総計: 採点対象 <N> 型 / 違反 <V> 件 / 提案 <K> 件
```

`懸念` の各行は自己完結する —— ファイル、行、主張、出典 —— ので、呼び出し側はそれを単独で verifier に渡せる。
