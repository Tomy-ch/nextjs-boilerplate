# drift 検出の基準

何を drift と数えるかの、唯一の canonical。`drift-detector` agent と `back-prop` の `SKILL.md` は
どちらもこのファイルを読み、どちらも内容を書き写さない。基準が変わるときは、ここで変わる。

**あなたは read-only である。** 発見を理由と選択肢の候補とともに示す。書き込まない、
`AskUserQuestion` を呼ばない。承認と書き込みは統合役が行う。

## 渡されるもの

| Input | 意味 |
| --- | --- |
| `layer` | 調べる対象のカーネル。例: `adapters` —— あるいは、文書だけのカテゴリなら `docs` |
| `files` | 解決済みのスコープ内ファイル一覧。git から解決し直さない |
| `categories` | この実行で選ばれた `A` / `B` / `C` / `E` の部分集合 |
| `baseRef` | ベースブランチ。履歴の問いにだけ使う |

## 実行時に、まずこれを読む

- そのレイヤー自身の `README.md` を、**frontmatter も含めて**（`imports-allowed` / `forbidden` /
  `test-requirement`）。frontmatter は機械が読める形であり、README が述べる中で最も強い宣言である。
- `architecture.ts` —— 依存マトリクス。何が何を import してよいかの権威は、README の本文ではなくこれである。
- `docs/rules.md` —— 日々強制される制約。
- カテゴリ `C` では、このレイヤーを名指すスキルの `SKILL.md`。
- カテゴリ `E` では、`docs/spec/glossary.md`。

**どれもハードコードしない。** 頭の中に持っている規則は、README が変わったその日に drift した規則である。

## カテゴリ A —— README → コードの drift

README が、コードがもうしていないことを述べている。

| 形 | 発見の例 |
| --- | --- |
| 宣言された責務がそこに無い | README はこのレイヤーが X を持つと言うが、ここの何もそれをしていない |
| 宣言された禁止が破られている | README は Y を禁じているが、あるファイルが Y をしている |
| 名指されたファイルやシンボルが移動した、または消えた | README がもう存在しないものを指している |
| frontmatter がツリーと食い違う | `imports-allowed` が、このレイヤーが実際に import しているパッケージを漏らしている |

**frontmatter の発見は本文の発見に優先する。** frontmatter は `architecture.ts` と ESLint の
boundary ルールが読むもので、本文は人が読むものである。両者が互いに食い違うときは、それ自体が発見である。

**コードを drift として、README を統べる側として報告する。** ただし README がそもそも存在しなかった
ものを記述していると示せる場合は別である。どちらが誤りかは人が決めることで、あなたの仕事は両方を示すことである。

## カテゴリ B —— コード → README の未記載パターン

コードが同じことを複数の場所でしていて、README がそれを一度も述べていない。

**しきい値は 3。** 2 回は偶然で、3 回は読み手が README から見つけられない慣習である。3 未満では
何も言わない —— 2 回での発見は、誰も採用していない規則を次の書き手に教えてしまう。

探すもの: 繰り返されるファイル命名の形、繰り返される export の形、繰り返されるエラー処理の手、
繰り返される配置の判断、繰り返されるテストの構造。

3 箇所（以上）をパスとシンボルで挙げる。**箇所の無い B の発見はレビューできない。**

## カテゴリ C —— スキル ↔ README の重複

スキルの本文が、README が既に述べていることを言い直している。

これが問題なのは、腐るのがコピーの側だからである: スキルに従った読み手は古い規則を受け取り、
規則が移ったことを知らないままになる。ここで特に問題になるのは、このリポジトリのスキルが
**基準を実行時に読む**ように書かれているからでもある —— 言い直した規則を抱えたスキルは、それをやめている。

| 形 | 報告するもの |
| --- | --- |
| 逐語、またはほぼ逐語の言い直し | 両方の箇所と、どちらがそれを持ち続けるべきか |
| README が持つ規則の一覧 | スキルは代わりに README を読むべきである |
| ツリーが既に持っているパスや対象の一覧 | スキルは実行時に列挙するべきである |

**スキルが自分の手順を具体にするために README を引用しているものは報告しない。** 引用が 1 節で、
スキルがその README を出典として名指しているときである。それはコピーではなくポインタである。

## カテゴリ E —— 業務語彙がその置き場から漏れ出している

業務語彙は `docs/spec/` に住む。レイヤー README と ADR は構造と決定を記述する。レイヤー README の
中に育った業務の語は置き場を離れており、その同じ語が誰も見ていない場所で改めて定義されることになる。

`docs/spec/glossary.md` は、自分が何を持ち、何を意図して持たないかを述べている: 契約が持たない
画面の語彙を持ち、**業務語彙もまたその対象ではない**。何を置き場にあるものと数えるかは、何かを
報告する前にそこを読んで確かめる。

**E の発見はすべて 2 種類に分け、ラベルを付ける:**

- **E1** —— 漏れがレイヤーの `README.md` にある。統合役の書き込みスコープの内側。
- **E2** —— 漏れが ADR か `docs/rules.md` にある。**報告だけ。** それらは決定の記録と統べる
  文書であり、検出器を満たすためにそれを書き換えれば、誰が決めるかを逆転させてしまう。

**E の発見を解消するために `docs/spec/glossary.md` の編集を提案しない。** 検出器を黙らせるために
語を削れば、定義を移すのではなく壊すことになる。語彙を保守するのは `glossary` である。

## 発見ではないもの

- **README と汎用コンポーネント自身の doc が同じことを言っている。** どちらもエントリポイントであり、
  どちらも、もう一方が読まれたと仮定してはならない。
- **サンプルだけの表面。** サンプルの削除が取り除くファイルは、テンプレートが使われた後では
  読み手の問題ではない。発見がそこにしか無いときはそう言う。
- **ファイルを開かずに推測したもの。** パスとシンボルを挙げ、行番号は挙げない。

## 返すもの

カテゴリごとにまとめた発見を、日本語で、それぞれ次の形で返す:

```text
[<category>] <一行の要約>
  該当: `<path>` の `<symbol / 節>`（B は 3 件以上すべて）
  正本: `<path>` の `<節>`（A / C / E1）
  理由: <なぜ drift か。1〜2 文>
  選択肢: <コード修正 / README 更新 / 規則の緩和 / スキルの簡略化 / 無視>
  確度: high | medium | low
```

続けて、カテゴリごとの件数を 1 行ずつ。**何も見つからなかったカテゴリは、明示的にそう言う** ——
黙っているカテゴリは、回されなかったカテゴリと見分けがつかない。
