# 仕様書の検証基準

仕様書のレビューが何を確かめるかの、唯一の canonical。`spec-validator` agent と
`verify-spec` の `SKILL.md` はどちらもこのファイルを読み、どちらも内容を書き写さない。

**あなたは read-only である。** 発見を証拠とともに示す。書き込まない、`AskUserQuestion` を呼ばない。

## 渡されるもの

| Input | 意味 |
| --- | --- |
| `route` | 1 つのルートの仕様書ディレクトリ。例: `docs/spec/route/auth/login` |
| `specs` | その中の仕様書ファイル —— `*.screen.md` と、あれば `*.function.md`。英語の canonical だけであり、`*.ja.md` のミラーは決して入力にならない |
| `implementation` | ルートが対応する `src/app` のエントリと、そこから届くファイル |

## 実行時に、まずこれを読む

- `docs/spec/README.md` —— 2 つのファイルがどう分担し、どこに置かれるか、そして**仕様書が意図して
  言わないこと**。
- このルートの**上位**にある `layout.*.md` の仕様書（その `*.ja.md` のミラーではない）。layout の約束はその下のすべてに及び、
  各画面はそこからの差分だけを書く。
- ルートが対応する実装。

## 存在の検査が既に覆っているもの —— 繰り返さない

すべてのルートに画面仕様書があるか、ルートより長生きした仕様書があるかは、ゲートが決着させる。
**それを導き直さない。** ファイルが存在するかを確かめている自分に気づいたら、ゲートの仕事を
より劣った道具でしている。あなたの主題は、ファイルが*言っていること*である。

## 4 つの発見

### 1. 約束と実装の食い違い

仕様書が、実装が守っていない、あるいは別の形で守っている、観察できる約束を述べている。

**どちらの側が誤りだと考えるかとその理由を述べる —— ただし決めない。** 向きは `docs/adr/0143` が
決着させている: 約束が変わったのなら動くのは仕様書で、変わっていないのなら実装である。そのどちらが
起きたかは差分からは見えないので、両方の読みを報告する。

**数えるのは観察できる約束だけである。** 仕様書は、利用者が観察できるものを記述し、コードがそこへ
どう到達するかは記述しない。観察できる振る舞いが一致したまま機構が違うものは、ここでの発見ではない。

### 2. 振り分けの誤り

記述が、2 つのファイルのうち誤った方にある。`docs/spec/README.md` 自身の問いで決着させる:

> バックエンドの契約と利用者の目的が同じまま、その記述だけが違う画面があり得るか。
> あり得る → 画面要件。あり得ない → 機能要件。

ルートの 2 つのファイルを一緒に読むのはこのためである: **置き場を誤った記述は、どちらのファイル
単独からも見えない。**

### 3. 上位 layout の書き直し

画面が、自分の差分だけを書く代わりに、上位の `layout.*.md` が既に約束していることを言い直している。

layout の仕様書と、それが重複しているセクションを報告する。言い直しは単に冗長なのではない ——
**2 つのコピーは drift し、読まれるのは画面の側のコピーである。**

### 4. 書かないものが書かれている

`docs/spec/README.md` は、仕様書が持たないものを名指している —— コンポーネントの名前、単位付きの数値、
レイヤーをまたぐ規約、実装の手順、この画面に固有でない操作。その一覧は実行時に読み、ここには持たない。

それぞれについて、その文と、**代わりにどこに属するか**を報告する。その一覧のどの項目にも置き場があるからである。

## 発見ではないもの

- **確かめられなかった約束。** 渡されたものから実装に届かないときは、その約束は未確認だと言う。
  **未確認の約束を守られていると報告することこそ、このレビューが防ぐために存在する失敗である。**
- **言い回しの好み。** 仕様書の仕事は、誰かが画面を作り直せるようにすることである。それができて
  いるなら、その言い回しはあなたのものではない。
- **`*.function.md` の欠落。** 機能要件の無い画面は、意図してそれを持たない。
- **サンプルだけの表面。** サンプルだけだと記す以上のことはしない。

## 返すもの

```text
[<finding kind>] <一行の要約>
  該当: `<path>` の `<節>`
  実装: `<path>` の `<symbol>`（1 のときのみ）
  理由: <なぜ食い違うか / なぜ置き場が違うか。1〜2 文>
  どちらが動くべきか: 仕様書 | 実装 | 判断が要る —— <根拠>
  確度: high | medium | low
```

続けて、種類ごとの件数を 1 行ずつと、**確かめられなかった約束とその理由**。確かめたものだけを
挙げるレビューは、すべてを確かめたレビューと見分けがつかない。
