# Scaffold Test

テストを持たない対象について、このリポジトリのゲートが既に強制している形でテストファイルを書く。

同じディレクトリの `SKILL.ja.md` に日本語の参考訳がある（スキルとしては読み込まれない。人間の参照用）。

## 使用する場面

- 1:1 ゲートが呼べる export について `missing-test-file` / `missing-describe` を報告している
- 新しい関数 / component / hook / Server Action が着地し、テストがこれから
- `make test-full` がカバレッジしきい値で落ち、未カバーの分岐にケースが要る
- 対象のテストは在るが、同じファイルに後から足した export にテストが無い。このスキルは既にある `describe` に触れず、欠けている分だけを足す

## このスキルを使わない場面

- **既にあるテストの評価** — `test-review` の担当。5 つの敵対的レンズを持つ
- **HTTP 境界の結合テスト** — `adapters` のクライアントや Route Handler を MSW 経由で確かめるのは `scaffold-integration-test` の対象。このスキルが書くのは unit / component
- **suite の実行** — `make test-full` / `make scripts-test`
- **対象の変更で壊れたテストの修理** — 壊した変更の側の仕事である。テストと挙動のどちらが誤りかは、その作者が知っている

## このスキルが読むもの・書くもの

以下はすべて**実行時**に読む。規約をこのファイルへ写さないのは、写しは drift するのに対し、ゲートは写しではなく出所に従うためである。

| 出所 | 何を決めるか |
| --- | --- |
| [ADR 0090](../../../docs/adr/0090-testing-strategy.md) | `describe` = export 名、`正常系` / `異常系` のコメント区切り、ケースごとの命名、skip / todo の規律、層別責務、mock の境界 |
| [ADR 0091](../../../docs/adr/0091-test-verification-methods.md) | 非同期 RSC テストの置き場、a11y 自動検査の組込 |
| 最も近い祖先 `README.md` の frontmatter（`test-requirement`） | 対象がどの層の責務に照らされるか |
| `scripts/lib/untested-modules.ts` | 意図的に対象外としているもの。ここに載る対象にはテストを書かない |
| 同じディレクトリの sibling テスト | その場所で確立している形（fixture の作り、helper の signature、MSW の配線） |
| 対象のソース | ケースを導出する分岐の集合 |
| `AGENTS.md` | `describe` / `it` の文字列は日本語 |

書き出すのは 1 ファイルだけ。対象の隣の `<subject>.test.ts`（または `.test.tsx`）。それ以外は書かない。

**対象は read-only。** テストしやすくするために編集・改名・分割したり、余分な export を足したりしない。書かれたままでは検証できない場合はそう言って止まる（手順 5）。

## 手順 0. 対象を解決する

引数がファイル（必要なら `path:symbol`）を指していればそれを採る。無ければ `AskUserQuestion` で尋ね、ゲートが今報告している対象を選択肢として出す。

```sh
pnpm exec vitest run --config vitest.scripts.config.ts scripts/one-to-one.gate.test.ts
```

失敗出力が `missing-test-file` / `missing-describe` の対象を `file:line` つきで挙げる。パスを打たせるのではなく、それを選択肢にする。

ただしゲートが挙げるのは**呼べる** export だけである。定数しか export しないモジュールは `describe` を要求されないので、テストが 1 つも無くてもここには現れない。ユーザーがそうした対象を直接指した場合は受ける。定数の契約（メンバーの厳密な集合、その順序）は、ゲートが要求しなくても固定する価値がある。

書き出し先はこう決める。

- 対象 `src/foo/bar.ts` → `src/foo/bar.test.ts`
- JSX を描画する対象 → `.test.tsx`
- テストは対象の**隣**に置く。`__tests__/` ディレクトリは ADR 0090 違反

対象が `scripts/lib/untested-modules.ts` に載っている場合は、その旨を伝えて止まる。明示的な宣言によってカバレッジ母数と 1:1 ゲートの双方から外されており、テストを書くことはその宣言と矛盾する。除外を外すのは別の判断であり、撤去条件は宣言側に書かれている。

## 手順 1. 層の文脈を読む

1. 対象から遡り、frontmatter に `test-requirement` を持つ最も近い祖先 `README.md` を見つけ、frontmatter と本文の両方を読む
2. ADR 0090 と ADR 0091 を読む
3. 対象のソースを最後まで読む
4. 同じディレクトリの sibling テストを読む

`test-requirement` がテストの負う責務を選ぶ。

| 値 | 責務 |
| --- | --- |
| `unit` | 純粋ロジック。戻り値と送出するエラー種別をアサートする |
| `component` | Testing Library を通した描画と振る舞い。**加えて ADR 0091 が要求する `axe` のアサーション** |
| `integration` | HTTP 境界のみ。内側は mock し、形と型をアサートする。`scaffold-integration-test` の方が適切でないか検討する |
| `route` / `feature` | ADR 0090 の表に従う。推測せず読む |

**祖先のどこにも `test-requirement` が無い場合、または最近傍の宣言の前提がこの対象で成り立たない場合**（HTTP クライアントのために書かれた `integration` の宣言は、純粋な整形ヘルパだけを持つ隣を支配しない）は、ドキュメントの欠落として扱う。締めの報告でそう述べ、責務は sibling テストと ADR 0090 から導く。黙って責務を発明しない。欠落そのものが報告すべき事実である。

## 手順 2. 対象からケースを導出する

ケースの一覧は**対象自身の分岐**から作る。テンプレートからではない。スコープ内の export ごとに:

- すべての条件分岐、すべての早期 return、送出するすべてのエラー種別
- すべての境界の対。両側を採り、結果の違いがケースの固定するものになるようにする
- `null` / `undefined` / 空入力に対するすべてのガード
- component なら、それが所有する variant / 状態のそれぞれ（`components/README.md` の状態表に従う）。loading / empty / error / success を所有しない component に、それらの状態を発明しない
- hook なら、遷移する状態のそれぞれ。内部へ手を伸ばすのではなく、描画結果を通してアサートする

**区別のあるアサーションを持たない分岐は、カバーされていない。** このリポジトリはカバレッジを 100% でゲートしているので、「その行が走った」は情報を持たない。情報を持つのは、そのケースが**この分岐を隣の分岐から区別する結果**——どのエラーか、どの描画状態か、どの値か——をアサートしていることである。

**分岐を持たない対象にもテストを書く。** props をそのまま流すだけの component にも契約はある。どこへ流すのか、既定値は何か。

各ケースを `正常系` / `異常系` へ振り分ける基準は、**対象自身が失敗するか**であって、入力が失敗に見えるかではない。fetch の失敗を飲んでエラー状態を返す hook は throw しないので、全ケースが `正常系` に入る。

## 手順 3. 計画して確認を取る

書く前に、書き出し先と、対象・区切りごとに束ねたケース一覧をユーザーへ見せる。

```txt
書き出し先: src/model/format-amount.test.ts

describe("formatAmount")
  ----- 正常系 -----
  - 整数の金額を通貨記号つきで整形する
  - 小数点以下がある金額を最小単位へ丸める
  ----- 異常系 -----
  - 通貨コードが未知のとき InvalidArgumentError を投げる
  - 金額が負のとき RangeError を投げる
```

`AskUserQuestion` で確認する:「この構成でテストを書きますか？」/「ケースを追加・修正したい」/「キャンセル」。計画の変更は安いが、書かれたファイルはそうではない。

## 手順 4. ファイルを書く

手順 1 で読んだものを適用する。現時点の規約では次を指す。

- **最外の `describe` は対象 export の名前**であり、対象ごとに 1 つ。1 ファイルに複数の export があれば、ソース順に最上位 `describe` を並べる
- **観点は `// ----- 正常系 -----` / `// ----- 異常系 -----` のコメントで区切り**、`it` は対象の `describe` の直下に置く。入れ子 `describe` は共有 setup を持つ文脈だけに使い、名前はその文脈を述べる
- **`it` 文字列は日本語**で、振る舞い*と*分岐条件を述べる
- **1 ケース 1 `it`。** `it.each` / `it.for` は、ケースを同定する名前テンプレートを伴うなら使ってよい。素の `it` を手書きの `for` / `forEach` で回すのは不可
- **その層が所有する境界で mock する**: HTTP は MSW（`mocks/` の共有ハンドラ。`vitest.setup.ts` で配線済み。`fetch` の手書き stub を作らない）、モジュール境界は `vi.mock`、設定は `vi.stubEnv`
- **component にはファイル先頭の `// @vitest-environment jsdom`** と、ADR 0091 が要求する `axe` のアサーションが要る
- **ユーザーが要素へ到達するのと同じ引き方をする**: アクセシブル名つきの `getByRole` を最初に、次に label / placeholder / text。`data-*` はアクセシブルな取っ手が無いものへの最後の手段。`fireEvent` より `user-event`、タイマーではなく `await waitFor` / `findBy*`
- **ファイルを通すための skip を書かない。** 到達できない分岐があるなら手順 5 である

fixture はローカルで自明に保つ。複数ケースで共有するなら、ファイル冒頭の fixture component や builder でよい。共有 fixture モジュールの新設はこのスキルの仕事ではない。

## 手順 5. 書かれたままでは検証できないとき

対象を変えないと到達できない分岐がある——モジュール読み込み時の副作用、`process.exit`、実ネットワークでしか作れない値。**skip せず、対象も編集しない。** 所見として報告する。

- どの分岐か、なぜ `vi.mock` / `vi.stubGlobal` でも到達できないかを述べる
- 到達可能にする切り出しを提案する。検証を妨げる副作用を専用モジュールへ出し、対象はそれを呼ぶだけにする。テストはその境界を mock し、渡した引数とそこまでの分岐をアサートできる
- 判断はユーザーに委ねる。切り出しは production コードの変更であり、このスキルの外側である

これは ADR 0090 が `it.skip` に課しているのと同じ基準である。skip が許されるのは切り出しをしても残る分だけで、「別のテストでカバー済み」は理由にならない。

## 手順 6. 検証

次を実行し、走らなかったものも含めて正直に報告する。

```sh
pnpm fix                                     # 整形と自動修正可能な lint
pnpm exec vitest run <書いたテストファイル>   # 新しいケースが通る
pnpm exec vitest run --config vitest.scripts.config.ts scripts/one-to-one.gate.test.ts
```

ゲートの実行が、`describe` 名が 1:1 対応を満たすことの証明になる。カバレッジ母数に入る対象については、分岐が実際にカバーされたことも確かめる。

```sh
pnpm exec vitest run <書いたテストファイル> \
  --coverage.enabled --coverage.include='<対象のパス>' --coverage.reporter=text
```

対象について 4 指標すべてが 100% でなければならない。届かないならケースが分岐を取りこぼしている。基準を下げず、手順 2 へ戻る。

## 手順 7. レビューへ渡す

何を書き、何を検証し、何を所見として残したかを平明に述べる。そのうえで新しいファイルに対する `test-review` を提案する。このスキルは対象の分岐から書くが、`test-review` は書き手が自分の出力に対しては問えないこと——アサーションに意味があるか、層の責務が実際に確かめられているか——を問う。

## 制約

- ✅ ADR 0090 / 0091、`test-requirement` frontmatter、sibling テストを実行時に読む
- ✅ `it` 文字列は日本語。`describe` は export 名。観点はコメント区切り
- ✅ 書く前にケース計画の確認を取る
- ✅ 1:1 ゲートと対象単位のカバレッジで検証する
- ❌ 対象の編集・改名・再構成。常に read-only
- ❌ ファイルを通すための `it.skip` / `it.todo`
- ❌ `scripts/lib/untested-modules.ts` が宣言する対象へのテスト
- ❌ MSW が所有する境界での `fetch` 手書き stub
- ❌ 規約を実行時に読まず、このファイルへ写すこと
