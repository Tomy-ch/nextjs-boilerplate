# Test Review

このリポジトリのテストファイルに対する、敵対的で偏りの少ないレビュー。read-only であり、壊れている・検証が薄い・実質何も確かめていない箇所を洗い出す。どう直すかは利用者が決める。

同じディレクトリの `SKILL.ja.md` に日本語の参考訳がある（スキルとしては読み込まれない。人間の参照用）。

## 使用する場面

- commit / PR の前に、その変更に含まれるテストファイルへ
- **カバレッジが 100% なのにリグレッションが出るとき。** このリポジトリは 100% のカバレッジゲート（`make test-full`）を敷いているため、**カバレッジは「アサーションに意味があるか」について何も語らない**。全行が構造上必ず実行されるからである。Lens 4 Axis B はまさにその盲点のために存在する
- カーネルや component ディレクトリ単位の単独監査として

## このスキルを使わない場面

- **実装コードのレビュー** — `impl-review` の担当
- **テストの実行** — `make test-full` の担当。このスキルはテストを読むだけで、実行しない
- **テストの作成・修正** — ファイルを一切編集しない。適用は利用者が行う

## このスキルが読むもの

このリポジトリに `docs/testing-conventions.md` <!-- skill-lint-ignore --> は無く、テスト生成スキルも無い。規則の出所は ADR とカーネル README であり、実行時に読む。

| 出所 | 何を決めるか |
| --- | --- |
| [ADR 0090](../../../docs/adr/0090-testing-strategy.md) | フレームワークの分担（Vitest / RTL / MSW / Playwright）、`正常系` / `異常系` の命名、table-driven 禁止、1 対象 1 テスト、層別責務、integration = HTTP 境界のみ |
| [ADR 0091](../../../docs/adr/0091-test-verification-methods.md) | 非同期 RSC テストの置き場、a11y 自動検査の組込 |
| カーネル `README.md` の frontmatter（`test-requirement: unit \| component \| integration \| route \| feature`） | 対象がどのテスト層に属するか |
| [AGENTS.md](../../../AGENTS.md) | `describe` / `it` の文字列は日本語 |
| 同じディレクトリの sibling テスト | その場所で確立している書き方（fixture の形、helper の signature、MSW の配線） |
| subject のソース | コード起点の 2 レンズが必要とする |

**go-boilerplate 由来の規約を持ち込まないこと。** Go の規約でこちらに対応物が無いもの（`t.Parallel()`、`require` と `assert` の使い分け、生成 mock `*_mock.go`）は適用されない。Vitest はファイル単位で既定で並列に走り、`expect` は 1 つで、mock の境界は MSW である。

**規則の出所が沈黙している箇所では、規則を発明せず「無い」と報告する。** go 側の原本は意味的品質のアンチパターン目録を読むが、このリポジトリにその対応物は無い。したがって Lens 3 は一般原則を適用し、**目録が未整備であること自体**を補遺で報告する。目録をリポジトリの方針であるかのように持ち込んではならない（`AGENTS.md`「Pending Decisions」= 保留領域に独自の規約を持ち込まない）。

無し。成果物は会話へ描画される日本語レポートだけである。

## 最初の手順: スコープの解決

**呼び出し元が `scope` payload を渡した場合、この質問は出さない**（Chainability を参照）。ファイル一覧は既に解決済みである。

`AskUserQuestion`:

- 質問: 「test-review の対象スコープを指定してください」
- 選択肢:
  - 「変更ファイル (HEAD-vs-working tree, 推奨)」 — `git diff --name-only` から `*.test.ts` / `*.test.tsx` を抽出。新規追加（`--diff-filter=A`）も含める
  - 「ブランチ base 比較」 — `git merge-base` で base を解決し、その間に touch されたテスト
  - 「特定パス / ディレクトリ (free-text)」
  - 「キャンセル」

スコープにテストが 1 件も無ければ、レビュー対象が無いので停止する。**単独実行時のみ**であり、呼び出し元から来た場合はテストの無い production ファイルこそが対象なので続行する。

対象ごとに **subject のソース**（同じディレクトリの、`.test` を除いた basename）を解決する。Lens 4 / 5 が必要とする。

## Step 1. 層の文脈を読む

対象ごとに:

1. ファイルから遡って最も近いカーネル `README.md` を見つけ、`test-requirement` frontmatter と本文を読む
2. ADR 0090 と ADR 0091 を実行ごとに 1 回読む
3. subject のソースを読む
4. 同じディレクトリの sibling テストを読む

`test-requirement` が ADR 0090 の層別表を引く鍵である。`unit` のカーネルと `component` のカーネルは同じ観点を負わないし、`integration` を宣言するカーネル配下の対象は「HTTP 境界のみ / 内側は mock / 型・形状をアサート」に縛られる。

## Step 2. 敵対的レビュアーを 5 つ並列に立てる

`adversarial-reviewer` の subagent を 5 つ**並列**に起動する。既定は `sonnet` で、Opus の実装者とレビュアーが別モデルになるようにする。全員が Step 1 の同じ文脈を受け取り、レンズだけが異なる。

うち 2 つは**コード起点**で、subject のソースから始める。したがってテストが 1 つも無いコードも視野に入る。これはテストファイルから読み始める方式では構造上見えない盲点である。

### Lens 1: 構造準拠

ADR 0090 への機械的な適合。現時点では次を指す。

- **最外の `describe` グループはリテラルの `正常系` / `異常系`** で、ケースはその内側にネストする。`正常系_xxx` の接頭辞形は違反であり、内側のケースが接頭辞を繰り返すのも違反（グループが既に軸を示している）
- **ケース名は日本語**で、振る舞いと分岐条件を述べる
- **table-driven 禁止。** ケース配列に対する `for` / `forEach` / `it.each` は、重複がどれだけ減ろうと違反。sequential な sibling の `it` が正しい形
- **1 対象 1 テスト。** 複数の subject を束ねる `describe`（共通の `*_Accessors` 的なもの）は違反。両方向を見る — 複数 subject を束ねた `describe` と、1 つの subject が複数 `describe` に割れている場合。**テストが 1 つも無い subject は Lens 5 の所管**であり、このレンズは既にあるテストの形だけを見る（二重報告しないため）
- **HTTP 境界の mock は MSW** で行う。手書きの `fetch` stub や adapter のモジュール mock は違反。ADR 0090 が integration をその境界に限定している
- **co-location。** テストは subject の隣に置く。`__tests__/` への集約は違反

ADR 0090 を実行時に読み、その時点の記述を適用する。上の一覧はその適用であって、drift しうる写しではない。

出力: `file:line` と違反した規則。

### Lens 2: 観点カバレッジ

層が負うものと、テストが実際に確かめているものを突き合わせる。

- カーネルの `test-requirement` が ADR 0090 の層別表の行を選ぶ。その行の責務（unit = 純粋ロジック、component = 描画・振る舞い、integration = HTTP 境界の型・形状、route / feature は ADR に従う）に照らす
- component のテストでは、ADR 0091 により a11y 自動検査が責務に含まれる。`axe` のアサーションが無い component テストは観点の欠落である
- `components/README.md` が「どの UI がどの状態を所有するか」を定めている。loading / empty / error / success を所有する component はそれらを確かめる必要があり、所有しない component に無意味な state ケースを作ってはならない。component が対象のときは読む

**カーネル README に Test Strategy の散文節は無く**、frontmatter があるだけである。ADR と frontmatter から観点を導けない対象については、黙って何も返さず（合格と読めてしまう）、補遺でドキュメントの欠落として報告する。

出力: 層が負っているのにテストが確かめていない観点。

### Lens 3: 意味的品質

アサーションに意味があるか。**このリポジトリにアンチパターンの目録は無い**ので、次の一般原則を適用し、目録が無いこと自体を補遺で報告する。

- 実質失敗しえないアサーション（型で保証済みの値への `expect(x).toBeDefined()`、唯一のアサーションが `expect(fn).not.toThrow()`）
- 具体的なアサーションを置くべき場所での snapshot — snapshot はコードの挙動をそのまま記録するので、バグも一緒に記録する
- subject が約束していない内部への結合（role とアクセシブルな名前があるのに `data-slot` で引く、private helper の呼び出し順を確かめる）
- 過剰な mock — 検証すると称しているものを mock している
- 時刻や乱数をリテラルで固定し、日付境界で腐るもの
- 名前がアサーションより多くを約束しているテスト

出力: `file:line` と、なぜ弱いかの一文。

### Lens 4: 分岐 × 意味の網羅（コード起点）

subject のソースを読み、関数ごとに 2 軸の行列を作る。**カバレッジ ≠ 意味**であり、100% ゲートを敷いたリポジトリではこの区別だけが情報を持つ。

**Lens 5 との分担**: Lens 4 は既にテストがある symbol の*内側*を見る。「テストが 1 つも無い」は Lens 5 の finding であり、Lens 5 が挙げた symbol の分岐をここで列挙し直さない（それは 1 件のギャップであって N 件ではない）。

**Axis A — 分岐網羅**: すべての論理分岐が少なくとも 1 ケースで到達される。あらゆる条件分岐、投げるエラーの種類、境界の対、nil / 空入力への防御。本体を実行しない harness だけが通る分岐はカバーされていない。

カバーするケースが無い分岐は **分岐未カバー** → severity **追加検討**。subject の `file:line` を引用し、`it` の名前を提案する。**criticality (1-10)** を本番影響で採点して添える（severity が「どの種類のギャップか」を言うのに対し、criticality は「壊れたらどれだけ悪いか」を言う直交軸）。壊れた場合に出荷されるリグレッションを一行で添える: 9-10 データ破壊 / 認証・認可の穴 · 7-8 ユーザ影響のあるロジック誤り · 5-6 軽微な edge · 3-4 網羅性のための nice-to-have · 1-2 任意。追加検討は criticality 降順に並べる。修正必須には criticality を付けない（常に今直す対象だから）。

**Axis B — 意味網羅**: カバー済みの各分岐のケースが、その分岐の*固有の* outcome をアサートしているか。

- エラー分岐は「どのエラーか」をアサートする。投げたことだけでは足りない
- 成功分岐は、他の分岐と区別できる結果の値や DOM 状態をアサートする
- 状態を変えるハンドラは、変更後の状態をアサートする。呼ばれたことだけでは足りない
- 境界のケースは、境界の両側で異なる結果をアサートする

カバーされているが固有の outcome をアサートしていない分岐は **分岐カバー済み・意味未検証** → severity **再考**。対象の分岐と、名目上それをカバーしているケースを結び付ける。

### Lens 5: subject シンボル網羅（コード起点）

subject のソースから、*symbol* の粒度で始める。答えるのは「そもそもテストが存在するか」の一点である。テストファイルから読み始める方式は見つけたテストしか判定できず、テストが 0 の symbol は見えない。

1. ペアになる subject から export シンボルの表を作る（export された関数・component・hook、および分岐ロジックを持つモジュールレベルの非 export 関数）。生成ファイルとテスト専用 helper は対象外
2. 各シンボルをテストに突き合わせる
3. 突き合わないシンボルを **シンボル未カバー** → severity **補完推奨** として挙げる。`symbol @ file:line` を引用し、`describe` 名と `正常系` / `異常系` の骨子を提案し、Lens 4 と同じ criticality を付す。criticality 降順に並べる

## Step 3. finding ごとに検証する

生き残った finding は、独立した `review-verifier` subagent（`sonnet`）へ渡す。finder を信用せずコードから結論を導き直し、**既定で懐疑的に倒す** — 曖昧さが残るなら PLAUSIBLE か REFUTED を付ける。

検証は finding 間で並列に走らせる。REFUTED はレポートから落とし、件数だけ伝えてノイズの水準を示す。CONFIRMED と PLAUSIBLE は残す。

## Step 4. レポートを合成する

日本語のレポート 1 本。

```text
# Test Review レポート

対象: <スコープ + ファイル一覧>
レンズ: 構造準拠 / 観点カバレッジ / 意味的品質 / 分岐×意味 / シンボル網羅
verifier 通過: CONFIRMED <n> 件 / PLAUSIBLE <m> 件 / REFUTED <k> 件（除外済み）

## サマリ
- 修正必須 / 補完推奨 / 再考 / 追加検討: 各 <件数>

## 構造準拠（修正必須）
## 観点カバレッジ（補完推奨）
## 意味的品質（再考）
## シンボル網羅（補完推奨）  ← criticality 降順
## 分岐網羅（追加検討）      ← criticality 降順
## 意味網羅（再考）

## 補遺
- <ADR / README の補完候補。意味的品質のカタログが未整備であることを含む>
```

severity の対応:

- **修正必須** — Lens 1。ADR 0090 の規則違反。CONFIRMED → 修正必須 / PLAUSIBLE → 確認推奨
- **補完推奨** — Lens 2 と Lens 5。層が負う観点が未実施、またはシンボルにテストが 1 つも無い
- **再考** — Lens 3 と Lens 4 Axis B。通るが何も明らかにしない
- **追加検討** — Lens 4 Axis A。subject 起点で見つけた未カバー分岐

## Step 5. 次の一手

具体的な提案を 1 つだけ添えて終える。このリポジトリにテスト生成スキルは無いので、修正は手作業になる。対象ファイルと追加すべきケースを名指しする。検証を通過した finding が無ければ、そう言う（「verifier 通過後 0 件です」）。

## Chainability

`impl-review` がこのスキルの呼び出し元である。その Step 4.5 がテスト観点をここへ委譲し、その実行中は自身の `test-gap` レンズを止める。したがって Lens 5 が「テストが 1 つも無い」を、Lens 4 が分岐 × 意味を所管し、どちらにも第三の報告者は存在しない。

呼び出し元が渡すもの:

- `scope` — 解決済みのファイル一覧（最初の質問を飛ばす）
- `base_ref` — ブランチ base 比較で動いている場合
- `reviewer_model` — finder と verifier の両方に適用し、`sonnet` の既定を上書きする
- `skip_verifier` — 真偽値。既定は `false`

payload を受けたときだけ、2 点が単独実行と異なる。

- **ペアテストが無い production ファイルもスコープに残す** — それこそが Lens 5 の対象である。Lens 1-3 はそのファイルについて読むものが無いので、合格と読める空の結果を返すのではなく、そのファイルについては起動しない
- **レポートは呼び出し元が埋め込む前提で返す。** severity 語彙（修正必須 / 補完推奨 / 再考 / 追加検討 + criticality）はそのまま保つ。呼び出し元の語彙へ写すと「規則に違反している」と「この分岐が未検証である」の区別が失われる

このスキルは他へ chain せず、`impl-review` へ呼び返すこともしない。

## 制約

- ❌ ファイルの編集（read-only）
- ❌ テストの実行（`make test-full` は別の重い gate — `repo-ops` §7）
- ❌ 検証を経ない finder 出力の採用。呼び出し元が `skip_verifier: true` を渡した場合を除く
- ❌ 規則一覧の焼き込み。ADR 0090 / 0091 とカーネル README を実行時に読む
- ❌ Go 固有の規約の持ち込み（`t.Parallel()`、`require` と `assert`、生成 mock）
- ❌ 規則の出所が沈黙している箇所での規約の発明。代わりに欠落として報告する
- ✅ verifier は既定で懐疑的に倒す
- ✅ レビュアーの既定モデルは `sonnet`。実装者と別モデルを保つためにオーケストレータが上書きしてよい
- ✅ criticality (1-10) は Lens 4 Axis A と Lens 5 の finding に付す本番影響のソート鍵で、レンズ由来の severity を置換しない
- ✅ 「テストが 1 つも無いシンボル」は Lens 5 の所管。Lens 1 の逆方向確認や Lens 4 と二重報告しない
