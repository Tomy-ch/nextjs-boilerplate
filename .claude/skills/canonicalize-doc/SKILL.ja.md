# Canonicalize Doc

このスキルは、英語の canonical な Markdown 文書と、その日本語ミラーのペアを生成または同期する。このリポジトリの規約に従って動作する。

## 利用シーン

以下のいずれかに該当する場合に使用する。

- canonical が変わり、そのミラーを同じ変更で追従させる —— 典型的なケース。文書を書くスキル（`sync-readme`、`new-feature`、`back-prop`、`scaffold-*` など）が最後の手順としてこのスキルへ連鎖する。
- 英語の canonical があるのにミラーが無く、そのパスがミラーを作らない一覧に載っていない。
- 日本語の下書きだけがあり、そこから英語の canonical を作る。
- 両方があるが、内容が乖離している。

対応ドキュメント種別 —— どれも同じ兄弟配置を使う:

- Claude Code スキルファイル: `SKILL.md` / `SKILL.ja.md`、およびその隣の `prompts/*.md` / `references/*.md`
- README: `README.md` / `README.ja.md`
- 追跡されているその他の Markdown 文書すべて: 同じディレクトリの `<name>.md` / `<name>.ja.md` —— `docs/**`（ADR、`docs/spec/**`、設計ノート、テンプレート）もルートの文書も同じ

## Step 0. 入力の確認

このスキルでは、**スキル起動直後に必ず `AskUserQuestion` で以下を確認する**。

1. **対象ファイルパス** — ユーザーが指している元ファイル（canonical またはミラー）。
2. **方向** — 何を生成するか:
    - `canonical-from-translation`: 日本語を英訳し canonical を書く。
    - `translation-from-canonical`: 英語を和訳しミラーを書く。
    - `sync-both`: 両方存在しており、差分を解消して片側を書き換える。

手順:

1. ユーザーや連鎖元のスキルがファイルパスを渡していれば候補として提示する。
2. 各候補の対となるファイル（同じディレクトリの `<name>.md` ↔ `<name>.ja.md`）を検出し、ADR [0140](../../../docs/adr/0140-documentation-operations.ja.md) のミラーを作らない一覧に載るパスを外す —— 一覧はコピーではなくそこで読む。
3. `AskUserQuestion` を呼び出す:
    - 質問 1: 「対象ファイルパスを確認してください。」（検出した候補を併記）
    - 質問 2: 「方向は？（canonical-from-translation / translation-from-canonical / sync-both）」 — 既存ファイル状況から推奨オプションを併記。
    - `sync-both` の場合はさらに「どちら側を source of truth として同期しますか？」を確認する —— ユーザーが別に指定しない限り canonical。

**一括モード**: 1 つの変更が複数の canonical に触れたとき（連鎖元のスキル、あるいは一括の掃除）は、ファイルの一覧と全体に共通する 1 つの方向を、1 回の `AskUserQuestion` でまとめて確認する。ファイルごとに 1 問ずつ聞かない。ユーザーが一覧から外したファイルには触れない。

対象パスと方向が確定するまでは、翻訳のためのファイル読み書きを行わないこと。

## リポジトリ規約

ペアの両側を生成する際に、以下の規約を適用する。canonical 言語モデルは ADR [0140](../../../docs/adr/0140-documentation-operations.ja.md) が持つ。このセクションは、このスキルがそれをどう実行するかである。

### 言語

- **サフィックス無しのパスの英語が canonical で、日本語は兄弟のミラー `<name>.ja.md` である。** 日本語だけのパラレルツリーは無い。canonical が source of truth で、ミラーがそれに追従する。
- **追跡されているサフィックス無しの `.md` はすべてミラーを持つ。例外は 0140 決定 1 の閉じた一覧だけである。** その一覧に載るパスにミラーを作らない。
- **エージェントは `*.ja.md` を読まない。** 例外はこのスキルだけで、指定された 1 つのペア（または確認済みの一括の一覧）に限る。
- **`AGENTS` のペアでは、書いてよいのはミラーだけである。** `AGENTS.md` はこのスキルの実行中も保護対象のまま（下記）なので、取りうる方向は `translation-from-canonical` だけ。

### canonical 側

- ミラーへリンクしない。プレーンテキストで名前を挙げるのは構わない —— `SKILL.md` は 1 行のポインタ文をリンク無しで持つ。
- `SKILL.md` は YAML frontmatter（`name`、`description`）を必須とする。`description` は英語で、スキル選択精度が最大化されるように書く。
- その他の frontmatter（レイヤー README の `imports-allowed` など）は canonical だけが持つ。

### ミラー側

- canonical が何を持っていても、**frontmatter を持たない**。frontmatter は canonical だけで読み書きされるので、コピーは最新を名乗ったまま古くなる。
- **1 行目は同期の注記**で、空行を挟んで日本語の H1 が続く。`<basename>` には canonical のファイル名を入れる:

  ```markdown
  > **このファイルは [`<basename>.md`](<basename>.md) の日本語訳です。**
  > 直接編集しないでください。変更は英語の canonical な `<basename>.md` を先に更新し、そのうえでこの日本語訳を同期してください。
  > エージェントが読むのは `<basename>.md` だけです。このファイルは人間が読むための翻訳です。
  ```

- `SKILL.ja.md` と `AGENTS.ja.md` は既存の 3 行の注記を使う。3 行目は、スキルや規約として何が読み込まれるかを述べる。

### ミラーの用語

Web と一般のソフトウェア開発の用語は、**カタカナか英語で書き、漢字の直訳語にしない**。定着した漢字の用語 —— 関数、型、依存、境界、設定、環境、契約、取得、生成物、台帳、外枠 —— はそのまま残す。この表がこの規則の恒久的な置き場である。書くものすべてに各行を当てる。

常に置き換える:

| --- | --- | --- | --- |

| インベントリ | インベントリ | | |

| レンダリング | レンダリング | プレゼンテーションレイヤー / プレゼンテーションレイヤー | プレゼンテーションレイヤー |
| サブツリー | サブツリー | シェル | シェル |

## AI Modification Scope

AGENTS.md の "Exception: Skill Execution" セクションに基づき、このスキル実行中は AI Modification Scope の縛りを解放する。ただしユーザーが Step 0 で確定したドキュメントペアに限定する。

変更可能なパス:

- 確認済みの対象ファイル。
- その対となるファイル（新規作成または再生成）。
- それ以外は変更しないこと。

スキル実行中でも保護対象として維持されるもの:

- `AGENTS.md` / `CLAUDE.md`
- 生成ファイル — `.gitattributes` が `linguist-generated` を宣言するパス（`git check-attr linguist-generated -- <path>` で引ける）と、`docs/` 配下の生成物
- `.claude/settings.json` の `permissions.deny` に列挙された任意のパス

## Step 1. 元ファイルの読み込み

確認済みの元ファイルを全文読み込む。方向が `sync-both` の場合は両ファイルを読む。

## Step 2. 出力パスの決定

- `canonical-from-translation`: `<name>.ja.md` → 同じディレクトリの `<name>.md`。
- `translation-from-canonical`: `<name>.md` → 同じディレクトリの `<name>.ja.md`。
- `sync-both`: source of truth ではない側を書き換える。

## Step 3. 翻訳（または同期）

- 見出し構造、リスト階層、コードブロック、リンク先、`<a id>` アンカー、撤去マーカーを、同じ位置で正確に保持する。
- 本文、コードブロック内コメント（元が翻訳されていた場合のみ）、インラインテキストを翻訳する。
- 翻訳しないもの: 識別子、ファイルパス、コマンド、コードサンプル（自然言語文字列で元が翻訳されていたものを除く）。
- canonical 側とミラー側の規則を適用し、ミラーには上の用語の表も適用する。

## Step 4. 出力ファイルの書き込み

- 生成したファイルを対象パスへ書き込む。
- 両方存在しユーザーが `sync-both` を選択した場合は、source of truth ではない側のみ書き込む。

## Step 5. 相互参照の追加

- ミラーは同期の注記から始まり、注記が canonical へリンクする。
- `SKILL.md` は `SKILL.ja.md` の名前を挙げる 1 行のポインタ文を、リンク無しで持つ。
- canonical からミラーへのリンクは決して足さない。

## Step 6. 検証

- 両ファイル間でセクション数と見出しの段を diff し、1:1 で対応していることを確認する。見出しの段のパリティ、1 行目の同期の注記、frontmatter が無いことは、`skill-lint` が CI で全ペアについて検査する。機械では判定できないもの —— ミラーが同じことを言っているか —— がこの手順の仕事である。
- `doc-links` は canonical からミラーへのリンクを reason `mirror` で落とす。そうしたリンクを持ち込まない。
- コードブロックがバイト同一であることを確認する（コードブロック内の翻訳済み散文部分を除く）。
- きれいに対応付けられないセクションがあればユーザーに報告し、対応方針を確認する。

## Step 7. 書いたファイルの整形

生成ファイル（および `sync-both` モードでは同期側）の書き込み後、このスキルが書いたファイルだけに `pnpm exec markdownlint-cli2 --no-globs --fix <書いたパス>` を掛ける。`pnpm lint:md` は pre-commit hook と CI に任せる（`docs/playbook.md`: Do not pre-run the gates）。

## チェックリスト

完了報告時に以下を確認すること。

- [ ] 対象ファイルパスを `AskUserQuestion` でユーザーに確認済み（一括の一覧なら 1 問で）
- [ ] 方向（`canonical-from-translation` / `translation-from-canonical` / `sync-both`）を確認済み
- [ ] `sync-both` の場合は source of truth 側を確認済み
- [ ] 0140 決定 1 のミラーを作らない一覧に載るパスにミラーを作っていない
- [ ] ミラーは兄弟の `<name>.ja.md` で、1 行目が同期の注記で、frontmatter を持たない
- [ ] canonical がミラーへリンクしていない
- [ ] ミラーが用語の表に従っている
- [ ] セクション構造とコードブロックが 1:1 で一致している
- [ ] `markdownlint-cli2 --fix` を書いたファイルだけに掛けた
- [ ] 確認済みペア以外のファイルを変更していない

## 注意事項

- 確認済みのドキュメントペア以外のファイルを変更しないこと。
- 識別子、ファイルパス、コマンド、その他の技術トークンを翻訳しないこと。
- 日本語へ翻訳する際は、人間が読む自然な日本語の散文にする。英語へ翻訳する際は、簡潔・宣言的な記述を心がける。
- 出力トークン（`問題なし`、`重大度` など）、PR テンプレートのセクション名、コミット件名の例、日本語のトリガ語句である日本語のリテラルは、英語の canonical の中でも日本語のまま残す。
