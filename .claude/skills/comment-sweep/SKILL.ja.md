# Comment Sweep

蓄積したコメントを、既存のレビュアーが問えない 1 つの問いで裁く。**この内容はここに属するか。**

同じディレクトリの `SKILL.ja.md` に日本語の参考訳がある（スキルとしては読み込まれない。人間の参照用）。

## 使用する場面

- 1 行ずつは正しいのに、あるディレクトリのコメントが膨れて散文的に感じる
- doc コメントが設計論・脅威モデルの議論・棄却した代案の一覧へ育っている
- 同じ根拠が ADR とその後に続くコードの両方にある。片方は必ず腐り、腐るのは誰も読み返さない側である
- カーネル / feature / `scripts/` の定期的な整理
- リリース前や fork 切り出しの前。蓄積した記述が他人の負担になる

## このスキルを使わない場面

- **今書いた変更のコメント** — `impl-review` の `comment-reviewer` が差分を所管する。あちらは品質を、こちらは在庫の管轄を裁く
- **README / docs の散文の質** — `doc-reviewer`
- **README ↔ コードの構造ドリフト** — `sync-readme` / `back-prop`
- **実装やテストのレビュー** — `impl-review` / `test-review`

## このスキルが在る理由

`comment-reviewer` が答えられるのは **削除**（その内容は在るべきでない）か **書換**（内容は正しいが述べ方が悪い）だけである。どちらにも当てはまらない第 3 の場合がよくある。**内容は正しく残す価値もあるが、コメントに属していない。**

その判定が **移設**であり、read-only のレビュアーには 2 つの理由で持てない。**移設先の文書を書く**必要があり、それはレビュアーがしてはならない。そして判断対象が 1 つの差分ではなく蓄積した在庫である —— ADR と 5 箇所の呼び出し地点に重複した同じ根拠は、変わったものだけを見ていては見えない。

## このスキルが読むもの

**実行時**に読む。方針を焼き込まない —— 基準は動くので、このファイルがその古い写しになってはいけない。

| 出所 | 何を決めるか |
| --- | --- |
| `docs/rules.md` | **Comment Rules 節を持つならそれが基準。** 現時点では持たない。推測せず確認する |
| `AGENTS.md` | Language Rules（コメントは日本語）と Code Style |
| `.claude/agents/comment-reviewer.md` | 現に効いている内容基準 —— What + 前提がその呼び出し箇所に在る制約。How は書かない |
| `docs/adr/` | 移設先の候補と、各 ADR が既に述べていること |
| 掃引先の上位にある層 / feature の `README.md` | もう 1 つの移設先候補と、その宣言された責務 |

## 手順 0. 範囲を決める

引数から範囲を採るか、`AskUserQuestion` で尋ねる。

- 「変更で触れたファイル」 —— 呼び出し元がファイル一覧を渡した場合（Chainability を参照）
- 「1 カーネル / 1 feature」 —— 例: `src/adapters/`、`src/features/products/`
- 「`scripts/` の 1 ツール」
- 「パスを指定」

**掃くのは 1 ディレクトリずつ。** リポジトリ全体の掃引は誰も終えられない承認待ちの列を作り、半端に終わった列は無いより悪い —— 読み手が掃引済みと未掃引を区別できなくなる。

## 手順 1. 基準と移設先を読む

1. コメントの基準を読む（上の表）。記憶からではなく今回の実行で読む
2. 範囲の上位の `README.md` と、そこが参照する ADR を読む
3. 範囲の全ファイルを読む。コメント**と**その下のコードの両方。管轄の判断はコメントだけでは下せない —— 前提がその呼び出し箇所に在るかは、コードについての事実である

## 手順 2. 範囲の全コメントを分類する

判定は 4 つ。最初の 3 つは既にあり、4 つめがこのスキルの足すものである。

| 判定 | どんなとき | 動作 |
| --- | --- | --- |
| **維持** | 正しい What、または前提がその呼び出し箇所に在る制約 | そのまま置く |
| **削除** | How のナレーション、言い換え、経緯、トートロジー、コードが既に満たしているマーカー | 取り除く |
| **書換** | 内容は正しいが述べ方が悪い —— 腐っている、曖昧、事実より長い | その場で書き直す |
| **移設** | 正しく残す価値もあるが、前提がその呼び出し箇所に**無く**、覆れば誰かが文書を更新せざるを得ない | その文書へ移し、効力のある残余と 1 行の参照を残す |

**移設の判定基準**: その宣言を編集せずに、この記述を偽にできるか。できるなら、ここでは誰も検証できず、偽になっても何も報告しない。**どこでなら検査されるか**を問う。そこがその記述の家である。

### 移設先と、拒むべき 2 つの誤配

| 内容 | 移設先 |
| --- | --- |
| 構造・機構・方針についての決定 | その領域を所管する ADR |
| その層 / feature が受け入れるもの・受け入れないもの | そのディレクトリの `README.md` |
| 前提がその呼び出し箇所に在る制約 | **コードに残す** |

名前を付けておくべき誤配が 2 つある。

- **ライブラリ固有の挙動はコードに残す。** 「この API はキーが無いとき throw せず `null` を返す」は呼び出し箇所についての事実であって決定ではない。ADR へ移すと、次の編集者がまさに編集している場所で必要とする細部を埋めることになる
- **業務知識を ADR へ入れない。** 発送前なら購入を取り消せる理由はその feature の知識であり、その feature の README（またはバックエンドの契約）に属する。決定の記録ではない。業務ルールを溜めた ADR は決定ログとして読めなくなる

## 手順 3. 承認のループを回す

所見を**判定ごとに束ねて**、影響の大きい順（移設 → 削除 → 書換）に提示する。各項目に次を添える。

- `file:line` とコメントの原文
- 判定と、一文の理由
- 移設なら、移設先のファイルと、そこへ入れる文言そのもの
- コードへ残す残余（制約が残るなら、呼び出し箇所を無言にしない）

`AskUserQuestion` で束ごとに確認する:「この判定で適用しますか？」/「個別に確認したい」/「この分類は見送る」。1 回の確認で 40 箇所を編集する掃引はレビューできない。

## 手順 4. 適用 —— コードと移設先を同時に

承認された項目ごとに、**両側を同じ手順で**書く。

1. 移設先の文書へ、その文書の語り口と節構成に合わせて根拠を足す。コメントをそのまま貼らない —— コメントと文書では読まれ方が違う
2. コードを編集する。移した散文を取り除き、効力のある残余を残し、移設先への 1 行の参照を足す

片方だけを行わない。移設先が存在しないうちにコードから根拠を消すのは情報の破壊であり、両端を握っているのはこのスキルだけである。

承認に関わらず効くガード。

- **機能ディレクティブを消さない** —— `// @ts-expect-error`、`// biome-ignore …`、`// eslint-disable*`、`/** @jsxImportSource … */`、`// Code generated … DO NOT EDIT`、shebang。（`"use client"` / `"use server"` は文字列ディレクティブでコメントではない。触らない）
- **保護されたパスを編集しない。** `AGENTS.md`、`LICENSE`、`.claude/settings.json` の `permissions.deny` にあるものは触らない。Accepted な ADR 本文は v1.0.0 未満では編集でき、通常の移設先である。v1.0.0 以降は他の ADR 編集と同じく承認を要する
- **生成ファイルに触れない** —— `**/gen/**`、生成バナーを持つもの
- **コードの振る舞いを書き換えない。** コードが誤っているせいでコメントが誤っているなら、報告して止まる

## 手順 5. 検証

```sh
pnpm fix
pnpm lint:ci
pnpm md-lint
```

そのうえで、触れたファイルの差分を読み直し、コメントと文書だけが変わったことを確認する。振る舞いは不変でなければならない。`git diff` に文が変わった箇所が出たなら、それはこの実行の欠陥である。

## 手順 6. 報告

ファイルごとに何を 維持 / 削除 / 書換 / 移設 したか、移設がどこへ着地したかを述べる。**掃かなかったもの**も平明に述べる —— 後回しにしたディレクトリ、設計判断が要るため見送った所見。述べない省略は「このディレクトリは綺麗だ」と読まれる。

## Chainability

`impl-review` は、変更が触れたファイルのコメント**在庫**をこのスキルへ委譲する。テスト観点を `test-review` へ委譲するのと並ぶ位置である。分担が成立するのは、2 つが別のものを見ているからである —— `comment-reviewer` は差分が*足した*コメントを裁き、このスキルはそのファイルが*抱えている*在庫を裁く。この形で呼ばれたときは、範囲を呼び出し元から受け取り手順 0 を飛ばす。

## 制約

- ✅ 基準と移設先の文書を今回の実行で読む
- ✅ 掃くのは 1 ディレクトリずつ
- ✅ 承認は判定の束ごとに取る。掃引ごとではない
- ✅ 移設先の文書とコードを同じ手順で書く
- ❌ ライブラリ固有の挙動をコードから移設する
- ❌ 業務知識を ADR へ移設する
- ❌ 機能ディレクティブの削除、生成ファイルへの接触、保護されたパスの編集
- ❌ 振る舞いの変更
