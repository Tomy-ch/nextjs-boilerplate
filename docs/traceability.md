# トレーサビリティ

**決定が何によって守られているかの一覧。** 集計であって決定ではない —— 各項目の強制手段は
[ADR](adr/README.md) の各決定と、[実装規約](rules.md) の各行と、実装タスクの issue が持つ。
ここはそれを並べ、**「散文のみ」で終わっているものに決着が付いているか**を見る場所である。

**ここに新しい規約を書かない。** 書きたくなったら、それは決定なので所有する文書へ置く
（[0144](adr/0144-decision-enforcement-pairing.md)「集計は決定を持たない」）。

## なぜ集計するのか

散文で書いた決定は、誰かが読み直さない限り守られたかどうかが分からない。機械が見ているものと
そうでないものを混ぜて数えると、**全体としてどれだけ守られているかが誰にも見えなくなる**。

区別して数える意味は、散文を減らすことではない。**散文のままでよいものと、寄せ忘れているものを
分ける**ことにある。前者は理由を持ち、後者は仕事が残っている。

## 規約（`docs/rules.md`）

**節頭が 20 節、規約ごとに自分で判定を述べるものが 33 件。**

節頭の `> Rationale: …; enforced via …` は、その節をどの機械が見ているかを述べる。節頭の手段に
載らない規約だけが、その場で寄せられるかどうかを述べる（`rules.md` 冒頭の規約）。

| 判定 | 件数 | 意味 |
| --- | --- | --- |
| 寄せられない | 20 | **原理的に機械化できない。** 理由を各規約が持つ |
| 寄せられる | 8 | 寄せ方は決まっており、実装だけが無い |
| 機械（未実装） | 4 | 機械化不能ではなく、**既存検査の走査範囲外** |
| 一部寄せられる | 1 | 静的に決まる部分と、契約を読まないと決まらない部分に分かれる |

**「寄せられない」と「機械（未実装）」を混ぜない。** 前者は道が無く、後者は道が在って歩いていない。
混ぜると、やれば済むものが「やれない」に埋もれる。

### 決着が要る 13 件

「寄せられる」8 + 「一部寄せられる」1 + 「機械（未実装）」4。**理由は各規約が既に持つ**ので、
ここは寄せ先と状態だけを並べる。

| 規約 | 寄せ先 | 状態 |
| --- | --- | --- |
| `use cache` の内側の `fetch` に個別のキャッシュ指定を置かない | ESLint | 未着手 |
| `revalidatePath("/", "layout")` を使わない | ESLint。所有境界の判定は人に残る | 未着手 |
| キャッシュのタグは 2 段だけ、付けるのは `adapters` 1 か所 | ESLint。資源名と契約の整合は不可 | 未着手・**一部のみ** |
| Server Action の version skew で full reload へ誘導する | integration テスト | 未着手（テストが無い） |
| 部品の中身を帯で分岐させない | ESLint | **設計判断待ち** |
| 画面の骨格を container query で分岐させない | ESLint | **設計判断待ち**（上と対） |
| `z-index` に任意値（`z-[…]`）を使わない | ESLint | 未着手 |
| 名前の付いた関数に TSDoc の枠を書く | 機械（対象もタグも宣言の形から決まる） | 未着手 |
| 破棄を生き延びる側に題材の語彙を残さない | 既存検査の走査範囲（いまは `src/` と `mocks/` だけ） | 未着手 |
| make の変数展開ではなく `export <NAME>` で渡す | 既存検査の走査範囲（Make の展開はどの検査も通らない） | 未着手 |
| シェル変数を全角の直前で `${NAME}` と囲む | 新しい検査（終了コードに出ない） | 未着手 |
| 作業ツリーを触る git 操作を使わない | `permissions.deny` に綴りを足す | 未着手 |
| `git add -A` / `--amend` などを使わない | `permissions.deny` に綴りを足す | 未着手 |

**設計判断待ちの 2 件は動かさない。** 規則として正しいかが決まっていないものを機械にすると、
間違いのほうが固定される。

**寄せる作業そのものはここでは行わない。** 判定を持つことと、規則を書くことは別の PR である
（設計判断待ちの 2 件を除く 11 件は #634）。

## 実装タスク（issue）

50 件。**強制手段の欄を持つのは 13 件**で、うち散文を含むのは 3 件（#483 / #447 / #317）。

### 37 件が欄を持たない

欄は issue テンプレートの必須項目だが、テンプレートの `required: true` が縛るのは GitHub の Web
フォームだけで、`gh issue create --body-file` は素通りする —— **そしてそれが AI が起票する経路である。**

欄の有無は起票時期と相関しない（2026-07-30 の #116 は持ち、2026-09-02 の #521 は持たない）。
古いから欠けているのではなく、**経路によって欠ける**。

塞いだ形は 2 つある。

- `.github/workflows/issue-field-lint.yaml` —— issue が作られた / 編集された時点で本文を見て、
  欠けている欄を issue へコメントする。PR ゲートにしないのは、**PR は issue を作らない**ため
- `make issue-field-lint` —— 開いている実装タスクをまとめて見る。過去に開いたままのものを掃く口

**閉じた issue の欄は埋めない。** そこから読む人はもう居らず、埋めても着地済みの実装が変わらない。
開いているものだけが、これから読まれる。

## 機械が届かないと分かっているところ

`app` の element 分割は、行ごとに強制の届き方が違う。表は
[0025](adr/0025-app-layer-elements.md) が持ち、`architecture.ts` の `APP_ELEMENTS` が
**`import` 先の集合として書ける分**を強制する。書けないものが 2 つ残る。

- `server config` と `NEXT_PUBLIC` の公開定数は同じ `config` カーネルに居る
- `route-segment` の `observability` / `config` の限定は「何を import してよいか」ではなく
  「**どう使ってよいか**」である

どちらも実装の不足ではなく、import の可否では表現できない。**層別のアーキテクチャ監査（未実装）が
受け持つ範囲で、それが在るまでは人のレビューが拾う。**

## この一覧が答えないこと

- **書かれた強制手段が妥当か。** 欄の有無しか見ていない。「テスト」と書いてあってテストが無い、は
  ここでは分からない（[実装規約](rules.md) 側は `doc-reviewer` の accuracy が見る）
- **散文のままでよいという判断が正しいか。** 理由が書かれているかまでを見る
- **どの規約を指しているか。** `rules.md` の規約に安定した識別子が無いため、この一覧は規約を
  名前でしか指せない。規約が書き換わると**指し直す手がかりが消える**（過去に番号で指していた
  10 項目は、節構成への組み替えで参照先を失った）。識別子をどうするかは #633
