# Locale-Aware Formatting (Dates and Numbers) and Date Arithmetic

Independently of i18n itself (the exclusion in [0121](0121-i18n-strategy.md)), this ADR settles **locale-aware formatting of dates and numbers** and **date arithmetic (addition / subtraction / differences / parsing, etc.)**, which are needed from day one even in a single-locale setup: **display formatting = `Intl.*` (ECMA-402) / date arithmetic = `date-fns` / where each lives / the seam that supplies the default locale**. [0121](0121-i18n-strategy.md) covers only the exclusion of the translation infrastructure and locale resolution; this ADR **fully settles, under kernel jurisdiction ([0021](0021-frontend-responsibility.md) / [0027](0027-directory-structure.md)),** where formatters and date-arithmetic helpers belong.

## Status

Accepted

## Context

- **Displaying dates and numbers is needed from day one even with a single locale**, and unless a home is decided, **the same formatter is reinvented per feature** (the "promote to a kernel once referenced from several places" judgment of [0021](0021-frontend-responsibility.md) gets postponed)
- On the other hand, **"arithmetic" on dates — addition / subtraction, differences, parsing, comparison, ISO conversion — is outside the reach of `Intl`**. `Intl` is **dedicated to locale-aware display (format)** and has no arithmetic API. Building arithmetic by hand on the bare `Date` reproduces bugs around leap years, DST, time-zone boundaries and end-of-month carry in every feature. As a general application foundation this arithmetic layer is needed from day one, so `date-fns` is adopted and consolidated in a kernel

## Decision

### 1. Display formatting uses `Intl.*` (ECMA-402) (invariant)

- **Locale-aware display (format) of dates, numbers, currency, percentages, etc. uses the runtime-standard `Intl.*` (`Intl.DateTimeFormat` / `Intl.NumberFormat`, etc.)**. The **display functions of `date-fns` such as `format` / `formatDistance` are not used; display goes through `Intl` alone** (no double formatting; see §2)
- **Vendor-independent justification ([0010](0010-standards-and-non-lockin.md))**: `Intl` is **the ECMA-402 (ECMAScript Internationalization API) standard**, not the API of a particular vendor or framework. It is **built into the JS runtimes** of both browsers and Node.js (which ships full ICU), and with zero dependencies **the same API is available in every execution context — Server Component, Client Component and Route Handler** (output does depend on the runtime's ICU version and locale data, so SSR (Node) and CSR (browser) can differ; how such display drift is handled is owned by the rule in `docs/rules.md#formatting` that dates and times state their display time zone and the server and client never render different values initially). The operational test of [0010](0010-standards-and-non-lockin.md), "is it still justified with that vendor removed from the justification?", holds trivially because `Intl` **has no vendor at all** (it is the language standard itself)
- This **complements rather than contradicts** [0121](0121-i18n-strategy.md) (no i18n library, translation infrastructure or locale resolution bundled). What 0121 excludes is **translation and locale resolution**, **not formatted display in a single locale**

### 2. Date arithmetic adopts `date-fns` (complementing `Intl`; no double formatting)

- **The date "arithmetic" that `Intl` lacks — addition / subtraction (`addDays` / `subMonths`, etc.), differences (`differenceInDays`, etc.), parsing (`parseISO`, etc.), comparison (`isBefore` / `isAfter`), boundaries (`startOfDay` / `endOfMonth`), etc. — uses `date-fns`**. It is introduced through the adoption flow of [0004](0004-library-management.md) (**exact pin + `pnpm audit`**)
- **Division of roles with `Intl` (no double formatting)**: split strictly into **display = `Intl`, arithmetic = `date-fns`**. The `format` family of `date-fns` (`format` / `formatDistance` / `formatRelative`, etc.) and its locale package (`date-fns/locale`) are **not used for display** (the `Intl` of §1 is the only way out for display). The same display is not held twice, in both `Intl` and `date-fns`. The responsibility of `date-fns` is **strictly limited to computing, creating and parsing `Date` values**, and the resulting `Date` is ultimately rendered with `Intl`
- **Vendor-independent justification ([0010](0010-standards-and-non-lockin.md))**: `date-fns` is **a set of immutable pure functions** taking and returning `Date` objects — it introduces no wrapper type of its own (Moment / Luxon's `DateTime`, Day.js's `Dayjs`, etc.), so **no library-specific object pollutes the type boundary** (consistent with the no-type-leakage rule of [0020](0020-adopted-architecture.md)). It is **tree-shakable** per function (only the functions used land in the bundle), and because each helper takes a standard `Date` and returns a standard `Date`, **swapping to another library (Luxon / Temporal, etc.) stays within the module boundary**. The operational test of [0010](0010-standards-and-non-lockin.md), "is the pattern still justified with the vendor removed?", is Yes — the **structure** of consolidating arithmetic helpers in `model` and keeping the standard `Date` as the boundary type is not specific to `date-fns`, and the structure is unchanged even if `date-fns` is replaced by a Temporal implementation once [ECMAScript Temporal](https://tc39.es/proposal-temporal/) is built into runtimes. Hence "among the many ways to do arithmetic, `date-fns` was chosen as one factor on the independent grounds of a standard `Date` boundary, tree-shakability and no type pollution" = no lock-in
- **Keeping it replaceable ([0010](0010-standards-and-non-lockin.md))**: `date-fns` functions are **not imported directly from features / components and scattered**. Date arithmetic is used through the thin helpers of the `model` kernel described next, confining direct vendor references to a single home (keeping the replacement point in one place)
- **`date-fns` is not used to compute boundaries that must pin a time zone**. The boundary functions of `date-fns` (`startOfDay` / `startOfMonth`, etc.) **resolve boundaries in the runtime's time zone**, so the same input gives different answers on the server (usually UTC) and in the browser (wherever the viewer is). The `DEFAULT_TIME_ZONE` of §3 is a pin that exists precisely to cut that dependency, so using `date-fns` here would make the pin meaningless. **Resolving a zone to a calendar date is done with the `Intl` of §1 (with `timeZone` specified), and carrying year / month / day is done on `Date.UTC`** (zone-free arithmetic, so the runtime does not affect it). This shape is likewise confined to the thin helpers in `model` and not scattered into features, as in the item above
  - **This applies only to arithmetic that decides "the calendar boundary itself"**. Arithmetic that involves no zone interpretation — differences, comparisons and parsing between `Date`s — keeps using `date-fns` as before
  - When building a period for aggregation or filtering as **a half-open interval of instants**, output **RFC3339 with an offset**. A string without an offset leaves its interpretation to implementation differences between the caller and the connected service
- **Date-only values (birthdays, publication dates, etc.) do not cross a boundary as a `Date`; they travel as a `YYYY-MM-DD` string**. A `Date` is an instant, and if the producer and consumer are in different time zones, the same instant is read as different calendar dates — this shape keeps browser and server time-zone conversion from applying to date-only values. An input component may use a `Date` internally, but the value it exposes (callback / hidden input) is a string. When handling a moment that includes a time and a time zone, either the caller decides the TZ and converts to a date-time, or a different component that handles instants is used

### 3. Where formatters and date-arithmetic helpers live = the `model` kernel

- **Locale-aware formatters (thin wrappers over `Intl.*`) and date-arithmetic helpers (thin wrappers over `date-fns`) both live in the `model` kernel**. In the responsibility definitions of [0021](0021-frontend-responsibility.md), `model` explicitly owns "display ValueObjects / **formatters** / unit conversion / display validation rules", so the home of formatters and date arithmetic (shaping domain values for display) is already named as `model`. Physical placement follows `src/model/` of [0027](0027-directory-structure.md) (flat colocation, per-file by default)
- **Consistency with the promotion rule ([0021](0021-frontend-responsibility.md))**: formatters and date-arithmetic helpers are exactly the promotion target "display logic (VO / formatter) → `model`". However, following the kernel acceptance criteria of [0021](0021-frontend-responsibility.md), **a one-off helper used by only one feature lives inside that feature** and is promoted to `model` once several features reference it (cross-cutting in `model`, single-feature helpers inside the feature). Direct references to `date-fns` are likewise consolidated into thin `model` wrappers once they become cross-cutting (§2 replaceability)
- **Confirming the forbidden directions**: formatters and date-arithmetic helpers are display logic and are not placed in `components` (pure UI) / `adapters` (external connections) / `capabilities` (runtime-capability hooks) ([0021](0021-frontend-responsibility.md) dependency matrix and naming discipline; no generic `utils` home is created either)

### 4. The seam that supplies the default locale

- **The default locale is consolidated in a single named constant inside `model` (e.g. `defaultLocale`)**, and formatters **take the locale as an explicit argument and use the default locale when it is omitted**. The default locale is not hard-coded in individual components (it is gathered into a single seam)
- This single seam becomes **the replacement point when i18n is adopted ([0121](0121-i18n-strategy.md))**. When next-intl or similar is introduced, the seam is swapped to supply "the active locale resolved from `proxy.ts` / the `[locale]` segment ([0121](0121-i18n-strategy.md) / [0043](0043-middleware-policy.md) / [0040](0040-routing-rendering-strategy.md))". The core stays at **the minimal seam of a single constant** and lays down no multi-locale resolution mechanism (resolver / port) (the specifics are settled when i18n is adopted; see "Notes")

## Prohibitions

- ❌ Using `date-fns`'s `format` / `formatDistance` / `formatRelative`, etc., or `date-fns/locale` for **displaying (formatting)** dates (display goes through the `Intl` of §1 alone; no double formatting) (Enforcement: Prose — **mechanizable** (`importNames` of ESLint `no-restricted-imports` can reject `format` / `formatDistance` / `formatRelative` from `date-fns` and `date-fns/locale`. No rule exists))
- ❌ Holding the same display **twice**, in `Intl` and `date-fns` (do not break the division of roles: display = `Intl`, arithmetic = `date-fns`) (Enforcement: Prose — **partly mechanizable**. Importing `date-fns` display functions can be rejected with `no-restricted-imports`, but no rule exists. Whether hand-built string assembly reproduces the same display as `Intl` is decided only by reading the meaning of the output)
- ❌ Adopting a date library with **its own DateTime wrapper type**, such as Moment / Luxon / Day.js (it pollutes the type boundary; keep the standard `Date` as the boundary type. [0020](0020-adopted-architecture.md) no type leakage / §2) (Enforcement: none — a decision not to adopt. No library with its own DateTime type is among the dependencies, and a change adding one shows up in the diff as a dependency added to `package.json`)
- ❌ **Importing `date-fns` functions directly from features / components and scattering them** (cross-cutting use goes through thin `model` wrappers; confine direct vendor references to one place to keep the replacement point. §2 / [0010](0010-standards-and-non-lockin.md)) (Enforcement: Prose — **partly mechanizable**. Importing `date-fns` from `components` can be rejected with `no-restricted-imports`, but no rule exists. One-off helpers inside a feature may reference it directly, so whether an import from a feature is "scattering" is decided by judging how widely it is referenced)
- ❌ Adding `date-fns` without going through the [0004](0004-library-management.md) flow (exact pin + `pnpm audit`) (Enforcement: the audit gate job of Dependency Scan rejects versions with known vulnerabilities. The exact pin is Prose — **mechanizable** (a range specifier `^` / `~` in a `package.json` version can be detected. No rule exists))
- ❌ Passing a date-only value across a boundary (callback / hidden input / API contract) as a `Date` (§2; carry it as a `YYYY-MM-DD` string) (Enforcement: Prose — **not mechanizable**. Date-only values and instants are both of type `Date` and cannot be told apart by type)
- ❌ Reinventing the same locale-aware formatter or date-arithmetic helper per feature (cross-cutting ones are promoted to `model`. [0021](0021-frontend-responsibility.md)) (Enforcement: Prose — **not mechanizable**. Whether two helpers produce the same display is a judgment of meaning, not decided by the shape of the code)
- ❌ Placing formatters or date-arithmetic helpers (display logic) in `components` / `adapters` / `capabilities` / a generic home (they belong to `model`. [0021](0021-frontend-responsibility.md) dependency matrix and naming discipline) (Enforcement: Prose — **partly mechanizable**. Creating `Intl.*` and importing `date-fns` in `components` / `adapters` / `capabilities` can be rejected with `no-restricted-syntax` / `no-restricted-imports`, but no rule exists. Whether something is hand-written display logic is decided only by reading it)
- ❌ Hard-coding the default locale in components here and there (gather it into the single seam = a `model` constant) (Enforcement: Prose — **mechanizable** (passing a string literal to the locale argument of `Intl.*` / `toLocale*String` outside `model` can be rejected with `no-restricted-syntax`. No rule exists))
- ❌ Writing **day-to-day rules** for using `Intl` / `date-fns` (always passing an explicit locale argument, memoizing to avoid the creation cost of `Intl.*` instances, not writing `Date#toLocaleString` and the like inline, importing `date-fns` per function, etc.) into the ADR body (rules go in `docs/rules.md`. [0140](0140-documentation-operations.md)) (Enforcement: Prose — **not mechanizable**. Whether a sentence is a rule or a decision is decided by the meaning of its content, not by the shape of the document)

## Notes

- **Decision / rule split ([0140](0140-documentation-operations.md))**: this ADR settles the **decisions** (adopting `Intl` for display / adopting `date-fns` for arithmetic / the no-double-formatting split / helper home = `model` / the default-locale seam). **Day-to-day usage rules** (always pass an explicit locale argument; reuse `Intl.*` instances rather than creating them and leaving them; avoid writing `toLocaleString` inline in components and go through a formatter; import `date-fns` per function so tree-shaking works; etc.) are held by `docs/rules.md` with a back-reference to this ADR
- **TZ / hydration mismatches and relative time (periodic client updates of `Intl.RelativeTimeFormat`) are outside the reach of this ADR**. This ADR covers **only where static formatting of absolute times and numbers lives, adopting `Intl` for display, and adopting `date-fns` for arithmetic**; display drift between the server (UTC) and the browser (local TZ), whether `suppressHydrationWarning` is acceptable, client rendering of times, and interval re-rendering of relative times are owned by the rules in `docs/rules.md#formatting` that dates and times state their display time zone and the server and client never render different values initially, and that relative times are displayed with `Intl.RelativeTimeFormat` (Rationale [0040](0040-routing-rendering-strategy.md)). The boundary: **"where and with what it is written" = this ADR / "rendering patterns for hydration, TZ and relative time" = `docs/rules.md#formatting`**
- **The complete line between the roles of `Intl` and `date-fns`**: "**shaping** a value (adding, subtracting, taking a difference, parsing, rounding to a boundary)" = `date-fns`; "**showing** a value (turning it into a locale-dependent string)" = `Intl`. No third display library is put between the two. Once [ECMAScript Temporal](https://tc39.es/proposal-temporal/) is built into runtimes as standard, there is room to reconsider moving `date-fns` (arithmetic) to Temporal (standards compliance [0010](0010-standards-and-non-lockin.md)). Thanks to the structure of §2/§3 (standard `Date` boundary, consolidation in `model`), that replacement stays within the module boundary
- **Where the default locale comes from**: it stays a `model` constant (a single seam). If it needs to become env-driven, it may be promoted to the `config` kernel of [0030](0030-environment-variable-management.md) (adding an env variable requires user confirmation. [0030](0030-environment-variable-management.md)). When i18n is adopted, the seam of [0121](0121-i18n-strategy.md) (`proxy.ts` / `[locale]`) supplies the active locale
