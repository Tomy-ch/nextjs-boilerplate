# Performance Budget

Defines performance's **metrics (Core Web Vitals) / budget mechanism (Lighthouse, bundle size) / where concrete thresholds live**. This repository holds **the mechanism and the thresholds that do not depend on the use case**, and leaves undefined here **only the thresholds that move with the use case**.

## Status

Accepted

## Context

**Among budget values, what depends on the use case (content volume, target devices, SLA) is bundle size; the Core Web Vitals thresholds do not.** The latter are the very boundaries the Web standard defines as "good", and point at the same values for any app. Making both use-case dependent wholesale as "budget values" produces a state where **everyone measures but nobody fails**, leaving only the mechanism.

## Decision

### 1. Metrics = Core Web Vitals

- The primary performance metric is **Core Web Vitals (LCP / INP / CLS)** (industry standard). **The collection path for field values (RUM)** against lab measurement (CI Lighthouse) **is defined by [0082](0082-client-observability.md)** (INP and others require real user interaction and are complemented on the field side)

### 2. Budget mechanism (measurement + hard gate)

- **Lighthouse / bundle size budgets are measured in CI and fail when exceeded**. Integration follows the frame of **[0153](0153-ci-configuration.md)** (job split / PR comment upsert foundation). There are two measurement jobs: `lighthouse` holds per-screen Core Web Vitals, and `bundle-budget` holds per-route client JavaScript
- **The two judge at different times.** `bundle-budget` is a required check per PR; `lighthouse` runs on pushes to protected branches and daily, opening an issue when it fails. **Whether to make `lighthouse` a required check is decided by the adopter** — which screens are bundled and which machines measure them changes whether the budget is met, so the default here is not required. The context for the judgment is already output per PR, so promotion takes only the required-check setting. **There are two cases where a PR measures without waiting, both decided by structure** — when the screen declaration (`e2e/lib/screens.ts`) moved (**a screen that has never been measured** may have appeared, and there is no number to compare against), and when a layout moved (every screen goes through it). Only cases whose reason can be stated without needing numbers are placed here. **The judgment that prompts for a label is not held here** — it is held by the side that reads the three deferred checks (`a11y` / `e2e` / `lighthouse`) at once, and that side does not recommend measurement on PRs already decided to be measured by the two cases above ([0153](0153-ci-configuration.md)). Holding a judgment with the same intent in two places leaves two comments with the same intent on the same PR. **Lighthouse measurement only works serially** — measuring concurrently mixes the degree of parallelism itself into the numbers, so the cost sticks at `screens × attempts` (measured at 23 screens × 3 attempts ≈ 16 minutes). Cutting attempts loses the median that absorbs runner jitter, and cutting screens loses the point of drawing the full set from the declaration, so **what is cut is frequency, not coverage**. The cost is that detecting a regression is delayed by one merge
- **The base branch is built with the same measurement too, and increments are judged by the difference from base.** With an upper limit alone, changes eat the headroom a few KB at a time, and whoever touches the last PR that crosses the line goes red — not whoever added the weight. Base comparison also covers routes with no declared upper limit (every route owned by the sample), so increments on routes without a declaration do not pass silently either
- **The increment limit is a ratchet for one change, and is not used for judgment on promotion PRs.** The upper limit holds the ceiling on the total, and the increment prevents "eating the headroom in small steps until only the last PR goes red". This role rests on base being **where that change lands**; on promotion (`release/*` → `production` / `staging`), base becomes the branch in production. The difference there is the sum of changes that each passed the increment individually, so applying the width for one change **always breaks on every release** — the only way to make it green becomes "widen the increment", which breaks the ratchet on the feature PR side along with it. On promotion the difference is only reported, and only the declared upper limits fail. **So what watches the total of a whole release on promotion is the routes declaration**, and a route without a declaration hits nothing on promotion
- **Thresholds are held not by this ADR but by [`performance-budget.yaml`](../../performance-budget.yaml)**. If the ADR were rewritten every time a value changed, the fact of moving a threshold would get lost in the history of decisions. **A basis is mandatory** in the declaration, and an empty one fails at load time
- Lighthouse judges **only the three metrics LCP / CLS / TBT, and does not look at the performance score**. The score is a weighted average of five metrics, and when it drops it cannot answer which one dropped. INP requires real user interaction and cannot be measured in the lab, so TBT is looked at as its substitute (the field-value collection path is [0082](0082-client-observability.md))
- **For an A/B of an effect, establish the noise floor first, then compare.** When saying which of two artifacts is faster, what decides whether the difference is real is **the difference from measuring the same artifact twice**. In measurement, a CPU-throttled, repeated-interaction measurement moved two runs of the same build by +12 to +63%, and the treatment's difference (−9 to −11%) was buried within it. Comparing one run each without establishing the floor measures the order of execution, not whether the treatment is present. **A difference that does not exceed the floor is not reported as an effect.**
- **CI runner numbers jitter, so each screen is measured several times and the median is taken**. The number of attempts is held by the same declaration. Continually loosening thresholds on the grounds of jitter stops them functioning as a gate. **Loosening is not forbidden, but it is not the first choice when something fails** (the procedure is §3)
- **A "floor screen" that reads the machine's speed is declared and measured on every split machine**. Runner speed acts directly as a multiplier on TBT, so whether a screen is slow or the machine is slow is told apart **by comparing against the floor in the same run** (TBT in §3). When split, the floor exists only on its assigned machine, and a failed screen and the floor measured on different machines cannot be compared. Measurements on machines that are not the assigned one are **not judged, only reported** — judging the same screen once per machine would fail whenever even one machine had a slow run
- **The list of screens to open is not held on the measurement side**. The declaration in [`e2e/lib/screens.ts`](../../e2e/lib/screens.ts) (matched against the build output) is used as is. Holding the list in two places lets a screen added to only one of them pass green without ever being measured
- **Client JavaScript is drawn from the build artifacts**. The `next build` output has no First Load JS column, so chunks are collected from each route's `__RSC_MANIFEST` and `build-manifest.json` and gzipped. What is counted is **the unit of public routes**, not the unit of artifact entries — a route with parallel routes (`@slot`) has several entries, and the HTML when opened loads all their scripts, so they are counted as a union. Counting per entry would split one route over several rows, and both the upper limit and the increment would look at only one of them
- **It is not only the initial JS that is counted.** Initial / deferred / total and CSS are lined up per route. A budget that looks only at the initial JS welcomes a change that moves something heavy behind `next/dynamic` as a "reduction" — even though the amount the person opening it ultimately pays has not changed. To make the `next/dynamic` rule of §4 checkable, the amount on the far side of the move must be visible. The deferred side is drawn by transitively following the chunks that initial chunks hand to the loader
- **CSS is also put on the budget.** It blocks rendering and so acts directly on LCP, and no other job looks at its amount. It is not mixed into the same number as JS because a regression in one would be cancelled by an improvement in the other
- **Polyfills are not counted**. Next.js emits them as `<script nomodule>`, so the browsers [0102](0102-browser-support.md) supports never fetch them. Counting them would add an amount nobody reads uniformly to every route, moving the budget away from "the amount the person opening it pays", which is what it is meant to watch

### 3. Where concrete thresholds live

**Where they live splits on whether they move with the use case.**

| Threshold | Where it lives | Reason |
| --- | --- | --- |
| Core Web Vitals CLS | **This document holds the value, inherited as is** | The "good" boundary is a fixed value defined by the Web standard and does not move with the app's use case |
| LCP | **This document holds the value, inherited as is. However, the value is derived from the lab** | **The "good" boundary (2.5 s) is a field definition and cannot be placed as is on a lab estimate.** The simulated network (150 ms RTT) and simulated CPU carry a fixed cost for the chain of requests, and a screen with almost no layout shell or client islands takes 2.16 s. 2.5 s sits 0.34 s above this floor, and measurement jitter is larger than the range the app side can move. So the lab upper limit is set as **floor + jitter across runs + the share allotted to the app**. Field LCP is held by RUM ([0082](0082-client-observability.md)) and is a separate thing from this upper limit |
| TBT | **This repository holds it. However, the value is derived from the lab** | **This is not a Core Web Vital but a metric Lighthouse places as the lab substitute for INP.** So its grounds also differ from the above: it is adopted as is not "because it is a value the standard defined" but "because there is no other way to measure INP in the lab". That the number matches INP's own "good" boundary (200 ms) is a matter of Lighthouse's scoring conventions, and by the no-lock-in test of [0010](0010-standards-and-non-lockin.md) this value loses its grounds the moment Lighthouse is removed. **When changing the measurement means, re-set only this row**. **As with LCP, 200 ms cannot be placed as is on a lab estimate** — TBT is the time the main thread was blocked, so runner speed acts directly as a multiplier. Across 10 runs of the sample, `not-found`, which holds only a layout shell, ranged 11–50 ms and the heavy screens 60–179 ms, and **every screen moved together by 3–4.5× within the same run**. The median of 3 removes a single slow attempt, but cannot remove a run that is itself slow. So the uniform upper limit is also set by the same derivation as LCP, **floor + jitter across runs + the share allotted to the app**, and only screens that have accepted heavier weight as a design declare it in `screens` with measurements as the basis. **Leaving the uniform upper limit at INP's boundary (200 ms) makes the screens that exceed it change from run to run** — over 4 releases of the sample, three screens took turns exceeding it, yet each was under half in other runs, and none had a reason to be heavier on the run where it exceeded. That is judging the machine's speed, not the screen's weight |
| Per-route upper limits for bundle size (initial JS) | **Re-measure and replace** | Values derived from measurement; they mean nothing in a different app |
| Increment limits for bundle size (initial JS / total JS / CSS) | This repository holds them | The range moved by dependency updates and re-chunking, independent of the use case. The three are set separately because their ranges of movement differ by orders of magnitude, and folding them into one number lets a regression in one be cancelled by an improvement in another |

Per-screen upper limits are declared with a basis in `lighthouse.screens` of `performance-budget.yaml`. **Tightening is written in the same place** — tightening light screens that hold only the layout shell and CSS below the default makes a layout-shell regression fire before it gets lost in the jitter of the heavy screens. Heavier screens jitter more across runs, so a uniform upper limit alone cannot catch a worsening of the floor. **However, only the LCP side is tightened** — TBT is dominated by the multiplier, and the more a screen holds only the layout shell the more faithfully it reflects the machine's speed, so drawing a thin line there would make the floor fire on every slow run and lose its role as the reference for telling things apart. **The reversal condition is when the floor measured per split machine (`floor`) comes to be used not only for reporting but to correct the judgment** — once correction is in, the tightened line is decoupled from machine speed. **"We want to catch regressions in light screens" is not a condition** — that purpose is already served by the rows that tighten LCP.

#### Procedure for loosening an upper limit

**Loosening itself is not forbidden. What is forbidden is making it the first choice when something fails.** A threshold is not moved to erase the fact that it was exceeded; it is re-set when the weight that screen needs has become clear. Moving it without following the order turns the gate into "a line that widens when it fails", and it protects nothing.

1. **First, make it lighter.** Apply the writing practices of §4 and cut everything that can be cut. Record the amount cut and the measurement after cutting
2. **State why it cannot be cut further, in the terms of the mechanism.** "Because it jitters" is not a reason — jitter is absorbed by the median and an upper limit that already factors in jitter across runs. What counts as a reason is something like "what this screen always shows the person opening it is heavy" or "moving the fetch outside the measurement window would break the experience instead" — when **you can say what would be given up instead**
3. **If there is an option that changes what is visible, line it up too.** Options such as making a component open on interaction or switching to another way of rendering are presented on the same footing as the loosening option. Which one to take is not decided by the implementer
4. **Get confirmation from the tech lead / architect.** Present 1–3 together, and write into `screens` only after approval. **This confirmation cannot be skipped** — the judgment to loosen is itself the judgment to accept that screen's weight as a design
5. **Write in the declaration the condition under which it can be lowered.** Unless what would need to change for it to be restored is written, it remains as a permanent loosening

**Tightening needs no such procedure.** Tightening a light screen below the default is a change in the direction of adding lines to protect.

### 4. Writing practices that do not bring in weight

**It is cheaper to avoid writing that exceeds the budget than to fix it after exceeding.** The shapes that recurred in measurements of the sample are placed as conventions.

- **Do not pull in a whole validation or schema set just to get one value.** Constants, field names and limit values are placed in a module without validation if the side using them does not need validation. JavaScript imports are per module, so an import that takes one `const` puts a whole zod schema set into the bundle. The default is to split out **modules that hold only spellings and numbers**, such as input `name`s in `form-names.ts` and item-count limits in `page-size.ts`
- **Heavy components not needed for the initial display are taken out of the first-loaded set with `next/dynamic`.** The deciding factor is "does the person opening that screen always see it", and what they might not see (a closed sidebar, an editing surface or drawing below the fold) is taken out. **The frame is placed at the same dimensions as the finished result** — otherwise the elements below all shift together the moment it arrives
- **`next/dynamic` is not "don't fetch until seen".** Fetching starts **when the element mounts**, and starts even if it is hidden with `hidden` or below the fold. So what it achieves goes only as far as **being excluded from the first-loaded set (the range `bundle-budget` counts)**, and the person opening the same page pays those bytes in the end. If you want to delay the fetch itself, the condition for not rendering it is held by the caller, not by `dynamic`
- **Do not place loading UI on data the outer frame already holds** ([0040](0040-routing-rendering-strategy.md)'s principle that boundaries are placed per unit of what is waited for). When the outer frame and the screen share the same fetch, the screen-side `<Suspense>` merely waits for a value already at hand, and **moves the position where reading began by piecing the screen together twice**
- **Japanese web fonts are not used for body text** ([0051](0051-styling-system.md)). The `@font-face` declaration lands as render-blocking CSS, so it takes effect before client JavaScript
- Minimizing the surface area of `NEXT_PUBLIC_` ([0030](0030-environment-variable-management.md)) and pushing the `"use client"` boundary down to the leaves ([0040](0040-routing-rendering-strategy.md)) are the foundation of these

## Prohibitions

- ❌ Not having the measurement mechanism itself (Enforcement: `bundle-budget` is a required check, and removing the job fails `make actions-required-check-lint`. `lighthouse` is not required, so removing it is Prose — **not mechanizable**, because whether to make it required is decided by the adopter)
- ❌ Placing a threshold without writing a basis (fails at load time)
- ❌ Making a failure the first reason to loosen a threshold (moving it without following the procedure in §3 turns the gate into "a line that widens when it fails", protecting nothing) (Enforcement: Prose — **not mechanizable**. Whether the §3 procedure was followed before loosening is the order of work and does not appear in the threshold diff)
- ❌ Loosening upper limits in `screens` without confirmation from the tech lead / architect (Enforcement: Prose — **partly mechanizable**. A diff that raises an upper limit in `screens` of `performance-budget.yaml` can be detected statically and an approver can be required via CODEOWNERS, but no rule exists. Who the tech lead / architect is is decided by the adopter)
- ❌ Holding the list of screens to measure outside `e2e/lib/screens.ts` (Enforcement: Prose — **not mechanizable**. Whether an array is "the list of screens to measure" is decided by meaning, not by the shape of the code)
- ❌ Importing from a module that holds validation and schemas just to get a constant (Enforcement: `scripts/client-schema-weight.gate.test.ts` rejects pulling `zod`'s default entry point or generated zod schemas from modules that reach the client. Imports that take only constants from other validation modules are Prose — **not mechanizable**. Whether that module holds validation and whether the importer needs validation are decided by meaning)
