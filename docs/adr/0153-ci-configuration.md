# CI Configuration

Defines the GitHub Actions **job split / trigger strategy / CI hardening (SHA pins, concurrency, minimal permissions) / hooks mirror / required checks / caching / matrix**.

## Status

Accepted

## Skeleton

Workflows are split as **"1 concern = 1 workflow"**, and **SHA pins** / concurrency / minimal permissions / **hooks mirror CI** / PR reports are the hardening common to every workflow. This skeleton is language-independent. The job contents are biome / tsc / next build / vitest / playwright; check logs are reported to the PR through upsert-pr-comment, and coverage through octocov.

"no-Docker" in this ADR refers to [0011](0011-no-docker.md). There are no jobs that presuppose container delivery (the image-scan / migration kind).

## Decision

### 1. Job split = 1 concern = 1 workflow

- Workflows are split per concern. Splitting is also for splitting runners — no job sits behind another job's runner. This repository's CI jobs:
  - **lint** (`pnpm lint:ci` = biome + ESLint + boundary reconciliation) / **md-lint** (`pnpm lint:md` = markdownlint + mermaid syntax + semantic checks on `.claude/**` (`skill-lint`); separate because biome does not look at Markdown) / **typecheck** (`pnpm typecheck` = tsc) / **build** (`next build`; includes the full build-time env validation of [0030](0030-environment-variable-management.md) and **reconciliations that only the build output can answer** — currently, checking against the rendering-mode declarations ([0040](0040-routing-rendering-strategy.md)). Adding another build just for reconciliation would add 10 minutes to a question one manifest can answer. Riding along is allowed because this job is not narrowed by `paths` and **always runs**; putting it on a job that stops on the diff (`bundle-budget`) would create days when the check goes silent) / **test** (vitest) / **e2e** (playwright)
  - **Lockfile drift**: besides `pnpm install --frozen-lockfile` passing (agreement with `package.json`), `git diff` checks that install does not rewrite tracked files (pnpm appends build-approval keys to `pnpm-workspace.yaml` on its own)
  - **Boundary checks**: ESLint boundaries ride in series in `lint:ci` ([0002](0002-formatter-linter.md) / [0021](0021-frontend-responsibility.md))
  - **Linting workflow definitions**: `.github/workflows/**` itself is checked with **actionlint** (`make actionlint`). actionlint checks the shell of `run:` steps by calling **shellcheck**, so both binaries are version-pinned in `mise.toml`, keeping the result independent of the execution environment ([0003](0003-version-manager.md)). Both land on PATH from the same `[tools]` through the same activate, so the guard of `make actionlint` only checks that actionlint exists, with no separate guard for shellcheck (**reversal condition**: when their supply paths diverge — one leaves `mise.toml` management, or installation through a path other than mise is allowed. "The check's coverage shrank in an environment without shellcheck" is not the condition — that is a PATH problem, fixed by PATH, not by a guard). No actionlint configuration file (`.github/actionlint.yaml`) is placed — a configuration changes two things, allowing self-hosted runner labels and declaring `vars.*`; while neither is used the result is the same as the default, and an all-commented template checks nothing while merely asserting where the extension point is (**reversal condition**: when a workflow references `vars.*`, or writes a self-hosted runner label in `runs-on`. For the former, an undeclared `vars.X` reference is detected only once `config-variables` is declared; for the latter, an undeclared label fails as unknown). Following hooks mirror CI in 4 below, it runs both locally and in CI. It is split off as a concern separate from the SHA-pin check (3 below)
  - **Linting the run shells of composite actions**: composite actions (`.github/actions/**`) cannot be scanned by actionlint directly (they would be interpreted as workflows), so there is a dedicated check (`make actions-shellcheck`) that parses `action.yaml`, extracts `runs.steps[].run`, adds a shebang decided from `shell:` and feeds it to shellcheck. Findings are mapped back to the line and column of `action.yaml`. A YAML parser is used for extraction because the body of `run:` can contain heredocs or `#`, so a line-based regular expression would get the end wrong, and could not pick up `run:` reached through an alias (`run: *anchor`) or a merge key (`<<: *base`). A `shell:` other than `bash` / `sh` is not checked, and is reported with its location and dialect rather than a count (no invisible skips). **A state where extraction breaks and it is "green without checking" is failed per file by reconciling against the count taken from the parser's own conversion** (looked at in total, one file's extraction failure hides behind other files' success. The path is separate from the hand-written node walk, so damage to one shows up as a difference in counts). The body of `run:` must be a literal (`|`), and block folding (`>`) is an error (it folds adjacent lines into spaces, so findings cannot be mapped back, and folded lines create syntax not in the source, producing false positives). It asks the same question as actionlint, "is the shell CI will run correct", so its workflow, PR comment and required check live together in `actions-lint` (the unit of splitting is the concern, not the number of commands). What actionlint's indirect check (resolving `uses: ./.github/actions/...` on the workflow side) covers is the consistency of the inputs (`with:` and `inputs`) of already-referenced actions, and that does not change (**reversal condition**: when actionlint can check `action.yaml` as distinct from a workflow. "The contents of composite actions are not checked" is not the condition — the check can live outside actionlint. [0151](0151-git-hooks.md))
  - **Linting for secrets leaking into PR-comment posting jobs**: "do not pass secrets to check steps" in 5 below cannot be expressed in actionlint, so a dedicated check (`make actions-comment-secret-lint`) guards it mechanically. The unit of scanning is **the job** — whichever step passes the secret, if it is in the same job as the step that creates the body file, it reaches it. Posting jobs are identified by reachability traced from `uses:`, including jobs that go through a local action that calls `upsert-pr-comment` internally (so that wrapping it in one layer does not make it vanish from the check). A YAML parser is used to cut out jobs because with a line-based regular expression, differences in indentation width or flow style would make no job header match at all, and **it would be green with nothing to check**. **What is searched for references is the parsed scalar values, not ranges of source** — cutting by range would pick up examples written in YAML comments as real references; an unclosed `${{` would be taken as one expression up to the next `}}`, swallowing real references in between; and values moved to another job through an alias would conversely fall out of scope. Looking per value and following aliases makes all of these disappear structurally. What can be detected is only direct references to the secrets context appearing in `${{ }}` expressions; indirect passing through `needs.<job>.outputs` cannot be traced statically — the positioning that **the convention is the source of truth, and this check is a regression guard against the convention being broken in the future by one `env:` line** is kept. **For a local reusable workflow (`uses: ./.github/workflows/*.yaml`), the callee is resolved, and the caller is treated as a posting job only when the callee posts** — the callee runs on its own runner, so a secret passed to it never lands on the caller's runner, and only the case where its destination posts needs checking (nesting is resolved by iterating until the set stops growing). **A remote reusable workflow cannot be resolved**, so it fails as before. Abnormal exits are split two ways: a convention violation is exit 1, and a state where the check itself does not hold (0 workflows / `jobs:` unreadable / **action definitions exist but not a single posting job is found** / **a job calls a remote reusable workflow**) is exit 2. The former closes the case where reference identification breaks and it stays green with the targets gone; the latter is because, since the secrets passed to the callee cannot be traced, leaning toward "not a posting job" would let paths the check cannot reach grow while staying green. It lives in `actions-lint` because what this check asks is, like the two above, **"are the Actions definitions CI is about to run correct"**; this grouping, one step wider than shell correctness, is the concern the three share (the unit of splitting is the concern, not the number of commands)
  - **Linting that required-check declarations match reality**: "only jobs that keep reporting on every PR may be registered as required" in 5 below **cannot be judged without reconciling two files**, the ruleset declaration (`.github/settings/branch-protection.json`) and the workflow definitions, so actionlint, which reads only one workflow at a time, cannot express it. There is a dedicated check (`make actions-required-check-lint`). For each required context it checks that exactly one job in the whole repository declares that name; that the workflow's `pull_request` is not narrowed by a filter (`paths` / `paths-ignore` / `branches` / `branches-ignore`); that if `types:` is narrowed it includes `opened` / `synchronize`; and that the context name does not branch at run time (`strategy.matrix` / a reusable workflow call). Jobs that step down with `if:` are not failed — a job that stepped down reports `skipped`, and required checks count that as success, so reporting is not interrupted. Abnormal exits are split two ways like the other lints: a declaration violation is exit 1, and a state where the check itself does not hold (declaration unreadable / no required-check rule / 0 workflows) is exit 2. **0 is not leaned toward "no violations"** because if a misread declaration passed as acceptable, the invariant this check protects would silently disappear. It lives in `actions-lint` for the same reason as the three above
  - **Static analysis of Actions definitions**: aspects the two above cannot see in principle are checked with **zizmor** (`make actions-zizmor`). Both actionlint and `actions-shellcheck` flatten `${{ … }}` into a placeholder preserving only the line count before passing to shellcheck. Once flattened, the expression becomes "just a word", and **whether it is quoted — the essence of script injection — disappears from what is analyzed** — `run: echo ${{ github.event.issue.title }}` expands an attacker-controllable value before the shell interprets it, but a design that goes through shellcheck cannot catch it. The correct shape is to pass it to an environment variable through `env:` and reference it as `"$VAR"`, and the check steers toward that shape. Both workflows and composite actions are scanned. **Only high findings fail** (it stops only what should be stopped before running, not by the total amount of findings). However, `--min-severity` also narrows the display, so **the run that prints all findings and the gate run are separate** — since suppression is done by lowering severity (4 below), if lowered findings also vanished from the output, that would be exactly the "silently passing through" that [0110](0110-security-operations.md) forbids. **Both hooks and CI run it with `--offline`** — adding audits that only work online (impostor-commit, etc.) on the CI side alone would break hooks mirror CI in 4 below, making failures appear only on PRs that cannot be reproduced locally. Detecting re-pointed tags is handled fail-closed by `resolve` in 3 below. Suppressions are declared with reasons in `.github/zizmor.yml`, and **the configuration is passed explicitly with `--config`** (if auto-discovery missed it, it would show up as "suppressions not taking effect" rather than "zero findings", so you would not notice it missed). Like the three above, the workflow, PR comment and required check live together in `actions-lint` (what is asked is likewise "are the Actions definitions CI is about to run correct")
  - **Startup smoke**: there is a startup check of `pnpm build` → `next start` → polling `curl /`. That the build passes and that its output starts and responds are different questions, and the latter cannot be known from the build job's green. It builds on its own rather than receiving the build job's output because of the splitting principle above (no job sits behind another job's runner) — it reads the same `actions/cache` generation, so it starts from the previous run's cache rather than cold
  - Verification of stripping (`strip-verify`) is held in the same shape. Stripping is mandatory, so this guard step is not placed — placing it would make every PR fail forever, everywhere <!-- boilerplate-only:line -->
  - **Generated-artifact drift gate** (type generation; [0072](0072-api-type-generation.md)) / **coverage gate** (100%; [0090](0090-testing-strategy.md)). The coverage **PR report** is output with **octocov**. Other check logs are output through the PR-comment upsert foundation in 5 below
- There are no jobs for concerns the backend owns, such as DB migrations / SQL lint ([0011](0011-no-docker.md) / [0070](0070-backend-role-separation.md); generated-artifact drift is handled by the type-generation drift gate above)
- **What is shared between workflows goes in composite actions (`.github/actions/**`). Reusable workflows (`workflow_call`) are for notification only**. A composite action runs as steps inside the caller's job, which would put a webhook on the same runner as the dependency tree just scanned. A `workflow_call` always gets its own runner, so notification lives there and does no checkout

### 2. Trigger strategy

- Groups: **CI Checks** (every PR / merge-blocking) / **Security** (weekly schedule + PRs whose diff reaches it; [0110](0110-security-operations.md)) / **Deployment** (pushes to protected branches) / **Documentation** (portal delivery; [0141](0141-portal-operations.md))
- **Only checks whose cause lies in the change under review may fail a PR**. Turning a PR red with checks whose cause lies outside the change — upstream drift, dependency vulnerabilities, the state of third-party services — stops work for reasons the author cannot fix. Such checks run on a schedule and either do not run on PRs or only report there. If the same tool asks both questions, split the job (e.g. ledger consistency fails on PRs, while confirming upstream tracking is weekly only)
- **Only Security may be narrowed**, and the basis is that a separate weekly schedule exists — narrowing means "moved to the weekly run", not "the scan disappears", so forgetting to write a verdict loses at most one week ([0110](0110-security-operations.md)). CI Checks are required checks, and there is no run that would cover for them, so they are not narrowed
- **Only scheduled runs notify**. On a PR, the author has already been reached by a red check or a PR comment, and adding a notification would only duplicate what the author is looking at. A weekly run has no author. The destination is held by a reusable workflow (`notify.yaml`), which has two modes: **a job failed**, and **a layer designed not to fail found something**. The former carries only the run URL, not the scan output, and the latter carries only identifiers — so as not to create a path by which details of secrets or vulnerabilities reach the destination. If no delivery destination is configured, it is skipped and stays green (a missing setting does not hide the event that was to be reported)
- Branch operations follow [0150](0150-git-workflow.md) (`production` / `staging` / `develop` / `release/**`)
- **Checks whose cost does not fit a single PR are trimmed by frequency of running** (not by coverage). The targets are the three, `a11y` / `e2e` / `lighthouse`, and they run through five paths — promotion PRs (base is `develop` / `staging` / `production`) / pushes to protected branches / daily / label / `workflow_dispatch`. **The judgment is held in one place, `.github/actions/check-trigger`**. Promotion PRs are included because that is where a person takes on the risk of "what to ship", which requires the answer to be **consistent** rather than **new** ([0110](0110-security-operations.md) draws the same line for vulnerabilities)
- **They step down via `if:`, not `on:`**. A job always starts and reports its context, and only the heavy steps step down. A PR whose registered required context is not reported is blocked forever (5 below), so removing it from `on:` is not an option. Each job answers why it stepped down in its own PR comment
- **"Should it have run" is answered once, in one place, and the answer names the label**. Each of the three can only answer "did it run" and does not even look at the other two. `deferred-checks.yaml` reads the diff once and leaves exactly one comment. **The judgment is structure first, with volume as a fallback** (`scripts/deferred-checks/recommend.ts` / `volume.ts`) — only what can be said in one sentence about which path calls which label is declared, and a line-count threshold (`ALERT_AT`) is applied only to diffs that cannot be. If volume were primary, a diff fixing one line of a layout shell would stay silent, and a large diff affecting only one check would get a table for all three. **This is not a gate and is not registered as required either** — the line-count threshold has no theoretical basis, and a number without basis is not put where it can stop a merge. **A label already attached drops only that check** (if all three went silent because of one label, the checks the person who attached it did not look at would vanish without being named). **Reasons for which a job can decide to run on its own are held by each job itself, and are not recommended here** (`lighthouse`'s "a screen's declaration moved / a layout shell moved" and `e2e`'s "layout shell / base CSS / a screen's declaration moved" are these; prompting for a label on a PR where they already run is wrong). **`e2e` holds this not because detection would be late, but because the path to fixing it exists only on a PR** — retaking baseline images is limited to the set the comparison reported, and that report appears only in PR runs. If a screen not compared on the PR diverges after merge, there is no longer a PR that can name what to retake, and another PR has to be raised while the release branch stays red. **The line is drawn not by "does it move a screen" but by "can one tell from the look of the diff that it moves one"** — mock responses and journey declarations also move screens, but that they do is visible to whoever wrote them, so they stay on the label side. Widening it would make it run on almost every PR. **No gate is placed to detect this declaration drifting from reality. The reversal condition is when a declaration comes to hold a path whose location is not fixed by an ADR or a framework convention** — all 10 current rules point at locations fixed elsewhere (stories and `mocks/` by [0027](0027-directory-structure.md), the token SSOT by [0051](0051-styling-system.md), the replacement declarations in `.storybook/` by [0054](0054-ui-catalog-storybook.md), `proxy.ts` by [0043](0043-middleware-policy.md), `fonts.ts` by [0045](0045-fonts-and-images.md), `e2e/` by Playwright's `testDir`, `layout.tsx` and `next.config.ts` by Next.js itself). Moving those means abandoning the convention, so it cannot turn into a form where only the declaration silently goes stale. The other condition is **when `deferred-checks` becomes a required check or a gate** — today, the cost of a dead rule is one missing comment, but as a gate it would turn into "green without checking". **"A case of a dead rule appeared" or "the targets decreased" is not the condition** — both are states. **The side that runs without waiting (`scripts/e2e/trigger.ts` / `scripts/lighthouse/trigger.ts`) pays one step more** — the cost of a dead rule there is merging without the check running — but the locations of the paths it lists are fixed by Next.js and Playwright, so it becomes a check for which the same condition suffices, and the point of trimming by frequency disappears

### 3. CI hardening (language-independent)

- **SHA pins**: actions are SHA-pinned in the form `uses: owner/repo@<40hex> # <tag>`. **The version SSOT is the tag in the trailing comment**, and the tag→SHA mapping is held by `.github/actions-pin.toml`. A tag is a name, not an identity — it can be re-pointed, which is why a lockfile is needed. Resolution / application / checking are `make actions-pin-{resolve,apply,check}` (the implementation is `scripts/actions-pin/`). `resolve` applies a quarantine of `ACTIONS_PIN_MIN_AGE_DAYS` (default 14) and does not adopt freshly published releases (it keeps an existing pin if there is one, and skips if not). `check` does not go to the network and fails closed on unregistered / unpinned / lockfile mismatch / unreferenced entries / uninterpretable `uses:` notation / tags containing characters unusable in a version. **Tags are limited to alphanumerics and `.` `_` `-` `+` `/`** (`resolve` applies the same check before going to the network) — while being the version SSOT, it comes in as an unvalidated string and flows to several output surfaces — lockfile keys, API URLs and the strings written back into `uses:` — so it is narrowed once at the entrance. `uses:` is therefore written in block notation, one step per line (flow mappings are an error because they escape the check's net). It runs in both the pre-commit hook and CI. **The quarantine buys time against automated takeovers; it is not a guarantee that withstands forged dates** — detection of re-pointed tags themselves is handled by `resolve` failing closed. **If a tag declared immutable resolves to something different, `resolve` fails with exit 1 and writes nothing to the lockfile** (neither approved moves nor other entries. Once a re-pointed SHA gets in, `check` keeps answering "consistent" from then on). Whether a tag is moving is **read from the shape of the comment tag as a declaration** — only a bare major number (`# v6`) is moving; `# v6.1.0` / `# v6.1` / `# main` are immutable. It is not a guess about upstream tag practice but a statement of intent by whoever wrote the tag, and when the declaration and upstream disagree it errs on the side of stopping — for upstreams that operate moving minor tags it is a false positive, but an error in the stopping direction (**reversal condition**: when an upstream that operates bare major numbers as immutable versions is adopted, or when moving tags other than bare numbers are adopted and habitual use of `ACTIONS_PIN_ALLOW_MOVED` takes root — if the declaration-from-shape constantly disagrees with upstream, move the kind from derivation by key to explicit storage. "The judgment is naive" or "a false positive kept the lockfile from updating" is not the condition). The judgment is made on the candidate SHA **before** the quarantine is applied (comparing on the post-quarantine adopted value, a SHA right after re-pointing would be the newest and so be quarantined, turning into "keep the existing pin" and delaying detection until the window opens). Intended updates are approved by listing the target keys in `ACTIONS_PIN_ALLOW_MOVED`. This value is not expanded into the make recipe but **passed to the script as an environment variable** — keys come from comment tags, and embedding them in a recipe line would make the repository's content subject to shell interpretation. For the same reason, the detection failure output does not assemble an approval command with the keys embedded. The reason no approval is required for a moving tag advancing is that an operation of approving on every routine update would make "add the flag and rerun when it fails" a reflex, and a re-pointing would slip into that bulk approval. **`uses:` starting with `docker://` is outside this mechanism**; digest pinning is handled by images-pin ([0011](0011-no-docker.md)). It is a registry reference that cannot be resolved with `git ls-remote`, so handling it here would duplicate digest resolution. Merely excluding it from pinning would make it silently drop out of the net, so the scan targets are aligned on the other side — images-pin scans down to workflow / composite action definitions and picks up `uses: docker://` lines. **Docker actions whose Dockerfile builds from a floating tag and runs tool installation without specifying versions are not adopted** — SHA-pinning such an action only pins the recipe, not the code that runs. Tools are installed directly in the workflow, as literals whose versions can be read. The operational skill is `actions-pin` (placed in the [0154](0154-claude-skills-operations.md) operations family as a dependency-audit skill — the same family as `tools-upgrade`). **When a tag declared immutable resolves to a different SHA, `resolve` exits with code 1 and writes not a single byte of the lockfile** — neither acceptable moves nor unrelated other entries. **Reporting them side by side is not adopted** — once a re-pointed SHA enters the lockfile, later `check` runs pass it as correct. Partially accepting and recording a detected anomaly makes the detection itself meaningless ([0157](0157-inspection-declaration-discipline.md))
- **concurrency**: the default is `group: ${{ github.workflow }}-${{ github.ref }}` / `cancel-in-progress: true` (cancel old runs). **Only the delivery workflows (Deployment / Documentation) put a shared resource name in the group and use `cancel-in-progress: false`** — there is only one delivery destination, not one per ref, so splitting the group by ref would make concurrent runs conflict, and cancelling a deploy in flight would leave the live site serving a partially transferred build. What the default protects is "not stacking old runs per PR", and these two points do not conflict with it
- **Minimal permissions**: two tiers — the top level is narrowed to `contents: read`, and jobs add only what they need (`pull-requests: write`, etc.)
- **Where tokens come from**: the default is the short-lived `GITHUB_TOKEN` issued per job. However, its rate limit is per repository and is not enough for jobs with REST calls proportional to item count, such as retaking baseline images. Calls beyond the limit are made with short-lived tokens issued from the GitHub App for the baseline-image store. Splitting Apps per use is not adopted — this key already holds `contents: write` on both repositories, and an attacker holding it can push arbitrary code, so the `pull-requests` / `issues` write that callers add is close to a subset of that; splitting would not shrink the attack surface. Splitting would leave the limit unfixed until a person registers the second one. At issuance, permissions are named, and only what the caller needs is put on the token (a caller that only reads baseline images is not given `pull-requests`). **Token sources are limited to these two, and no standing credentials are placed in CI** — a long-lived credential differs in kind from a short-lived one in that, if leaked, it stays valid until revoked. Adding one standing key to raise the score of a check that measures supply-chain posture would damage the very thing that check tries to measure. **A low measured score is not the same as having no protection** — the substance of the protection is declared by [`.github/settings/branch-protection.json`](../../.github/settings/branch-protection.json), and the score also depends on whether credentials able to read it fully were provided
- **Runner hardening**: `step-security/harden-runner` runs at the start of every job and **blocks outbound traffic to anything but allowed destinations** (`egress-policy: block`). The SSOT of the allowlist is the single `.github/egress.yaml`; `make egress-apply` reflects it into workflows and `make egress-check` fails on differences (the implementation is `scripts/egress/`). **It cannot be moved into a composite action** — `uses: ./...` resolves from the workspace and so needs a checkout, but harden-runner is meaningful only as the first step, before checkout. So the values are written back into each workflow, and a machine holds the reconciliation (the same shape as actions-pin). **Additions are based on measurement** — the `domain resolved:` lines recorded by `audit` remain in the job logs and are taken from there. **Do not look only at runs where the cache hit** (a run that does not fetch dependencies shows no `registry.npmjs.org`). **A workflow whose records are not complete stays at `audit` by declaration, with the reason and the condition for removing it written down** — an allowlist made by guessing stops runs that must not be stopped. This blocking also stops the tools' own telemetry. **What can be cut at the source is cut first** (the catalog build stopped it with `core.disableTelemetry`) — added to the allowlist, it becomes a passage no one questions from then on

### 4. hooks mirror CI

- lefthook ([0151](0151-git-hooks.md)) duplicates "local == CI". **pre-commit = fast feedback** (glob-narrowed, cache enabled), **pre-push / CI = authority** (full, cache disabled, coverage gate) (consistent with the two-tier execution of [0090](0090-testing-strategy.md)). However, **while the host is saturated, the pre-push side steps out of the duplication** — gate failures on a saturated host are untrustworthy, and delegating to CI, the authority, is faster and correct. The judgment uses measured utilization, and the configuration stays identical in every environment ([0151](0151-git-hooks.md))
- Design principles: glob-scoped (hooks narrowed by changed file type) + bypass-then-verify-once (`--no-verify` while splitting commits, then verify once at the end). pre-push runs `make test-full` and typecheck to fail before reaching CI. Only pre-commit uses the cache, which balances iteration speed while editing with complete verification before push

### 5. Required checks / PR gate

- **Failures that happen outside a PR become issues**. There is no place to read a red check, so it is turned into a form with an owner. **One per title**; a second failure comments on the same issue (failing again on a condition already flagged is the same single unresolved fact). Finding and opening is held in one place, `.github/actions/upsert-issue`, and callers pass only the body and title — the same division of labor as `upsert-pr-comment` on the PR-comment side, with **the responsibility for sanitizing the body** left with the caller (below)
- **Check logs** do not fail immediately; the result is captured → **the PR comment is upserted** (existing comment detected by an HTML marker → update / create) → and finally it fails closed (`exit 1`). For **coverage**, octocov structures the LCOV after the Vitest run and reports to the PR, and then the gate's failure is returned. Test failure details are also treated as check logs and posted through the same mechanism — octocov reports only coverage and does not say which tests failed
- **Log volume is designed on the assumption that the reader is an agent**: logs of failed runs are read not only by people but by agents. Agents load the full text into context, so **the volume of lines that only say "passed" is directly the cost of diagnosis**. Measured, of the 1.6 MB full log of the Test workflow, 46% is line prefixes added by `gh` and 27% is the coverage table, and the clues to the failure lie outside them. So **reporters that output a full one-line-per-file table are not used in CI** — coverage outputs only files below the threshold (`skipFull`), and shards that hold no verdict output no table at all. For the same reason, **before truncating a comment body by line count, confirm that no verdict remains on the side that is cut** — with a full table thousands of lines long, a body cut from the end would be only the tail of the table and contain not one line of the failure diff
- **No comment is created when green, but an existing comment is updated even when green**: the caller passes the verdict as `status`, and only on `success` is **creation of a new one** suppressed. If every job posted every time, the PR conversation would fill with "PASS" and the one FAIL among them would not reach the reader — the value of notification is decided by signal-to-noise ratio, not count. Updates are not stopped because otherwise an old red would remain when fixed from FAIL → PASS, which "do nothing when green" cannot achieve. **Only report-only scanners differ in what the verdict means** — they are designed not to fail on detection, so passing the job's outcome as is would let a run that found a vulnerability suppress the comment as `success`. Pass "did it find something", not "did it run". **Reversal condition**: when a green run comes to carry **information that exists only in that run** in its body — today a PASS comment carries only the verdict, which the check's color already states. Those carrying measurements (`bundle-budget`'s client JS per route, `lighthouse`'s Core Web Vitals) are closest to this condition, and **if reverted, revert per job** (`status` is passed by the caller, so the mechanism is already split per job). **"It is lonely that a green PR gets no comments" is not the condition**
- **A missing body file is treated as the job having been cut off, not as a failure of the posting step**: a job that was cut off never reaches the step that writes the body. If the posting step failed here, nothing would remain on the PR, and **the absence of a comment cannot be told apart from "the check was green"**. It posts with a dedicated heading and does not name the cause (only the run log can distinguish a timeout from an earlier failure). Only this cut-off comment is **deleted**, rather than overwritten, by a later success — the cut-off recorded no verdict, so the later success answers it rather than overwriting it
- **Building the body is treated as input from the PR submitter**: linters and compilers output source lines verbatim in check logs, and since this repository is public, their content is controllable by the PR submitter. On that premise the following are fixed
  - **The fence for folding is decided from the body**: enclosing it in a fixed triple backtick lets the body itself close the fence, and what follows is rendered as raw Markdown (mentions that send notifications to third parties, and fake headings or links, appear under the CI bot's name). It is enclosed in a fence one backtick longer than the longest backtick run in the body. Fence assembly is confined to one place, `details-summary`, and fences callers assemble themselves are not checked. **Reversal condition**: when a workflow is placed that assembles its own fence into the body without going through `details-summary` — the condition is that the change bringing in that notation also brings in the check, and the check is not built ahead until then (a check with 0 targets keeps returning green with nothing to protect)
  - **What decides whether to enclose is whether it is raw, not whether it is folded**: the fence above is needed for bodies that pass tool output through as is. **A body the caller assembled after filtering its values is rendered without enclosing** — enclosing a table makes it unreadable as a table, leaving only a row of characters inside the fold. The filter target is the same set as "values readers paste into a shell" below, on the same basis (the allowed set can produce neither markup nor mentions). **Filtering is placed at the entrance, not the exit** — narrowing values at the point they are declared means they need no re-filtering no matter how many paths that use them are added (this is `e2e/lib/screens.ts` limiting screen names to kebab-case, and both the baseline-image file names and the PR tables inherit that guarantee). The declaration is made with `body-sanitized` of `upsert-pr-comment`, and the default leans to "not filtered"
  - **Values placed outside the fence are limited to static literals**: sanitization applies only to the body; `title` is placed outside the fence as raw Markdown and `details-summary` as raw HTML. Routing log-derived strings (such as a check result's summary line) there would revive, from outside the fence, the injection that was supposed to be closed. Callers pass only fixed strings written in the workflow definition to either
  - **Existing comments are identified by both "bot author" and "prefix match"**: a partial match on the marker alone would let a comment a third party posted first become the update target. But the author condition alone is not enough either — every workflow posts as the same bot, so the author does not distinguish sibling workflows. Making another workflow's marker appear in a log could steer that workflow to the wrong comment. A body the action wrote always starts with the marker, so a prefix match is also required. As a premise for this identification, `github-token` is given **a token that posts as a bot** (`GITHUB_TOKEN` or a GitHub App token) — posting with a personal PAT would make it never find the comments it wrote again
- **Values readers paste into a shell are dropped line by line if outside the allowed character set**: when a comment shows a command for copying (such as one line to open a failed target locally), values containing `$(...)` or backticks are **evaluated by the reader's shell** before reaching `make`. Branch names can legally contain both, and story ids and screen names also come from declarations on the repository side. **Wrapping in quotes is not enough** — a value containing a single quote closes the quote on the spot. So a value with characters outside `[A-Za-z0-9/._,-]` is not sanitized but **its line is dropped entirely**. The same check is also the basis for allowing these values in plain Markdown — the allowed set can produce neither markup nor mentions. It applies to comparison (VRT / E2E) failure comments and retake completion comments ([0091](0091-test-verification-methods.md)), and **the judgment is held in one place (`scripts/lib/accepted-chars.ts`), which each workflow calls** — "the same set" is an invariant, not a matter of handing transcriptions out to each place. Scattered, no one would notice when only one of them widened
- Protected branches block merges on required checks + high-severity detections ([0150](0150-git-workflow.md) / [0110](0110-security-operations.md))
- **Required-check granularity**: every job in the CI Checks group is required. Since `paths:` filters are not used (below), every job always reports on every PR, so there is no reason to exclude any from required
- **Only jobs that keep reporting their name on every PR may be registered as required**: GitHub does not read "the context is not reported" as "not applicable"; it blocks the PR forever, waiting on the required check. So jobs whose reporting can be interrupted are not registered — **jobs that do not run on PRs** (those producing network-caused failures the author cannot fix step down with `if:` and are not registered), **jobs narrowed by `paths:` to changes to themselves**, and **checks whose verdict depends on a third-party account** (in configurations without that account, it would become a merge condition). **The context name is decided by the job name**, so placing the same job name in different workflows is also forbidden (two check runs would be reported under one name, and which one the requirement points at would be undecided). These are checked mechanically by `make actions-required-check-lint` in 1 above
- **`paths:` filters = not adopted**: CI Checks workflows do not narrow their triggers and run on every PR. Narrowing would create PRs on which required checks are not reported, and the maintenance cost of keeping a pair with guard workflows that fill them in, always as exact inverses, is higher than a few minutes of run cost (the procedure for adding a job you want to narrow is in `.github/workflows/README.md`). The judgment of when heavy jobs step down is held in one place, `.github/actions/diff-scope`, and callers pass a list of **things that cannot affect them** — an omission costs one wasted run, but a mistake in the opposite direction errs toward the job silently checking nothing, and **a gate that checks nothing cannot be told apart from no violations**. The list is each job's own claim, and the action has no default. Writing the side of what can affect it (`only`) is possible only when the job's target is not the tree itself (a dependency scanner reads the lockfile) and a weekly schedule scans the whole tree — without the latter, an omission becomes a permanent blind spot rather than a one-week delay
- **Do not pass secrets to check steps**: the upsert above copies analysis logs verbatim into public PR comments. Actions secret masking applies only to the path the runner captures for log display, and content written to a file with `tee` passes through unmasked. So `secrets.*` are not passed to check commands themselves through `env:` (if needed to fetch a tool, limit them to the fetch step). `GITHUB_TOKEN` is an exception because it is needed for posting the comment itself and is a short-lived token Actions issues per job. This convention is checked mechanically by `make actions-comment-secret-lint` in 1 above — **no mechanism is built that receives values to mask through an input and replaces them**. That would be needed only when a job appears whose very generation of check logs needs a secret, and that job cannot be separated from the posting job. If Actions masking came to cover the bytes of a `tee`d file too, the check itself, not an input, would become unnecessary. The lint staying green is neither a reason to add the mechanism nor a reason to remove the check — green is evidence that the convention is kept, not a reason the mechanism is unnecessary

### 6. Runtime supply / cache / matrix

- **Runtime supply**: Node / pnpm are supplied from `mise.toml` by **an in-house composite action (`setup-mise`)**. The mise binary itself is pinned by version and SHA256 and **verified before running** — the Actions cache is not a trust boundary (it is shared across branches and can be replaced by anyone with push rights), and since an executable is placed there, without verification cache poisoning would become arbitrary code execution inside CI. In the same shape as the SHA pins of `uses:` and the digest pins of images, the version declaration is kept in one place. `actions/setup-node` is not adopted — `node-version-file` accepts only `.nvmrc` / `.node-version` / `.tool-versions` / `package.json` and cannot read `mise.toml`, so adopting it would mean a second version declaration ([0003](0003-version-manager.md))
- **There are only two kinds of exceptions where a version is written in a workflow**. One is the mise CLI itself — `mise.toml` declares what mise resolves and cannot declare mise's own version. It is written in each workflow as a version and SHA256 pair, and a bump touches every workflow. The other is a scanner that, if taken through a `mise` backend, would bring a whole language runtime into the version SSOT (a CLI on .NET installed directly from NuGet) — the whole runtime is not put under mise management for one scanner that runs only in CI
- **Cache**: the pnpm store (the resolved `pnpm store path`) and the `next build` cache (`.next/cache`) are kept with `actions/cache`. The key starts with the hash of `pnpm-lock.yaml`; `.next/cache` adds the source hash and falls back to the previous generation through restore-keys
- **The matrix is not used to expand runtimes**: a single `runs-on: ubuntu-latest`, with the Node version taking `mise.toml` as the SSOT and not expanded by matrix ([0003](0003-version-manager.md)). What is forbidden is **crossing versions with OSes**, not the mechanism itself
- **A matrix to split work is used**: for checks whose cost is proportional to the number of targets and which already use up one machine's parallelism, the only remaining way to cut wall time is more machines. This applies to per-story VRT and per-test-file Vitest, split by `playwright --shard=i/N` / Vitest shards, with an aggregating job merging back into one report. **The number of machines affects billing linearly**, so it stops where the reduction is worth the fixed cost. **What is made a required check is the single aggregating job, not the matrix side** — a matrix's context names branch at run time, and a required check cannot name them (`required-check-lint` in 5 above checks the same condition)

## Prohibitions

- ❌ Using actions with moving tags without SHA-pinning them (quarantined SHA pins are mandatory)
- ❌ Giving workflows broad permissions (read-only default + local additions) (Enforcement: Prose — **mechanizable** (check in YAML that each workflow has a top-level `permissions` that does not exceed `contents: read`. No rule exists))
- ❌ Stacking old runs per PR without concurrency control (Enforcement: Prose — **mechanizable** (check in YAML whether workflows started by `pull_request` have a top-level `concurrency` with `cancel-in-progress: true`. No rule exists))
- ❌ Permanently bypassing hooks to get through CI (local == CI duplication) (Enforcement: Prose — **not mechanizable**. A bypass is how something is launched locally and does not appear in the repository's diff)
- ❌ Bringing jobs that presuppose container delivery or a DB (image-scan / migration, etc.) into this no-Docker repository ([0011](0011-no-docker.md)) (Enforcement: none — a decision not to adopt. Having no jobs that presuppose container delivery or a DB is itself the state, and bringing one in shows up in the diff as an added workflow)
