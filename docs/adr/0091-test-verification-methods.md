# Test Verification Methods (Where Async RSC Tests Go, Building In Automated a11y Tests, Visual Regression, E2E Execution Conditions)

Settles **where async Server Component (RSC) tests go**, which [0090](0090-testing-strategy.md) delegated to this ADR, **building in automated a11y tests** on top of the static checks and manual checks of [0100](0100-accessibility-target.md), and **visual regression** and **the execution conditions of E2E**. All of these are **verification methods** riding on the tooling of [0090](0090-testing-strategy.md)'s test pyramid (unit / component / integration / e2e), and are bundled into this ADR as one domain.

Whether to adopt a UI catalog (Storybook) is a separate subject — a development tool choice, not a functional seam — and is owned by [0054](0054-ui-catalog-storybook.md).

## Status

Accepted

## Context

[0090](0090-testing-strategy.md) settles per-layer responsibilities (unit / component / integration / e2e) but delegates **the testing policy for Server Components / the line between RSC, route handlers and E2E** to this ADR. Without it, this discussion flares up again with every test PR, and the means of satisfying the coverage gate (0090) are not settled either.

[0100](0100-accessibility-target.md) composes a11y verification from "biome static checks + manual checks", but **automated checks against the runtime DOM** (ARIA consistency, measured contrast) cannot be detected by biome (static), leaving verification of the AA target (0100) dependent on manual review.

This ADR settles them on the basis of the two principles of [0010](0010-standards-and-non-lockin.md) (standards conformance / the no-lock-in test).

## Decision

### 1. Where RSC tests go

- **Async RSCs themselves are verified with unit (Vitest + RTL)**. An async Server Component is **an async function that returns JSX**, and can be rendered in the form `render(await Component(props))`. What React Testing Library cannot handle is `render(<Component />)` (passing it as an element); the form that awaits it as a function and then passes the result does not hit this limitation
- **Fetching is swapped at the module boundary**. Replacing `adapters` with `vi.mock` means the import chain including `server-only` is never loaded at all, so there is no need to stack rendering mocks imitating the server runtime (consistent with the mock strategy of [0090](0090-testing-strategy.md), which swaps module boundaries with `vi.mock`)
- **What unit bears is how fetch results are assembled and passed on**. How fetched values are mapped, routing to framework boundaries such as `notFound()`, and rethrowing failure classifications are all decided without the substance of the fetch, so they are unit's subjects
- **What E2E / integration bear is limited to what can be verified only end to end**. The shape of real API responses and contract conformance are integration (MSW); browser paths, the correspondence between streaming and HTTP status, hydration and cache revalidation are E2E (Playwright). A fetch mocked in unit is not counted as "having verified the fetch"
- **Route segments (`src/app/**/page.tsx`) are judged separately**. They depend on the App Router convention that `params` / `searchParams` are Promises and on generated types, so whether to include them as unit subjects is decided individually as the route side's verification method (placed on the E2E side)
- **Justification (vendor-independent / [0010](0010-standards-and-non-lockin.md))**: this line is decided not by "how much of the rendering path the framework provides is reproduced" but by **whether the subject of verification needs the substance of the fetch**. So the line does not move when React / Next.js implementation details change, and it does not depend on whether Vitest or Playwright is used
- What this ADR settles is **placement**. **The concrete MSW mock pipeline (contract → contract-driven MSW mocks) is the responsibility of [0071](0071-bff-api-integration.md)**, and is not decided twice in this ADR (it connects to the mock strategy of [0090](0090-testing-strategy.md) = MSW / `vi.mock`)

### 2. Building in automated a11y tests

- **axe-core is built in as the runtime automated a11y check**. The bindings ride on each framework 0090 adopted = **`vitest-axe` (Vitest + RTL) for the component layer / `@axe-core/playwright` for the story and e2e layers**
- **Every story is checked in a real browser**. It piggybacks on the same digest-pinned container and the same story enumeration as visual regression, adding no extra runner (§3). **Being a real browser is the essence** — jsdom has neither rendering nor colour computation and cannot check `color-contrast`, so that rule is disabled in the component layer
- **Only the one theme that is captured is checked**. Checking every story for two themes would double the run. For the theme not captured (dark), only that the colour scheme takes effect on surfaces is checked (`vrt/theme-tokens.spec.ts`). **Contrast violations that occur only in one theme are not reached** — the correctness of colour values is held by matching the token SSOT against the generated artifacts (`tokens-drift`), and what this place holds is detection in real rendering
- **Specs and jobs are separate from visual regression**. If a11y failures mixed into the retake report, the retake path would try to retake them. Retaking does not fix a11y; only the baseline images would end up approved
- **The responsibility boundary is drawn not by "whether there is a story" but by "what is visible at that layer"**. `axe()` **is written in every test of a subject that returns rendering, whether or not it has a story**. The two layers are not maintaining the same viewpoint twice; **they see different things**:
  - **What the component layer (jsdom) sees** is the **ARIA consistency, accessible names and relationships** that the component must satisfy on its own. These are pinned as the component's contract, so the unit run fails the moment the contract breaks. Colour is not visible (`color-contrast` is disabled). **`region` is disabled too** — it is a page-level best-practice rule checking "whether all page content is contained in landmarks", and structurally fits neither the render of a single component with no landmark nor content that portals out directly under `body`. It is not a rule about a component's semantics, so disabling it does not narrow the scope of checking
  - **What the story layer (real browser) sees** is **what appears only in real rendering** — measured contrast, and breakage in composed states. All stories are run in one theme (above)
  - ARIA rules can fire in both layers, but **the timing and unit of failure differ**, so it is not duplication. Dropping one side means either the PR's unit run can no longer detect that a component's contract broke (if the component side is dropped), or that text cannot be read in the actual colour scheme can no longer be detected (if the story side is dropped)
  - Therefore **subjects without stories (feature compositions / pages) also need `axe()`**. The story layer does not reach them, so that is the only checkpoint
- **The range of rules checked is decided by the conformance target itself**. By default axe runs beyond the target (`best-practice`, etc.), so without declaring the range, levels that were never committed to get evaluated across every story. The declaration maps the target ([0100](0100-accessibility-target.md) = WCAG 2.x AA) onto axe tags, and moving the target means changing 0100 first
- **Disabled rules are declared in one place with a reason and a removal condition**. What may be removed from every story is only what fires as a side effect of a story rendering a component on its own; "can't fix it right now" is not a reason
- **Disabling that names a story is limited to cases unreachable because of an upstream implementation**. The condition is that it cannot be removed by the consuming implementation and that users cannot actually reach it, and the declaration enumerates the target stories. The same rule stays alive for other stories
- **Justification (vendor-independent / [0010](0010-standards-and-non-lockin.md))**: the AA target (0100) requires a layer that machine-verifies **ARIA consistency and contrast in the runtime DOM**, which biome (static) cannot express. This need does not depend on any particular vendor — axe-core is the de facto a11y engine shared by Lighthouse / Deque / various `*-axe` wrappers, and the pattern "with axe removed from the justification, lay a layer in the tests that automatically asserts runtime a11y" is justified by AA conformance itself (axe was chosen as one factor, on independent grounds, from among the options (manual only / other engines)). `vitest-axe` / `@axe-core/playwright` are unique as the standard bindings for the frameworks already decided in 0090
- Adding dependencies: exact pin + `pnpm audit` ([0004](0004-library-management.md)). CI integration goes to [0153](0153-ci-configuration.md)

### 3. Visual regression = adopt Playwright screenshot comparison

- **Visual regression is adopted**, running on **the Playwright screenshot comparison (`toHaveScreenshot()`) that [0090](0090-testing-strategy.md) already adopts**. No additional service or separate runner is introduced
- **Justification (vendor-independent / [0010](0010-standards-and-non-lockin.md))**: what we want to detect is "unintended visual change", which DOM assertions cannot express. Playwright already runs for E2E, and screenshot comparison is its **built-in feature**, so the pattern "compare diffs against baseline images in CI" holds even with a dedicated SaaS removed from the justification
- **The primary subject is Storybook stories** ([0054](0054-ui-catalog-storybook.md)). The stories are the list of what components exist, and make a more stable unit of comparison than feature screens. Screen-level comparison is limited to the main journeys
- **Baseline images are placed in a dedicated repository and referenced as a submodule**. PNGs are already compressed and neither delta nor zlib helps, so placing them in the same repo would permanently accumulate almost the whole of every update, and every touch of a design token moves all of them. The store holds neither workflows nor rulesets, and all updates and cleanup are pushed in from the main repository
- **The store's visibility is `private` by default**. Baseline images are the screens' look itself, so a default that leans public is not taken. The cost is that **comparison fails on PRs from outside (forks)** — fork PRs receive no secrets and cannot obtain the token to read baseline images. A repository that accepts external PRs makes it `public`
- **A retake is one commit containing the whole set, whose parent is always the store's root**. Chaining retakes would make old sets ancestors of new sets, and cleanup could drop none of them. The root is shared because compare cannot compare unrelated histories
- **Only the sets pointed at by the main repository's live refs are retained**, and the condition is declared in one place with a reason and a removal condition. That baseline images are not complete when going back to past commits is a premise, and **cleanup is triggered by a person** (it cannot be undone, and a miscalculated retention would kill live pointers)
- **The pointer enters by the path through which that branch receives changes**. It is pushed to branches that accept direct pushes; for branches whose ruleset requires a PR (`release/**` / `hotfix/**` and each environment's branch), a PR carrying only the gitlink is opened. **That PR is one per target, updated rather than reopened on every retake** — retakes happen repeatedly, so adding one per retake leans toward unmerged proposals piling up. **The shape where protection is relaxed to let a bot push directly is not adopted** — protection that can be bypassed is not protection, and what is relaxed cannot be narrowed per ref, so `production` would be opened along with it. The path is decided by querying the ruleset itself, holding no copy of its patterns
- **Nothing is captured from a broken tree**. Retakes run at times when no one is watching, so the picture at that moment becomes the source of truth as is, and capturing while the inputs that decide the picture are broken burns the breakage into the baseline images. What is used for the decision is **a list naming the checks that can move the picture**, not everything that is failing — counting everything would include the check that waits for approval of images that do not exist until captured, and approval would wait for the retake while the retake waits for approval. **What is looked at is the latest result of each check**, without aggregating attempts — aggregating would keep a check that wobbled once failed for as long as that commit lives, and the retake could not happen even after rerunning it to green
- **On a revert, retake without a label**. Cleanup may have deleted the set to return to. A revert is by definition an operation that "returns to a previously approved state", so automating it does not break the meaning of approval
- **Approval is done by reviewing image diffs, and its unit is a label (`baseline-approve`), not PR review**. The operation of retaking baseline images (the `baseline-retake` label / running it locally) goes only as far as "making the pixels viewable", and is not itself approval. On a PR where baseline images move, the approval label is required. The unit is a label because what is being judged is the baseline images, not the whole PR; that it also works in a one-person repository is merely a consequence. Diffs are viewed through before/after links that the retake comment lists per moved image — the images themselves are not pasted into PR comments because, when the store is private, GitHub's image proxy accesses them anonymously and gets 404 (the viewer's permissions do not matter). The store's compare view cannot be used: a retake stacks the whole set on top of the store's root, so the common ancestor becomes the root, and instead of the few images that moved, the whole set is listed as "added"
- **What can be retaken is limited to the diffs reported by the preceding run**. Taking the reported set and the retaken set from the same source (the run's result report) closes the path by which diffs not shown get into the baseline images
- **When one label covers multiple lines, the label is not consumed until all lines are covered**. If each line has a different report source, the reports also come out at different times. Retaking only the line that reported first and removing the label means the line that reported late is never retaken on that branch again — **a retake happened, yet it is not covered**, a state that is neither green nor red. The decision distinguishes "the report has not come out yet" from "it came out but has no diff", rather than just "no report". The former is waiting, not that there is nothing to capture
- **The tree that is judged and the tree that is captured are made to match**. Comparison is done against the result of merging into the base, so branches behind the base are not allowed to retake. Requiring being up to date at merge time means the judged tree is merged as is
- **Comparison also runs after landing on a protected branch**. It fires only when the premise (the judged tree is what gets merged) breaks. Baseline images are not retaken here — that would make a state in which nobody looked at the pixels the source of truth
- **Exclusions are declared in one place with a reason and a removal condition**. Limited to stories where capturing has no meaning (those whose look is a function of time, etc.); "can't fix it right now" is not a reason for exclusion
- **OS / browser differences are absorbed by confining the execution environment to a digest-pinned container**. Font rasterization changes with both the OS and the CPU architecture, so baseline images are unique only by "which image they were captured with". Running directly on the host fails before comparison, so the capturer's environment never becomes the baseline
- **No tolerance is placed on the count of differing pixels** (`maxDiffPixels: 0`). Since the premise of capturing with the same image holds, a count threshold only lets through regressions that fit within it (a 1px shift, a local change)
- **The per-pixel colour-difference tolerance (`threshold`) is placed only at the floor that cuts off the anti-aliasing jitter on arcs (measured ±3)** (`0.02`, up to a difference of 5.28 in greyscale). Playwright's default of `0.2` counts differences up to 52.8 as the same colour, letting through a mix-up between adjacent colour steps (`neutral-400` and `neutral-500` differ by 48). Lowering the floor below this leaves the jitter as a permanent red; raising it lets low-contrast regressions through. The calculation and how it was measured are owned by [`vrt/README.md`](../../vrt/README.md)
- **Flakiness is eliminated by pinning the capture conditions** (stopping animations / `prefers-reduced-motion` / waiting for font loading / hiding the cursor / pinning timezone and locale). Stories that change over time are handled by "waiting until they settle", not absorbed by a tolerance. **However, the anti-aliasing jitter on arcs (measured ±3) is not suppressed on the story side. The reversal condition is when two captures of the same input come to match byte for byte** — when rasterization no longer depends on parallelism, or when comparison can judge by shape rather than per-pixel colour difference. In measurement, the arcs of a slider thumb and the roundness of badges move within 15 × 8 pixels with a maximum difference of 2, staying inside the comparison floor. **What would have to be suppressed is the arc itself**, so the story side has no move to make — that is the reason for not doing it — and the defense lies on the capturing side (limiting retakes to the reported set). **"An unexplained line appeared in a retake diff" is not a condition** — that means a full retake happened, and is a matter of closing that path

The mechanism's procedures (the flow of retaking, approval and cleanup) are owned by [`docs/design/vrt.md`](../design/vrt.md).

### 4. E2E execution conditions

- **E2E runs in MSW mode, independent of the backend**. No backend is started in CI. The premise is that the mocks **return the same response to the same request**; responses generated from the contract change their contents on every call as is, so neither screen baseline images nor content verification would hold
- **Screen-level comparison piggybacks on the same digest-pinned container as story comparison, and shares the baseline image store too** (§3)
- **The app is started on the host, and only the browser runs in the container**. `node_modules` is resolved for the OS and CPU it was installed on, so `next start` cannot be started inside the container
- **Three items riding on the same Playwright foundation are included in E2E's reach rather than made independent**:
  - **Browser errors** — detects hydration mismatches / exceptions during rendering / communication failures. **Hydration mismatches pass both the build and type checking, and appear only on a real device**
  - **Responsive** — checked at the three tiers of [0051](0051-styling-system.md). The boundary values are held by design tokens, and no numbers are written into tests
  - **Cross-browser** — checks only the modern browsers that [0102](0102-browser-support.md) ratifies, folded into three rendering engines (Chromium / Firefox / WebKit). **That neither brands nor versions are checked** is written in the job

## Prohibitions

- ❌ Running async RSCs by stacking rendering mocks that imitate the server runtime (fetching is swapped by `vi.mock` of `adapters`; verification that this cannot cover is E2E / integration's job) (Enforcement: Prose — **partly mechanizable**. Importing server rendering implementations (`react-server-dom-*` / `next/dist/server/**`) from tests could be rejected in the form of `no-restricted-imports`, but no rule exists. A hand-assembled mock runtime is not determined by the shape of the code)
- ❌ Counting a fetch mocked in unit as "having verified the fetch" (the shape of real API responses is integration; browser paths and status are E2E) (Enforcement: Prose — **not mechanizable**. What is counted as "verified" is a matter of reporting and judgment and does not appear in code)
- ❌ Removing a feature's `page-content.tsx` from the denominator of coverage and the 1:1 gate on the premise that it cannot be verified (exclusion is limited to what "can be verified only end to end") (Enforcement: `scripts/coverage-exclusion.gate.test.ts` makes exclusions be recorded in the owning README. Adding `page-content` to the exclusions itself is Prose — **mechanizable** (rejecting when a pattern matching `page-content` enters `EXCLUDED_FROM_CHECKS`; no rule exists))
- ❌ Settling the MSW mock pipeline mechanism in this ADR (owned by [0071](0071-bff-api-integration.md); not decided twice) (Enforcement: Prose — **not mechanizable**. Which ADR decides the mechanism is a matter of document ownership and does not appear in the shape of code)
- ❌ Disabling axe (`vitest-axe` / `@axe-core/playwright`) without reason, or detaching automated a11y checks from feature implementation to make them an "afterthought" (connects to [0100](0100-accessibility-target.md)'s guarantee at implementation-PR time) (Enforcement: disabling in the story layer is required by `vrt/lib/a11y-rules.test.ts` to carry a reason and a removal condition, and the existence of the `a11y` job as a required check is checked by `make actions-required-check-lint`. The scaffold (`pnpm gen`) places `axe()` at generation time. Disabling inside component-layer tests and deletion after generation are Prose — **not mechanizable**. Whether a disabling has a reason is a judgment)
- ❌ Adding a11y-related dependencies without an exact pin / `pnpm audit` ([0004](0004-library-management.md)) (Enforcement: the `dependency-review` job rejects vulnerabilities of high or above that the PR brings in. The exact pin is Prose — **mechanizable** (rejecting `^` / `~` in `package.json` version specifiers; no rule exists))
- ❌ Raising the visual regression diff tolerance to absorb flakiness (flakiness is eliminated by pinning capture conditions; a threshold lets regressions of that width through; the colour-difference `threshold` is not raised from the floor of `0.02` that cuts off the jitter) (Enforcement: Prose — **mechanizable** (rejecting when a non-zero value of `maxDiffPixels` / `maxDiffPixelRatio`, or a `threshold` value other than `0.02`, appears in the Playwright config and specs; no rule exists))
- ❌ Including unreported diffs in what is retaken, or treating the retake of baseline images itself as approval (Enforcement: the `baseline-approval` job (required) requires, on a PR that moved baseline images, an approval label separate from the retake. The range to retake is taken from the report by `scripts/vrt/report.ts`, but whether images captured locally fit within the reported set is Prose — **not mechanizable**. It is not decided without checking against that run's report)
- ❌ Automatically retaking baseline images on a protected branch (it would erase the signal that the premise broke) (Enforcement: Prose — **mechanizable** (a gate reading the workflow that rejects unless `vrt-guard.yaml`, which runs on protected branches, has no write permission and does not call the retake; no rule exists))
- ❌ Counting every failing check as a retake condition, or aggregating attempts in the decision (§3; approval and retake would wait for each other) (Enforcement: Prose — **mechanizable** (cutting the retake decision out into scripts and pinning with unit tests that it reads only the named list of checks and the latest attempt of each; no rule exists))
- ❌ Relaxing the protection of the baseline image store to let a bot push directly (§3; the gitlink is carried by a PR) (Enforcement: Prose — **partly mechanizable**. That `bypass_actors` in the declaration file is empty can be seen statically, but no rule exists. The actual ruleset lives on GitHub and does not appear in this tree)
- ❌ Making do with exclusions declared only on the story side, or excluding on the grounds of flakiness (flakiness is eliminated by capture conditions) (Enforcement: `vrt/lib/excluded-stories.test.ts` makes exclusions live in one declaration with a reason and a removal condition. Not using flakiness as a reason is Prose — **not mechanizable**. The validity of a reason's content is a judgment)
- ❌ Making stories opt in to comparison (with opt-in, newly added stories silently fall out of scope) (Enforcement: `vrt/lib/story-index.test.ts` (pins that the capture targets are taken from the full inventory, and exclusions are drawn only from the declaration))
- ❌ Applying a ruleset to the baseline image store (blocking our own retake pushes), or giving the store its own workflows (the source of truth would split in two) (Enforcement: Prose — **not mechanizable**. The store is a separate repository, and its rulesets and workflows do not appear in this tree)
- ❌ Running baseline image cleanup automatically (an irreversible operation is not run without the judgment of a person who read the report) (Enforcement: Prose — **mechanizable** (rejecting when `on:` of `baseline-prune.yaml` has anything other than `workflow_dispatch`; no rule exists))
- ❌ Making E2E depend on the backend / starting the app inside a container (§4) (Enforcement: Prose — **partly mechanizable**. That the E2E config starts the app on the host in MSW mode could be rejected by a gate reading the config, but no rule exists. Whether a spec's verification depends on real backend behaviour is not determined by the shape of the code)

## Notes

- This ADR settles placement, and by delegating the mock pipeline to [0071](0071-bff-api-integration.md) avoids duplicating 0090's mock strategy and 0071's contract-driven mocks
- The per-feature granularity of applying axe is decided per feature, and CI integration is owned by [0153](0153-ci-configuration.md) (CI configuration)
- **The UI catalog is outside this ADR's reach**. The Storybook / UI catalog subject is owned by [0054](0054-ui-catalog-storybook.md), and guaranteeing the catalog's quality is owned by 0054
