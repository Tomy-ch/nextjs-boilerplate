# `/mypage/coupons` クーポン（機能要件）

> 画面要件は [`page.screen.md`](page.screen.ja.md)。

## 主体と所有

ユーザー自身のクーポン。**どのクーポンを持っているか、コードで 1 枚出るかはバックエンドの判断**で、
この画面はどちらも決めない。

**各クーポンの状態はここで、その時刻を「いま」と突き合わせて決める。** 契約は状態を返さず、判定の
たびに突き合わせるよう求めている（`openapi/api.gen.yaml` の `CouponResponse`）。複数が同時に成り立つ
ときは、もう変わらないほうを先に言う: 使用済み、次に期限切れ、次に利用開始前。「いま」は route が
読んで渡すので、検証で固定できる（[`config/clock`](../../../../../../src/config/README.ja.md)）。

## 取得

1 系統: `GET /v1/users/me/coupons`。契約が返す順（発行の新しい順）のまま、ページングなし。キャッシュ
しない。レンダリングのたびに取り直す。

## 送信

`<form action>` + `useActionState` + `useFormStatus`（[0061](../../../../../adr/0061-form-mutation-ux.ja.md)）で
`POST /v1/campaigns/claims` へ。

- **コードは入力のまま送る。** 前後の空白と大文字・小文字の違いは契約が無視する。送る前に止めるのは
  空（または空白だけ）のコードだけで、必ず弾かれるため。長さと形式はここでは確かめない —— 契約が
  どちらも宣言していない
- **受け取りには毎回冪等キーを付ける。** 受け取りは取り消せず、別のキーで送り直すと上限内でもう 1 枚
  出る。キーは応答が受け取りを確定させたら作り直す —— 成立・コードが弾かれた・契約が読めなかった要求
  （`400`）。競合（同じキーの受け取りが処理中）・一時的に使えない・通信の失敗のあとは同じキーで送り直す
  ので、成立していた受け取りが 2 枚目にならない
- 成立したら一覧を取り直し、画面はその場に留まる

**受け取りの応答が届かなかったときは、一覧を確かめてから押し直す。** その場合を見分ける仕組みは
足さない —— 行は一覧に現れたか、現れなかったかのどちらか。

## 失敗

| どこで | 何が起きるか |
| --- | --- |
| 一覧の取得 | route の境界が画面全体を受け、再試行を出す（[0080](../../../../../adr/0080-error-handling.ja.md)） |
| 受け取り: コードが受け付けられない（`422`） | **理由によらず 1 つの文言。** 契約が区別しないため。区別すると有効なコードを言い当てる手がかりになる |
| 受け取り: 競合（`409`） | 待ってから同じキーで送り直す。契約が宣言するのは汎用の競合だけで、ここは IETF の Idempotency-Key の draft（`draft-ietf-httpapi-idempotency-key-header` §2.7）に従う —— 同じキーの同時要求に `409` を充て、直さずに送り直してよいとする |
| 受け取り: 要求を読めなかった（`400`、またはキーが無い） | 画面を読み込み直す。コードを直しても通らない |
| 受け取り: 使えない・失敗（`5xx`、通信） | フォームの脇に出す。入力とキーは保つ |
| 受け取り: セッション切れ（`401`） | ログインへ送り、この画面へ戻す |

## 認可

マイページと同じ（[`../page.function.md`](../page.function.ja.md#認可)）。未認証の主体はログインへ、
未登録の主体は登録（`/onboarding`）へ、どちらもこの画面へ戻る指示つきで送る。
