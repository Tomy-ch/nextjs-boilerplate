# `/admin/users/[id]/coupons/new` 1 人のユーザーへのクーポンの発行（機能要件）

> 画面要件は [`page.screen.md`](page.screen.ja.md)。
>
> 認可とレイアウトシェルの約束は [`../../../../layout.function.md`](../../../../layout.function.ja.md) が持つ。

名指された 1 人のユーザーに、クーポンを 1 枚発行する。値引き、適用される商品、有効期限、任意で使えるようになる時点と
必要な最低購入額を決める。

## 主体と所有

**管理者の役割を要する。** 画面に辿り着けるかは外枠が決めるが、**送信のエンドポイントも自分で確かめる**。送信は画面とは
別のエントリポイントで、画面を通らずに呼べる。

**受け取り手は URL が決め、この画面では選ばない。** 入ってくる道はユーザー一覧の行である。画面は誰がクーポンを受け取るかを
見せ、それを変える操作を出さない。発行は取り消せないので、内容と同じ面で受け取り手を選ばせると、別の人へ送ってしまう
余地が広がる。

**業務上の妥当性はバックエンドが持つ。** この画面が見るのは形と、画面から見える前後関係 —— 利用開始日が有効期限より前で
あること —— だけである。受け取り手がまだクーポンを受け取れるか、範囲の対象が存在するか、内容が全体として受け付けられるかは
バックエンドが判定する（[0070](../../../../../../../adr/0070-backend-role-separation.md)）。

**発行は取り消すことも編集することもできない。** 契約には、発行したクーポンを無効にする道も変える道も無い。

## 誰が受け取れるか

**退会していないユーザーだけ。** 存在しないユーザーは not-found の面になる。退会したユーザーはそのことを出し、フォームは
出さない —— この画面がその人のために送れるものは無い。

## 送るもの

| 項目 | 必須 | 補足 |
| --- | --- | --- |
| 受け取り手 | ○ | URL が名指すユーザー。入力ではない |
| 値引き | ○ | 種類（定額か定率か）とその値。上限は定率にだけ付く |
| 範囲 | ○ | 全商品、1 つのカテゴリ、1 つの商品のいずれか |
| 有効期限 | ○ | クーポンが使えなくなる最初の時点 |
| 利用開始 | — | 空なら発行した時点から使える。有効期限より前 |
| 最低購入額 | — | 空なら購入額を問わない |

**額・日時・範囲は、キャンペーンの定義と同じ規則に従う** —— 額は数値を経由させず、日時は打つ人の時間帯で打って瞬間として
送り、範囲はちょうど 1 つの対象を持つ
（[`../../../../campaigns/new/page.function.md`](../../../../campaigns/new/page.function.ja.md)）。

## 入力の判定は 1 か所が持つ

**送る前と受け取った後で、同じ module の同じ判定を通す。**

## 送信

**発行は、受け取り手を名指す確認からだけ送る。** 取り消せないので、内容と相手を出ていく前に一度読み上げる。

**結果が分かるまで、再送は同じ冪等キーを載せる。** 契約はキーを要求し、そのキーでの再送には最初の結果を繰り返し返す。
別のキーは別の発行である。**失敗が結果を定めないまま残しているあいだ（通信が切れた、サービスが利用できない）は内容を
変えられず**、そのまま送り直すことだけができる。**競合は、同じキーのリクエストがまだ処理中であると読む。** キーと内容は
止めたまま保ち、文言は同じ内容を後でもう一度送るよう求める。応答が結果を定めたら —— 成立も含めて —— 次の送信は新しい
キーを載せる。開き直した画面は新しいキーを載せる。

## 成立したら留まる

**成立したら画面に留まり、誰が何を受け取ったかを言う。** 管理側にはユーザーのクーポンを出す画面が無いため、移った先では
発行が起きたことを出せない。フォームは空にして「続けて発行する」の後ろに隠すので、気づかないまま同じ操作をもう一度
押して 2 枚目を発行することはない。2 枚目は新しいキーを載せる。

## 失敗

| 起きたこと | 出すもの |
| --- | --- |
| 形や前後関係の誤り | 欄ごとの文言。送る前に出す |
| 受け取り手が退会した、またはもう存在しない | フォームを、そのことを言って一覧へ戻す面へ差し替える。何も送り直せない |
| 範囲のカテゴリや商品がもう存在しない | その対象の欄に出す。残りは保ち、もう一度送れる |
| 2 つのどちらが見つからなかったのか判らない | どちらも名指さない文言を 1 つ、確認の中に出す |
| 競合 | 確認の中に出す。内容は送り直すために止めたまま |
| バックエンドが欄を名指した | その欄に出す |
| バックエンドが欄を名指さずに内容を拒んだ | 全体の文言を 1 つ、確認の中に出す |
| 結果が定まらない（通信が切れた、サービスが利用できない） | 確認の中に出す。送り直すまで内容を止める |
| 役割が足りない | 送信そのものが通らなかったことだけ |

**2 つの「見つからない」は、応答ではなく画面が見分ける。** 契約は、受け取り手が無いときも範囲の対象が無いときも同じ
ステータスを返す。全商品の範囲は対象を持たないので、そこでの not-found は受け取り手である。そうでなければ受け取り手を
読み直す。無いか退会済みなら受け取り手、あれば対象である。

**欄を名指す拒否は確認を閉じる。** 直す欄は確認の中ではなく画面にある。

## バックエンドが無いと届かないもの

**発行したクーポンがユーザー自身のクーポン一覧に現れること**は、モックに対しては見せられない。モックはリクエストの間で
状態を持たず、買う側でサインインしているユーザーは受け取り手ではない。行程は画面の成立の報告で止まる。
