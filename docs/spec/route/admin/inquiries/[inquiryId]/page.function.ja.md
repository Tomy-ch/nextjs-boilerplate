# `/admin/inquiries/[inquiryId]` 問い合わせの対応（機能要件）

> 画面要件は [`page.screen.md`](page.screen.ja.md)。

## 主体と所有

**管理者ロールを要する。** 役割の判定はバックエンドが持ち、足りない主体には `403` が返る。

送り手の種別は**サーバが決める**。このエンドポイントから入った回答は運営として記録され、送信で指定はできない。

## 取得

`GET /v1/inquiries/{inquiryId}/messages` の 1 系統だけ。形も開始位置の意味も、利用者側の履歴と
同じ。存在しない問い合わせには `404` が返る。

動的セグメントは取得へ渡す前に識別子として確定させる。形が契約に合わない要求は取得が
`not-found` として返す。

## 購読

**この画面は会話そのものを購読しない。** 契約が持つ購読のエンドポイントは「自分の問い合わせ」と
「更新フィード」の 2 つで、運営が任意の 1 件を直接購読するエンドポイントが無い。

代わりにフィードを購読し、**開いている問い合わせが動いたときだけ**canonical を取り直す。新しい 1 通は
届いた本文としてではなく、取り直した canonical として現れる。フィードが本文を運ばない以上、これは
遠回りではなく唯一の経路である。

## 送信

`POST /v1/inquiries/{inquiryId}/messages` を Server Action の往復で送る。

**回答先は画面が送信に載せる。** 運営は複数の問い合わせを行き来するため、「いま開いているもの」を
サーバ側で決められない。

冪等キーと本文の扱いは利用者側の送信と同じ
（[`../../../shop/mypage/inquiry/page.function.md`](../../../shop/mypage/inquiry/page.function.ja.md)）。

成立したら**開いている 1 件だけ**を取り直す。一覧はフィードが知らせる。

## 失敗

| 契約の応答 | 画面 |
| --- | --- |
| 403 | 役割が足りない |
| 404 | 存在しない問い合わせ |
| 422 | 本文の項目エラー |
