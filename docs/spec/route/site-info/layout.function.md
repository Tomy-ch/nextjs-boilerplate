# `(site-info)` 外枠（機能要件）

> 画面要件は [`layout.screen.md`](layout.screen.md)。
>
> ここに書くのは**配下のすべての画面に効く約束**です。個々の画面はそれぞれの `page.*.md` が持ちます。

配下は [`/about`](about/page.function.md) / [`/privacy`](privacy/page.function.md) /
[`/terms`](terms/page.function.md) の 3 枚。

## 何も取得しない

**この器はバックエンドにも cookie にも触れない。** それがこの器の存在理由である。

器が 1 つでも request 時の API に触れると、その route group の画面はすべて動的描画になる。静的な
殻と動的な穴を分ける仕組みは採っていないため（[0041](../../../adr/0041-cache-components-decision.md)）、
**配下の 3 枚を build 時に固めるには、器が何も読まないところまで下がるしかない**。

したがって `(shop)` と分けたのは、**描く時点が違うから**であって見せたい姿が違うからではない
（[`../shop/layout.function.md`](../shop/layout.function.md) の「カートの供給」）。

## 行き先

global nav が指すのは商品・購入履歴・マイページの 3 つで、`(shop)` と同じものを出す。利用者から
見れば同じサイトの同じ導線であり、器ごとに別の一覧を持つと、通った画面によって行ける場所が変わる。

**カートの入口を出さない。** 点数は読んだ状態であり、出すには request 時に読む必要がある。入口が
消えるだけで、`/cart` そのものへは nav とリンクから到達できる。

**管理への入口も出さない。** 出す・出さないの判定は session を読む。読まない器では判定ができず、
出さない側が安全側である（[0079](../../../adr/0079-auth-frontend-seam.md)）。

## 買い物との境界

**`(shop)` との間で client の状態は持ち越さない。** 器が分かれているので、境界を跨ぐ遷移は器ごと
入れ替える。買い物の途中で案内を読みに来ると、買い物の内側でだけ意味を持つ状態——取り消しの記憶
（[`../shop/layout.function.md`](../shop/layout.function.md)）——は失われる。

**これは受け入れた結果である。** 案内を読むことは買い物の続きではなく、そこを離れる操作だからで
ある（[0026](../../../adr/0026-layout-shell-mount.md)）。跨いでも残す必要が出たときは、この器と
`(shop)` を親の route group でまとめる。

## 認証

**保護しない。** 配下はいずれも、ログインする前に読めなければ意味を持たない内容である。
