# `(site-info)` 外枠（機能要件）

> 画面要件は [`layout.screen.md`](layout.screen.ja.md)。
>
> ここに書くのは**配下のすべての画面に効く約束**です。個々の画面はそれぞれの `page.*.md` が持ちます。

配下は [`/about`](about/page.function.ja.md) / [`/privacy`](privacy/page.function.ja.md) /
[`/terms`](terms/page.function.ja.md) の 3 枚。

## 何も取得しない

**このレイアウトシェルはバックエンドにも cookie にも触れない。** それがこのレイアウトシェルの存在理由である。

レイアウトシェルが request 時の API に触れるダイナミックホールを 1 つでも持つと、シェルは先に配られても、そのダイナミックホールを埋めるために
要求のたびにサーバーが動く（[0041](../../../adr/0041-cache-components-decision.ja.md)）。
**配下の 3 枚を build 時の姿だけで配るには、レイアウトシェルが何も読まないところまで下がるしかない**。

したがって `(shop)` と分けたのは、**レンダリングする時点が違うから**であって見せたい姿が違うからではない
（[`../shop/layout.function.md`](../shop/layout.function.ja.md) の「カートの供給」）。

## 行き先

global nav が指すのは商品・購入履歴・マイページの 3 つで、`(shop)` と同じものを出す。利用者から
見れば同じサイトの同じ導線であり、レイアウトシェルごとに別の一覧を持つと、通った画面によって行ける場所が変わる。

**カートの入口を出さない。** 点数は読んだ状態であり、出すには request 時に読む必要がある。入口が
消えるだけで、`/cart` そのものは閉じない。このレイアウトシェルから `/cart` を直接指す導線は無く、nav で
買い物の画面へ移れば、そこの header の入口から入れる。

**管理への入口も出さない。** 出す・出さないの判定は session を読む。読まないレイアウトシェルでは判定ができず、
出さない側が安全側である（[0079](../../../adr/0079-auth-frontend-seam.ja.md)）。

## 買い物との境界

**`(shop)` との間で client の状態は持ち越さない。** レイアウトシェルが分かれているので、境界を跨ぐ遷移はレイアウトシェルごと
入れ替える。買い物の途中で案内を読みに来ると、買い物の内側でだけ意味を持つ状態——取り消しの記憶
（[`../shop/layout.function.md`](../shop/layout.function.ja.md)）——は失われる。

**これは受け入れた結果である。** 案内を読むことは買い物の続きではなく、そこを離れる操作だからで
ある（[0026](../../../adr/0026-layout-shell-mount.ja.md)）。跨いでも残す必要が出たときは、このレイアウトシェルと
`(shop)` を親の route group でまとめる。
