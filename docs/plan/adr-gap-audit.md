# フロント開発における ADR 空白領域の監査(Fable 5)

監査対象: `docs/plan/adr-digest.md`(既存 ADR 群)+ `docs/adr/BACKLOG.md` + 個別 ADR 本体(0040 / 0060 / 0090 / 0071 / 0080 / 0081 / 0110 / 0101 / 0043 の関連箇所を grep で裏取り)
監査者: Fable 5 / 生成日: 2026-07-13
注記: 本リストは「あった方が良いかもしれない」候補の発散列挙であり、**各項目が本当に必要かの取捨選択は未実施**。必要性判断は別途。

## データ取得・キャッシュ・レンダリング境界

### 空白領域: Cache Components(PPR)有効化判断
- **内容**: `next.config.ts` の `cacheComponents: true`(PPR 既定化)を有効化するか否か。0040 は「B3 / B6 確定後に判断」と明示保留したが、B3(0071)/ B6(0080)が Accepted になった現在も判断が宙吊りのまま。
- **フロントでの影響**: 有効/無効でキャッシュモデル(`use cache` opt-in vs `cache: 'force-cache'`)と Suspense 境界の意味が根本的に変わるため、最初の feature 実装から書き方が分岐する。
- **隣接 ADR**: 0040(A4)— 「モードを強制しない」ことのみ確定し、有効化可否そのものは未決と本文に明記。
- **一次分類の目安**: decision

### 空白領域: キャッシュ・再検証戦略の具体
- **内容**: `use cache` / `cacheLife` / `cacheTag` / `revalidateTag` / `revalidatePath` の使い分け、tag 命名規約、どの層(adapters / feature / page)がキャッシュ指定を所有するか。
- **フロントでの影響**: Next.js 16 は fetch 既定 uncached のため、規約なしでは「全部素通し(性能問題)」か「各自バラバラに opt-in(stale データ・無効化漏れ)」の二択になる。
- **隣接 ADR**: 0040 が B3 へ委譲したが、0071(B3)は fetch wrapper の resilience(timeout / retry / breaker)のみで Next.js データキャッシュ設計を持たない(本文確認済み)。委譲の受け皿が実在しない「委譲先消失」状態。
- **一次分類の目安**: decision

### 空白領域: Suspense / streaming 境界と `loading.tsx` 配置
- **内容**: `loading.tsx` をどの route セグメントに置くか、`<Suspense>` 境界を feature 内のどの粒度で切るか、streaming SSR を前提にした fallback 設計。
- **フロントでの影響**: 境界の切り方で体感性能(TTFB vs 部分描画)と layout shift が決まり、後からの変更はコンポーネントツリー再編を伴う。
- **隣接 ADR**: 0040 が「`loading.tsx` / `error.tsx` 配置は B6 へ」と委譲したが、0080(B6)は `error.tsx` / `global-error.tsx` / `not-found.tsx` のみ確定し `loading.tsx` / Suspense に触れていない(本文確認済み)。こちらも委譲先消失。
- **一次分類の目安**: decision

### 空白領域: ミューテーション後の UI 更新規約
- **内容**: Server Action 成功後の画面反映を `revalidatePath` / `revalidateTag` / `router.refresh()` / `useOptimistic` のどれで行うかの既定と使い分け。
- **フロントでの影響**: 規約なしでは「更新したのに画面が古い」「二重に再取得する」が feature ごとにバラつく。
- **隣接 ADR**: 0071(Server Action は編成のみ)/ 0060(Server state = RSC fetch)はデータの「取り方」のみで「更新後の反映経路」が空白。
- **一次分類の目安**: rule(キャッシュ戦略 decision の従属規約)

### 空白領域: リクエスト重複排除・per-request メモ化
- **内容**: React `cache()` / fetch memoization を使って同一リクエスト内の重複 fetch を排除する規約(adapters クライアントに組み込むか、呼び出し側責務か)。
- **フロントでの影響**: RSC ツリーの複数箇所から同じ adapter を呼ぶと、規約なしでは BFF/バックエンドへの重複リクエストが静かに増える。
- **隣接 ADR**: 0071 — resilience は定めたが dedup / memoization は未言及。
- **一次分類の目安**: rule

### 空白領域: プリフェッチ方針
- **内容**: `<Link prefetch>` の既定(自動 prefetch を許すか)、`router.prefetch` の手動使用条件、大量リンク一覧での prefetch 抑制。
- **フロントでの影響**: 既定のままだと一覧ページで大量の投機的リクエストが BFF に飛び、レート制限・コストに直結する。
- **隣接 ADR**: 0040 / 0071 — いずれも未言及。
- **一次分類の目安**: rule

### 空白領域: ページネーション / 無限スクロール規約
- **内容**: offset vs cursor の UI 側扱い、searchParams でのページ状態表現、無限スクロール(IntersectionObserver + client fetch)を許すか(0060 の「Server state = RSC fetch 既定」と衝突する)。
- **フロントでの影響**: 無限スクロールは client fetch を必然的に伴うため、既定方針との整合を先に決めないと 0060 / 0071 違反かどうか判断できない。
- **隣接 ADR**: 0060(B5)/ 0071(B3)— client からの追加取得パターンが未定義。
- **一次分類の目安**: decision

### 空白領域: Route Handler(`/api/*`)の設計規約の残余
- **内容**: thin proxy と決めた `/api/*` の実装規約 — ルート命名、ストリーミング応答の可否、`waitUntil` 等の非同期後処理、Node runtime 前提の確認(0043 は proxy.ts のみ対象)。
- **フロントでの影響**: BFF 中継(テレメトリ・API proxy)実装時にハンドラごとに書き方が割れる。
- **隣接 ADR**: 0070(thin proxy の責務)/ 0043(proxy.ts の runtime)— Route Handler 自体の実装規約は両者の谷間。
- **一次分類の目安**: rule

## フォーム・ミューテーション UX

### 空白領域: 素の form の書き方規約
- **内容**: 0060 で form ライブラリを exclusion とした裏面として、「ライブラリなしでどう書くのが標準形か」(`<form action={serverAction}>` + `useActionState` の canonical パターン、非制御 vs 制御コンポーネントの既定)。
- **フロントでの影響**: exclusion だけでは実装者が各自流儀で書き、boilerplate として最も頻出する UI(フォーム)が最も不統一になる。
- **隣接 ADR**: 0060(B5)— ライブラリ非同梱のみ決定。0040 — `actions.ts` の置き場のみ。「書き方」は空白。
- **一次分類の目安**: rule(あるいは reference 実装同梱の decision)

### 空白領域: バリデーション UX(client 側検証)
- **内容**: zod スキーマ(0072 生成物)を client 側検証に再利用してよいか(型漏洩禁止との整合)、検証タイミング(blur / submit)、エラーメッセージの表示位置・文言規約。
- **フロントでの影響**: server round-trip でしか検証エラーが出ない UX になるか、スキーマを二重管理するかの分岐が feature ごとに発生する。
- **隣接 ADR**: 0072(B4)— zod は adapters 境界の response 検証用。「入力検証への転用」は未言及で、型漏洩禁止原則と緊張関係がある。
- **一次分類の目安**: decision

### 空白領域: Server Action の戻り値契約・pending・エラー統合
- **内容**: `useActionState` に返す state の標準形状(フィールドエラー / フォームエラー / 成功値)、0080 の sentinel 分類を Server Action 境界でどうシリアライズして client に渡すか、pending 表示(`useFormStatus`)の規約。
- **フロントでの影響**: Action ごとに戻り値形状が異なると、エラー表示コンポーネントが共通化できず 0080 の正規化投資が UI に届かない。
- **隣接 ADR**: 0080(B6)— adapters 境界の正規化までは確定。Server Action → client への「境界越えエラー契約」が空白。0071 — Action は編成のみ、と役割だけ確定。
- **一次分類の目安**: decision

### 空白領域: 楽観的更新・二重送信防止
- **内容**: `useOptimistic` の採用条件と失敗時ロールバック UX、submit ボタンの disabled / 冪等キーによる二重送信防止の標準形。
- **フロントでの影響**: 変更系 UI の体感と安全性が feature 実装者の裁量になり、二重 POST 事故(0071 で POST は retry opt-in と決めた思想と表裏)を UI 層で防げない。
- **隣接 ADR**: 0071(B3)— retry は HTTP 層のみ。UI 層の冪等性は未言及。
- **一次分類の目安**: rule

### 空白領域: ファイルアップロード / メディア送信 seam
- **内容**: アップロードを BFF 中継(multipart を `/api/*` proxy)にするか presigned URL 直 PUT にするかの seam、サイズ制限・進捗表示・中断の規約。
- **フロントでの影響**: thin proxy 原則(0070)と大容量ボディ中継は緊張関係にあり、seam を決めないと最初のアップロード機能で BFF 責務の議論が再燃する。
- **隣接 ADR**: 0070(A2)/ 0071(B3)— fetch wrapper は JSON API 前提の設計で multipart / バイナリに未言及。
- **一次分類の目安**: decision(または exclusion + seam)

### 空白領域: 離脱ガード / フォーム下書き
- **内容**: 未保存変更がある画面での遷移確認(`beforeunload` + App Router のクライアント遷移ブロック)と下書き保存の要否・標準形。
- **フロントでの影響**: App Router はクライアント遷移の中断 API が素直でなく、ad-hoc 実装が乱立しやすい。
- **隣接 ADR**: なし。
- **一次分類の目安**: rule(または exclusion)

### 空白領域: リッチテキスト / エディタ方針
- **内容**: WYSIWYG / Markdown エディタ(TipTap 等)を本体非同梱とする exclusion の明文化と、採用時のサニタイズ・表示(rehype 等)の seam。
- **フロントでの影響**: 0052 の exclusion 列挙(UI ライブラリ / アイコン / form コンポーネント)に含まれず、「沈黙 = 未判断」なのか「exclusion」なのか判別できない。
- **隣接 ADR**: 0052(B2)— 列挙外。
- **一次分類の目安**: exclusion

### 空白領域: 日付ピッカー等の複雑入力 UI の帰属
- **内容**: 日付ピッカー・コンボボックス・オートコンプリート等が 0052 の「form コンポーネント群」exclusion に含まれるのかの境界確定と、採用時の選定基準(a11y 準拠必須等)。
- **フロントでの影響**: exclusion の射程が曖昧だと、実装時に「入れてよいか」の判断が毎回ユーザ確認になる。
- **隣接 ADR**: 0052(B2)— 射程が粗い。0100(C2)— a11y 目標との接続も未記述。
- **一次分類の目安**: exclusion(射程の追補)

## UX 横断(表示状態・通知・インタラクション)

### 空白領域: ローディング / スケルトン UI 規約
- **内容**: スピナー vs スケルトンの使い分け、表示までの遅延(フラッシュ防止)、スケルトンと実 UI の形状一致要件。
- **フロントでの影響**: Suspense 境界(前述)と対になる「見た目」の規約がないと、画面ごとにローディング表現が不統一になり CLS も悪化する。
- **隣接 ADR**: 0101(C3)— CLS を指標にするが UI 規約は持たない。
- **一次分類の目安**: rule

### 空白領域: 空状態 / ゼロデータ / エラー状態の設計規約
- **内容**: 一覧 0 件・検索ヒットなし・部分エラー(一部 widget のみ失敗)時の表示パターンと文言の規約。
- **フロントでの影響**: 0080 は「エラーの正規化」まで、0100 は「目標水準」までで、実際に何を描画するかが毎回発明になる。
- **隣接 ADR**: 0080(B6)/ 0052(B2)。
- **一次分類の目安**: rule

### 空白領域: トースト / 通知 UI 規約
- **内容**: 操作結果のフィードバック手段(トースト / インライン / リダイレクト+メッセージ)の使い分け、トースト実装(自前 or ライブラリ = 0052 exclusion との関係)、a11y(live region)要件。
- **フロントでの影響**: Server Action 成功/失敗の通知経路が決まらないと、ミューテーション UX の標準形(前述)が完結しない。
- **隣接 ADR**: 0052(B2)/ 0080(B6)/ 0100(C2)— いずれも通知そのものは未言及。
- **一次分類の目安**: decision

### 空白領域: エラー画面の UX 階層
- **内容**: 404 / 5xx / 権限なしの各画面の文言・復帰導線(再試行ボタン / トップへ戻る)・デザインの規約。0080 は「正規化済みを表示するだけの薄い境界」という構造のみ。
- **フロントでの影響**: `error.tsx` の `reset()` を使った再試行 UX 等、ユーザに見える部分が未規定で品質がばらつく。
- **隣接 ADR**: 0080(B6)— 構造のみでコンテンツ・UX が空白。
- **一次分類の目安**: rule

### 空白領域: アニメーション / モーション方針
- **内容**: モーションライブラリ(Framer Motion 等)の採否(exclusion か)、CSS transition / View Transitions API の使用方針、`prefers-reduced-motion` 対応の必須化。
- **フロントでの影響**: reduced-motion は WCAG AA(0100)と直結するのに実装パターンが未定義で、ライブラリ持込可否も 0052 の射程外。
- **隣接 ADR**: 0050(B1)/ 0052(B2)/ 0100(C2)。
- **一次分類の目安**: decision(ライブラリ)+ rule(reduced-motion)

### 空白領域: モーダル / ダイアログ / ポータル / フォーカストラップ
- **内容**: ネイティブ `<dialog>` vs ポータル自前実装の既定、フォーカストラップ・Escape 閉じ・背景スクロールロックの必須要件、App Router の intercepting routes(`@modal` / `(.)`)を使った route-as-modal の採否。
- **フロントでの影響**: モーダルは a11y 事故の最頻発地点で、route-as-modal の採否は URL 設計にも波及する。
- **隣接 ADR**: 0100(C2)— 目標のみ。0040(A4)— parallel/intercepting routes に未言及。
- **一次分類の目安**: decision

### 空白領域: z-index / レイヤリング規約
- **内容**: レイヤー種別(ドロップダウン / モーダル / トースト / ツールチップ)ごとの z-index スケールを design token として定義するか。
- **フロントでの影響**: 規約なしの z-index は単調増加合戦になり、後から直すのが最も難しい CSS 負債になる。
- **隣接 ADR**: 0050(B1)— token = CSS 変数と決めたのみでスケール未定義。
- **一次分類の目安**: rule

### 空白領域: スクロール制御規約
- **内容**: 遷移時のスクロール復元(App Router の既定挙動の追認/上書き)、モーダル時の body ロック、アンカー/ページ内リンク、`scroll-behavior`。
- **フロントでの影響**: モーダル・無限スクロールと組み合わさると挙動が壊れやすく、ad-hoc 対応が積もる。
- **隣接 ADR**: なし。
- **一次分類の目安**: rule

### 空白領域: キーボードショートカット方針
- **内容**: グローバルショートカットを持つか、持つ場合の登録機構・競合管理・表記(ヘルプ)規約。
- **フロントでの影響**: 後付けで散在実装すると input フォーカス時の誤発火等の事故が起きる。
- **隣接 ADR**: 0100(C2)— キーボード操作性の目標のみ。
- **一次分類の目安**: exclusion(必要になるまで持たない)+ seam

### 空白領域: クリップボード操作規約
- **内容**: コピー機能の標準形(`navigator.clipboard` + 成功フィードバック)と権限失敗時のフォールバック。
- **フロントでの影響**: 小粒だが頻出 UI で、フィードバック(トースト)規約と連動して不統一になりやすい。
- **隣接 ADR**: なし。
- **一次分類の目安**: rule

### 空白領域: ドラッグ & ドロップ方針
- **内容**: 並べ替え・ファイルドロップの実装手段(ネイティブ DnD / ライブラリ)の採否と a11y 代替操作の要件。
- **フロントでの影響**: ライブラリ選定(0052 exclusion との関係)と WCAG 2.2 のドラッグ代替要件が絡む。
- **隣接 ADR**: 0052(B2)/ 0100(C2)。
- **一次分類の目安**: exclusion

### 空白領域: 印刷 / PDF 出力方針
- **内容**: print CSS を持つか、PDF 生成(client 印刷 vs サーバ生成)を seam として定義するか。
- **フロントでの影響**: 帳票系要件が出た時に BFF 責務(0070)との整合を毎回議論することになる。
- **隣接 ADR**: 0050(B1)— print media query 未言及。
- **一次分類の目安**: exclusion + seam

### 空白領域: モバイル対応の深掘り(セーフエリア / タッチ)
- **内容**: `viewport` 設定(Next.js の `viewport` export)、セーフエリア(`env(safe-area-inset-*)`)、タッチターゲット最小サイズ、ホバー非依存 UI の規約。
- **フロントでの影響**: 0130 は PWA(インストール性)の exclusion であって「モバイルブラウザでまともに使える」ための規約は別問題として空白。
- **隣接 ADR**: 0130(C8)/ 0100(C2)/ 0044(C7 — viewport export 未言及)。
- **一次分類の目安**: rule

### 空白領域: オンライン / オフライン検知 UX
- **内容**: 接続断の検知(`navigator.onLine` / fetch 失敗)と再接続時の再取得・ユーザ通知の標準形。オフラインキャッシュ(0130 exclusion)とは別の軽量な話。
- **フロントでの影響**: 0071 の retry/breaker はサーバ側 fetch の話で、ブラウザ側の接続断 UX は誰も所有していない。
- **隣接 ADR**: 0130(C8)/ 0071(B3)。
- **一次分類の目安**: rule(または exclusion)

## レイアウト・スタイリング深掘り

### 空白領域: レスポンシブ / ブレークポイント体系
- **内容**: Tailwind 既定ブレークポイントの追認 or カスタムスケール、mobile-first の明文化、コンテナクエリ(`@container`)の採用方針。
- **フロントでの影響**: 最初の 2〜3 画面でブレークポイントの使い方が固まってしまうため、後から体系を入れても手遅れになりやすい。
- **隣接 ADR**: 0050(B1)— Tailwind 採用と token = CSS 変数のみで、ブレークポイント体系は未言及。0102(C4)はブラウザ行列でありビューポートの話ではない。
- **一次分類の目安**: decision

### 空白領域: デザイントークン体系の具体
- **内容**: 「CSS 変数で token」(0050)の中身 — semantic 命名(`--color-bg-primary` 等)vs raw scale、spacing / typography / radius / shadow のスケール定義、Tailwind v4 `@theme` との対応。
- **フロントでの影響**: token の命名層(semantic か raw か)を決めずに書き始めると、ダークモード(0050 で採用済み)の切替実装が破綻する。
- **隣接 ADR**: 0050(B1)— 「design token は CSS 変数」という器のみで体系が空白。
- **一次分類の目安**: decision

### 空白領域: アイコン・SVG 運用の具体
- **内容**: アイコンライブラリ非同梱(0052)の裏面として、自前 SVG の置き場(`components` カーネル?)、inline component 化の方法(SVGR 採否 / 手書き)、`currentColor` 等の色規約。
- **フロントでの影響**: 最小 UI でもアイコンはほぼ必須で、規約なしでは置き場と実装形式が即座に発散する。
- **隣接 ADR**: 0052(B2)— ライブラリ exclusion のみ。0045(C5)— 「装飾 SVG は生 `<img>` 可」とだけ。
- **一次分類の目安**: rule

### 空白領域: Tailwind クラス運用規約

## 認証・セキュリティ seam

### 空白領域: 認証のフロント側 seam
- **内容**: 認証本体は out of scope(BACKLOG)だが、fork 先がどの認証を選んでも変わらない seam — トークン/セッションの保管場所規約(httpOnly cookie 前提か)、保護ルートの表現(layout / proxy optimistic / データ境界の 3 層分担の型)、未認証時リダイレクトと `returnUrl` 規約、ログアウト時の状態破棄。
- **フロントでの影響**: 0043 が「optimistic は proxy、確定認可はデータ境界」と分担を書いた以上、その間を繋ぐ画面側パターンがないと保護ページが実装できない。out of scope の中で最も「seam の欠落」が濃い領域。
- **隣接 ADR**: 0043(C6)/ 0070(A2)— 分担原則のみで seam の型が空白。
- **一次分類の目安**: decision(seam 定義)

### 空白領域: CSP / セキュリティヘッダ
- **内容**: Content-Security-Policy(nonce 運用 — Next.js は proxy でのヘッダ付与と交差)、`X-Frame-Options` / `Referrer-Policy` / `Permissions-Policy` / HSTS 等の既定セットと設定場所(`next.config.ts` headers vs proxy.ts vs PaaS)。
- **フロントでの影響**: 0110 はサプライチェーン/CI 系防御のみで、実行時のブラウザ側防御が丸ごと空白。後付け CSP は inline style/script との衝突で最も導入コストが高い。
- **隣接 ADR**: 0110(B10)— 本文確認済みで CSP 未言及。0043(C6)— ヘッダ操作「可能」とのみ。
- **一次分類の目安**: decision

### 空白領域: CSRF / Server Actions の origin 検証
- **内容**: Server Actions の `allowedOrigins`(`serverActions` 設定)、Route Handler 側の CSRF 対策方針(SameSite cookie 前提で足りるとするか)、の明文化。
- **フロントでの影響**: BFF が cookie ベース認証を中継する構成(0070 想定)では CSRF が現実の脅威になるが、所有 ADR がない。
- **隣接 ADR**: 0070(A2)/ 0110(B10)— いずれも未言及。
- **一次分類の目安**: rule

### 空白領域: XSS / サニタイズ規約
- **内容**: `dangerouslySetInnerHTML` の原則禁止と例外条件(sanitizer 必須 — DOMPurify 等の採否)、ユーザ生成コンテンツ表示の標準形、URL(`javascript:`)の検証。
- **フロントでの影響**: リッチテキスト・CMS 由来 HTML を表示した瞬間に必要になり、biome ルールで部分強制できるのに未決のまま。
- **隣接 ADR**: 0110(B10)— CodeQL で検出はするが「書いてよい/だめ」の規約は空白。
- **一次分類の目安**: rule

### 空白領域: BFF レート制限・abuse 対策 seam
- **内容**: `/api/*`(テレメトリ中継含む)への レート制限・ボディサイズ上限・認証なしエンドポイントの保護を、本体で持つか PaaS/fork 先に委ねるかの線引き。
- **フロントでの影響**: 0081 が「ブラウザ→BFF 中継」をテレメトリの seam にした結果、無防備な公開エンドポイントが本体構成に生まれるのに防御方針がない。
- **隣接 ADR**: 0081(B7)/ 0070(A2)— 中継 seam だけ決まり保護が空白。
- **一次分類の目安**: decision(または exclusion + seam)

### 空白領域: サードパーティスクリプト読込方針
- **内容**: `next/script` の strategy 使い分け、タグマネージャ / 埋め込みウィジェット / 決済 SDK 等の外部スクリプトを許す条件(CSP・同意ゲートとの連動)、`@next/third-parties` の採否。
- **フロントでの影響**: 0131(同意)と CSP(前述)の両方に跨る実行面の規約がなく、外部スクリプト 1 本目で判断が止まる。
- **隣接 ADR**: 0131(C9)— 同意ゲートの概念のみ。0045(C5)— フォント CDN 禁止のみで一般スクリプトは未言及。
- **一次分類の目安**: rule

### 空白領域: 決済 UI seam
- **内容**: 決済(Stripe Elements / PayPal 等)を本体非同梱とする exclusion の明文化と、採用時の seam(外部スクリプト方針・PCI 上フロントに置いてよい範囲・BFF 中継の要否)。
- **フロントでの影響**: EC 系 fork で最初に踏む領域なのに、i18n / PWA / 同意と違って exclusion 宣言すら存在しない。
- **隣接 ADR**: なし(0070 の thin proxy と間接関係)。
- **一次分類の目安**: exclusion + seam

## 国際化・フォーマット(i18n exclusion の外側)

### 空白領域: 日付・数値・通貨の locale-aware フォーマット

### 空白領域: タイムゾーン・hydration mismatch 方針
- **内容**: サーバ(UTC)とブラウザ(ローカル TZ)で日時表示がずれる問題の標準解 — 表示 TZ の既定(ユーザローカル / 固定)、`suppressHydrationWarning` の可否、時刻はクライアントで描画する等のパターン。
- **フロントでの影響**: RSC 既定(0040)の構成では日時を含むほぼ全ページで hydration mismatch の地雷になり、場当たり対処が増殖する。
- **隣接 ADR**: 0040(A4)— RSC 既定を決めたことで問題が生じるが対処は未言及。
- **一次分類の目安**: rule

### 空白領域: 相対時刻・リアルタイム時刻更新
- **内容**: 「3 分前」等の相対時刻表示(`Intl.RelativeTimeFormat`)と、その定期更新(client での interval 再描画)の標準形・更新粒度。
- **フロントでの影響**: RSC で描画すると即座に stale になる代表例で、client 境界の切り方(0040)との整合を型として示す必要がある。
- **隣接 ADR**: 0040(A4)/ 0060(B5)。
- **一次分類の目安**: rule

### 空白領域: UI 文言(コピー)の管理規約
- **内容**: i18n 非同梱(0121)の間、ハードコード文字列をどう置くか — JSX 直書き許容か、feature 内定数に寄せるか、エラーメッセージ文言(0080 と接続)の管理場所、トーン&マナー。
- **フロントでの影響**: 後から i18n を入れる fork 先にとって、文言が JSX 全面に散っているか定数に寄っているかで移行コストが桁違いになる。
- **隣接 ADR**: 0121(C1)— seam は route 構造のみで文言管理は未言及。0080(B6)— メッセージ変換はするが文言の置き場は空白。

## 観測性・分析・段階的公開の seam

### 空白領域: Web Vitals フィールド計測(RUM)の具体

### 空白領域: プロダクト分析イベント設計 seam

- **フロントでの影響**: exclusion(SaaS 非同梱)でも、計測呼び出しがコンポーネントに直書きされるか抽象を通るかは本体の構造問題として残る。

- **一次分類の目安**: decision(seam)+ exclusion(サービス)

- **一次分類の目安**: rule

### 空白領域: メンテナンスモード / 機能停止
- **内容**: 全面メンテ表示への切替手段(proxy.ts rewrite + env/フラグ)と、部分機能停止(kill switch)の標準形。

### 空白領域: build info / バージョン露出
- **内容**: デプロイ中のフロントのバージョン(commit SHA / build time)をどこに露出するか(meta タグ / ヘッダ / `/api/health`)と、0072 の「バックエンド SHA スタンプ」との突合手段。
- **フロントでの影響**: 障害調査時に「どのフロントがどの契約 SHA で動いているか」を特定できない。CI の起動スモーク(0153)にもヘルスエンドポイント規約がない。
- **隣接 ADR**: 0072(B4)/ 0081(B7 — resource attribute に version を入れるかは semconv 範囲だが供給元が未決)/ 0153(B9)。
- **一次分類の目安**: rule

### 空白領域: dynamic import / コード分割規約
- **内容**: `next/dynamic` / `React.lazy` の使用基準(重い client コンポーネント・条件付き表示 UI)、`ssr: false` の可否、分割しすぎのガイドライン。
- **フロントでの影響**: bundle size を予算指標(0101)にしながら、削減の主手段であるコード分割の規約がない。
- **隣接 ADR**: 0101(C3)/ 0040(A4)— 葉押し下げまでで分割手段は未言及。
- **一次分類の目安**: rule

### 空白領域: server-only / client-only 境界の一般規約
- **内容**: `import "server-only"` を config(0030)以外のどこに義務付けるか — adapters(トークン中継を含む)全体に必須化するか、`client-only` の使用基準。
- **フロントでの影響**: サーバ秘匿ロジックが client bundle に混入する事故の防御が config 1 箇所にしか敷かれていない。
- **隣接 ADR**: 0030(A7)— config のみ。0071(B3)— adapters の server-only 化は未言及。
- **一次分類の目安**: rule

### 空白領域: デプロイ version skew 対応
- **内容**: デプロイ跨ぎで旧クライアントが新サーバの Server Action / RSC payload を叩いた時の挙動方針(skew protection の PaaS 依存機能に頼るか、フルリロード誘導を実装するか)。
- **フロントでの影響**: Server Actions 採用(0040)により skew 時の action ID 不一致エラーが構造的に発生するが、対処が未定義。
- **隣接 ADR**: 0040(A4)/ 0011(R1 — PaaS 前提)。
- **一次分類の目安**: rule

### 空白領域: typed routes・リンク規約
- **内容**: Next.js `typedRoutes` の有効化可否、内部遷移は `next/link` 必須・生 `<a>` 禁止(外部リンクの `rel` / `target` 規約含む)の明文化。
- **フロントでの影響**: route 文字列のタイポはビルドで捕まえられるのに未活用のままになり、外部リンク規約はセキュリティ(tabnabbing)にも接続する。
- **隣接 ADR**: 0040(A4)/ 0028(A6)— route 命名はあるが参照側規約が空白。
- **一次分類の目安**: rule

## テスト・品質保証の残余

### 空白領域: Server Components / RSC テスト方針の確定
- **内容**: 0090 が「RSC・route handler・E2E の線引きは実装時に確定」と明示保留した部分の決着(async RSC を unit で回せるか、E2E に寄せるか)。
- **フロントでの影響**: RSC 既定(0040)の構成では「実装時確定」のままだと最初のテスト PR で毎回この議論が再燃し、90% ゲート(0090)の充足手段も定まらない。
- **隣接 ADR**: 0090(B8)— 本文確認済みの明示保留。
- **一次分類の目安**: decision(追補)

### 空白領域: visual regression テスト
- **内容**: スクリーンショット比較(Playwright 内蔵 / Chromatic 等)を持つか、持つならベースライン管理・許容 diff の規約。
- **フロントでの影響**: Tailwind ユーティリティ主体(0050)は CSS の影響範囲が読みにくく、リグレッションを機械検出する層が現状ゼロ。
- **隣接 ADR**: 0090(B8)— unit/component/integration/e2e の 4 層に視覚回帰が含まれない(本文確認済み)。
- **一次分類の目安**: decision(または exclusion)

### 空白領域: a11y 自動テストの組込
- **内容**: axe-core(vitest-axe / @axe-core/playwright)を component / e2e テストに組み込むか。0100 は「biome 静的検査 + 手動チェック」のみで、実行時 DOM に対する自動検査が空白。
- **フロントでの影響**: コントラストや実 DOM の ARIA 整合は biome(静的)では検出できず、AA 目標(0100)の検証手段が手動レビュー頼みになる。
- **隣接 ADR**: 0100(C2)/ 0090(B8)。
- **一次分類の目安**: decision

### 空白領域: E2E のデータ・環境戦略
- **内容**: Playwright E2E がどこに向かって走るか — バックエンド不在(別リポ)の前提で mock(MSW/route 差し替え)か契約スタブか、テストデータ・シードの所有。
- **フロントでの影響**: バックエンド別リポ構成(0070)では E2E の相手が自明でなく、CI(0153 の playwright job)が実装できない。
- **隣接 ADR**: 0090(B8)— E2E の存在まで。0153(B9)— job 枠のみ。
- **一次分類の目安**: decision

### 空白領域: dev 時のバックエンド不在モック戦略
- **内容**: ローカル `pnpm dev` でバックエンドが立っていない時の開発手段(MSW の dev 利用 / スタブ BFF / 常時接続前提)の既定。
- **フロントでの影響**: 別リポ・バックエンド前提(0070)の表示層は「ローカルで何を叩いて開発するか」が決まらないと dev 体験が個人依存になる。
- **隣接 ADR**: 0090(B8)— MSW はテスト文脈のみ。0072(B4)— 契約取得はあるがモック生成は未言及。
- **一次分類の目安**: decision

## 監査サマリ

- 挙げた空白領域: **58 件**(データ取得・キャッシュ 8 / フォーム 8 / UX 横断 12 / スタイリング 4 / コンポーネント設計 7 / 状態・URL 3 / セキュリティ seam 7 / 国際化・フォーマット 4 / リアルタイム 3 / 観測性・公開 4 / ビルド・運用 7 / テスト 5 — 一部重複領域あり)
- 特徴的なパターンとして、**「委譲先消失」が 2 件**確認された: ①キャッシュ設計(0040→B3 委譲だが 0071 は resilience のみ)②`loading.tsx` / Suspense 境界(0040→B6 委譲だが 0080 は error 系のみ)。既存 ADR の関連節に「確定先」と書かれたまま宙に浮いており、通常の空白より発見されにくい。
- また 0090(RSC テスト)と 0040(Cache Components)は ADR 自身が「後で確定」と明示保留しており、トリガー条件(B3/B6 Accepted)は既に成立している。

**フロント開発の初期に効いてきそうなトップ(優先度の示唆であり、必要性の確定ではない)**:

1. **Suspense / streaming 境界と `loading.tsx`**(委譲先消失。最初のページ実装から必要)
2. **キャッシュ・再検証戦略 + Cache Components 有効化**(委譲先消失 + 明示保留。書き方の根本が分岐)
3. **素の form の標準形 + Server Action の戻り値・エラー契約**(0060 exclusion の裏面。最頻出 UI が無規約)
4. **認証のフロント側 seam**(out of scope の中で唯一、seam なしでは保護ページが書けない)
5. **searchParams のシリアライズ / 型付け規約**(ほぼ全一覧画面で即必要)
6. **デザイントークン体系の具体 + ブレークポイント**(最初の 2〜3 画面で事実上固定される)
7. **日付・数値フォーマットとタイムゾーン / hydration mismatch**(RSC 既定の構成で初日から地雷)
8. **CSP / セキュリティヘッダ**(後付けコストが最も高い実行時防御)
