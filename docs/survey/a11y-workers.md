# 調査台帳: a11y の worker 数

> **このファイルはこのブランチだけのものである。判定が出たら削除し、このブランチはマージしない。**
> 結論は #240 へ書き戻す。

複数日にまたがる測定なので、セッションをまたいで記録が消えないようここへ積む。

## 何を確かめたいか

`a11y` の worker 数を**コア数より多く**すると実行時間が縮むか。

前に `--workers=200%` を測って見送った（#231）が、その測定は **axe の二重実行が残っていた条件**で
行ったものである。二重実行は #233 で解消され、flaky は 30 → 0 になった。**棄却の決め手だった機構
そのものが、もう存在しない。**

判定が付けば `a11y` の実行時間を下げられる。付かなければ、いまの `100%` を根拠のある既定として
確定できる。どちらでも「測れていない」状態からは前進する。

## 測り方

**`vrt` を対照に使う。** 同じ push で同じランナー世代の 2 ジョブが走るので、`vrt` の実行時間が
そのランナーの速さを表す。比 `a11y / vrt` を見れば個体差が相殺される（#231 でこの設計は機能した）。

- **処置**: `a11y` = `VRT_ARGS=--workers=200%`
- **対照**: `vrt` = 変更しない

**読む値はテストループの時間**とする。ジョブ全体の時間には Storybook の build とイメージの取得が
入り、そこは worker 数と関係なく動く。ログの次の 2 行から取る。

```text
Running 931 tests using 4 workers
  931 passed (10.7m)
```

flaky は `N flaky` の行から取る。**実行時間だけを見ると、リトライで失った時間を並列度の効果と
読み違える。**

### 測定を実際に走らせる方法

**何も考えずに push しても測定にならない。** 2 つの層がどちらも実行を省くためである。

1. `diff-scope` が `docs/*` `*.md` `.claude/*` を無関係と判定する —— この台帳を直すだけの push
   では a11y も vrt も走らない
2. `make a11y` / `make vrt` が「絵を決める入力」のハッシュを前回と突き合わせ、一致していれば
   検査を省く（`scripts/vrt/render-hash.ts` の `RENDER_INPUTS`）

したがって 1 回の測定ごとに、**入力に当たるファイルを 1 つ動かして push する**。いちばん軽いのは
`vrt/` 配下の `.ts` のコメントで、これは入力かつ scope 内である（`vrt/` の散文は入力ではない）。

```bash
# 例: 測定ラウンドの番号をコメントで進める
$EDITOR vrt/stories.spec.ts   # 先頭コメントの「measurement round: N」を進める
git commit -am "CI: 計測ラウンド N"
git push
```

## 基準値（変更前・`--workers=100%`）

`release/v0.5.0` 上の実測。両ジョブとも 4 worker で、flaky は 0 だった。

| commit | a11y | vrt | 比 | flaky |
| --- | --- | --- | --- | --- |
| `136bbc6b` | 931 tests / 10.7m | 940 tests / 7.8m | **1.37** | 0 |
| `9c644924` | 906 tests / 10.3m | 915 tests / 6.7m | **1.54** | 0 |

`--workers=100%` は 4 worker に解決される（public runner のコア数）。#231 の基準値 1.67 は
axe の二重実行が残っていた条件のものなので、そのままは使えない。

## 記録

| 日付 | run (a11y / vrt) | worker 数 | a11y | vrt | 比 | flaky | メモ |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 2026-08-22 | 32498678024 / 32498678167 | a11y 8 / vrt 4 | 931 tests / 10.4m | 940 tests / 5.9m | **1.76** | 0 | 1 対目。`--workers=200%` が 8 に解決されることを確認 |

1 対目の読み方（判定ではない）: **a11y の絶対値がほとんど動いていない**（基準 10.7 / 10.3 → 10.4）
一方で、対照の `vrt` は基準より速い（7.8 / 6.7 → 5.9）。速いランナーを引いてなお a11y が縮んで
いないので、比は基準（1.37 / 1.54）より上がった。worker を倍にしたぶんが効いていないように見えるが、
**n=1 では判定しない**というのが事前に決めた条件である。flaky は 0 のまま。

## 判定の条件（測る前に決めておく）

- **採用**: 比が基準（1.37 / 1.54）より**一貫して下がる**。サンプルは最低 5 対。1 対の改善では
  判定しない
- **棄却**: 比が変わらない、または **flaky が 0 でなくなる**。オーバーサブスクリプションは
  メモリ競合で衝突の窓を広げうるので、flaky の増加は単独で棄却条件とする
- どちらでも、結論を #240 へ書いてから撤去する

## 撤去

判定が出たら、採用・棄却のどちらでも次を行う。

1. この台帳を削除する
2. 結論と記録の表を #240 へ写す
3. 棄却なら `a11y.yaml` を `--workers=100%` へ戻す。採用なら worker 数の変更だけを別 PR で出す
   —— このブランチはマージしない
