# ドキュメント

**設計知識をどこへ置くかを決めるための判定**を持つ。各文書が何を持つかはそれぞれの冒頭が述べる
ので、ここには再掲しない —— ここに置き場のインベントリを書くと、置き場が増えた日に黙って古くなる。

## 置き場より先に、分類を決める

| 分類 | 何か | 行き先 |
| --- | --- | --- |
| **decision** | 選択肢の中から選んだ、結果が残る判断 | [`adr/`](adr/) |
| **exclusion** | **意図してやらない**と決めたこと | [`adr/`](adr/) |
| **rule** | 決定の帰結として日々強制される制約 | [`rules.md`](rules.ja.md)（ADR へリンクする） |
| **inventory** | コードに追随して漂うインベントリ | 生きた参照。**ADR には入れない** |

**inventory を ADR へ入れない**のが、この 4 分類を持つ理由である。不変の記録と漂うインベントリを同じ
文書に同居させると、インベントリの側が「根拠」の顔をしたまま静かに腐る。依存の**選定方針**は decision
だが、依存の**一覧**は inventory であり、両者は同じ場所に住めない。

## 判定 —— 上から順に当て、最初に YES になったところが行き先

1. **これを覆すとしたら、誰かが「別の案を選び直した」と言うことになるか。**
   → [`adr/`](adr/)。却下した案が書けるなら確実にここ。「意図してやらない」も ADR ——
   ただし**再検討を始める条件を同じ本文に持つ**。条件は前提の変化（道具が備えた・標準が定めた）
   であって状態（件数が 0・いまは速い）ではなく、条件を書けない「やらない」は先送りである
   （[0140](adr/0140-documentation-operations.ja.md)）
2. **次に同種のものが来たとき、どちらへ倒すかを答える基準か。複数のレイヤーやコンポーネントにまたがるか。**
   → [`design/`](design/README.md)
3. **「やったら違反」と機械的に言える形か。**
   → [`rules.md`](rules.ja.md)。根拠の ADR へリンクし、**何が守るか**（型 / lint / ゲート / テスト /
   散文）を同じ場所に書く（[0144](adr/0144-decision-enforcement-pairing.ja.md)）。テストを書くとき・
   レビューするときの規約は、分量の都合で [`testing-conventions.md`](testing-conventions.md) に
   分けてあり、判定は同じ
4. **1 つのレイヤー・feature の中で完結する責務・禁止・所有する状態の話か。**
   → そのレイヤー / feature の `README.md`
5. **業務が何を意味するかの話か。その領域の語彙で書けるか。**
   → [`spec/`](spec/README.md)
6. **コードに追随して漂うインベントリか。**
   → 生きた参照。ADR へは入れない
7. **どれでもない。**
   → **元の場所（コード）に置いたままにする**

**名前の付いた誤配が 2 つある**（[`rules.md`](rules.ja.md#comments) がこの判定を指して禁じる）。
**ライブラリや API の具体的な振る舞いを ADR へ上げない** —— それは呼ぶ相手の性質であって選択では
なく、依存を上げれば変わる。家は呼び出し地点で、判定 7 に落ちる。**業務知識を ADR へ入れない**
—— 業務の語彙で書けるので判定 5 に落ち、家は `spec/` である。

### 語と接触点 —— 判定 5 と 6 の内訳

2 つだけ、上の判定が素直に当たらないものがある。どちらも**インデックスであって根拠を持たない**ので、
判定をコピーせず**指すだけ**にする。

- **[`spec/glossary.md`](spec/glossary.md)** —— 判定 5 は「業務の語彙で書けるか」を問うが、
  仕様書の散文は**業務でも実装でもない画面の側の語**（レイアウトシェル・外枠・バンド・サイドバー・ローディング表示）も使う。
  それらの家は既に散らばって在るので、語彙表が持つのは**どの文書が定義しているか**と、
  **どこにも家が無かった語の定義だけ**。業務の語は入れない —— 正は契約と生成型である
- **[`design/context-map.md`](design/context-map.md)** —— 判定 6 のインベントリだが、辺ごとに
  **「境界の所有」という、コードから読めない事実**を持つ。読めないものを記録する以上、
  コードに追随するインベントリではなく、判定 2 の「複数の主題にまたがる基準」の側に近い。
  各辺の仕組みは主題ごとの design 文書が持ち、ここは指すだけにする

## 2 つのテスト

判定に迷ったときは、この 2 つで決まることが多い。

- **管轄テスト** —— **これを覆すとしたら、誰がどの文書を更新する義務を負うか。** そこが家である。
  「この Why は非自明か」ではない。非自明さは量の議論にしかならない
- **前提の所在テスト** —— **この宣言を編集せずに、この記述を偽にできるか。** できないなら、それは
  気づかれずに腐ることがないのでコードに残る。できるなら（上流の振る舞い・運用方針・業務規則）、
  誰もそれを検証できず、偽になっても何も鳴らない

手順の文書（レイヤー README / `SKILL.md` / [`.makefiles/README.md`](../.makefiles/README.md)）に理由を
残すかは、もう 1 つの問いで決まる —— **それを読まなかった読み手が違う操作をするか。** しないなら
それは理由であり、ADR が単独で持つ。手順側に置くのは挙動と使い方だけで、理由は
`> Rationale: [NNNN](...)` の逆参照で済ませる（[0140](adr/0140-documentation-operations.ja.md)）。

## デフォルトは「動かさない」

**行き先が決まらないものに、仮の置き場を作らない。** どの行き先にも当てはまらないなら、それは
コードが正しい置き場だった証拠である。

間違った移動は、移動しなかったことより**取り消しが難しい**。移した先の文書は書き換わり、元の
場所には残余しか残らないので、後から「本当はここで良かった」と戻すには両方を直すことになる。

## 写さず、指す

**1 つの記述の家は 1 つで、他の文書はそこを指す。** インデックスは腐っても壊れたリンクとして現れるが、
コピーは黙って食い違う —— 食い違いは両方を読んだ人にしか見えず、書いた側には一般化したことと
元の場所を畳んだことの区別が付かない。

- **一般化したら、元の場所は 1 行の参照へ畳む。** 残すのは、そのレイヤーに固有の分（綴りの形式・そのレイヤー
  だけの制約）だけである（[`rules.md`](rules.ja.md#comments)）
- **親子の README は境界を持つ。** 子が自分の README を持つなら、親はその子を 1 行の digest と
  参照リンクに留め、中身を再帰的に展開しない（[0140](adr/0140-documentation-operations.ja.md)）
- **仕様書は契約・token・コンポーネントの語彙・規約・ADR を指すだけで、コピーしない**
  （[0143](adr/0143-spec-driven-development.md)）
- **逆引きと手順の表は「どこを開くか」だけを持つ。** 基準を書き写した時点で古いバージョンが二重に残る
  （[`playbook.md`](playbook.md)、[`tutorial/`](tutorial/README.md) がこの形）

## ノードごとの問い

同じ主題について、ノードごとに別々の問いに答える。

| ノード | 問い | 時間的性質 |
| --- | --- | --- |
| [`adr/`](adr/) | **何を決め、何を却下したか** | 記録。本文を上書きしてよいかは [0140](adr/0140-documentation-operations.ja.md) が持つ |
| [`design/`](design/README.md) | **目の前の case をどう裁くか** | **育つ。** 基準が鋭くなるたび書き足す |
| [`rules.md`](rules.ja.md) | **何をしたら違反か** | 強制可能な禁止だけ。判断の根拠は持たず、上の 2 つへリンクする |
| [`tutorial/`](tutorial/README.md) | **実際にどう書くのか** | 1 画面を端から端まで。**サンプルを消したあとの状態から始まる** |
| [`project/`](project/README.md) | **このプロジェクトが何であって何でないか** | スコープ・対象外・方針・バージョン・方向。最初に置き換える |
| [`reference/`](reference/README.md) | **いま何が入っているか** | **コードに追随するインベントリ。** ADR と違い、変わることを前提とした参照 |
| [`templates/`](templates/feature-readme.md) | **繰り返し作られる文書はどのセクションから始まるか** | テンプレート。`pnpm gen` が置き、必須セクションはテンプレートが宣言して採点する側が実行時に読む —— 必須セクションの一覧はここにしか無い |

**`design/` が生えるのは、1 つの README では収まらない判定手続きがあるときだけ。** 「この取得は
どこに置くか」を毎回裁く必要がある主題には基準が要るが、「必ずこのエンドポイントを通す」で終わる主題には
裁く余地がなく、書くことがない。後者は決定（ADR）と、それを実装するレイヤーの README で足りる。

## `spec/` とレイヤー・feature の `README.md`

| | [`spec/`](spec/README.md) | レイヤー / feature の `README.md` |
| --- | --- | --- |
| **何の語彙で書くか** | **業務・ドメインの語彙** | **実装構造の語彙** |
| 何を答えるか | この業務ルールは何を意味するか。どの値がどの範囲か。どの遷移が許されるか | 何を所有し、何を禁じ、どの状態を持ち、どうテストするか |

**入場条件はその語彙で書けるかであって、粒度ではない。** 業務の語彙で書けないものは、どれだけ
詳細でも spec には入らない。逆に、業務の語が README の中で育ち始めたら、それは家を出た語であり、
同じ語が別の場所で再定義される。

## 行き先にならない場所

**設計知識をここへ移設しない。** それぞれ別の理由で、受け取っても保たない。

**ただし「行き先にならない」と「読まなくてよい」は別である。** ここに挙げた場所にも決定は書かれて
いて、行き先が無いまま置かれているからこそ**引き上げる対象**になる。とくに `get-started/` は、
**まだ ADR になっていない決定の在り処**である。移設先として選ばないことと、
探しに行かないことを取り違えない。

| 置き場 | 受け取らない理由 |
| --- | --- |
| [`playbook.md`](playbook.md) | 逆引きのインデックスと、画面を作るときの作業順。どちらも「どこを開くか」を持つだけで、基準は指す先が持つ。行き先が増えたらインデックスを更新するだけ |
| [`traceability.md`](traceability.ja.md) | 集計。自分でそう宣言している。規約の集計は `rules.md` から生成され、手で数えた件数を置かない（[0146](adr/0146-rule-reference-stability.ja.md)） |
| [`adr/BACKLOG.md`](adr/BACKLOG.md) | 進捗ボード。決定も撤回条件も持たず、持つ ADR の本文を指す <!-- boilerplate-only:line --> |
| [`portal/`](portal/) | 生成ビュー。生成器が書き直す。`docs/<dir>/` 直下の `*.md` はスキャンで自動発見され、載る位置は [`manifest.yaml`](portal/manifest.yaml) の `meta` が決める（[0141](adr/0141-portal-operations.ja.md)） |
| `plan/` | 過程の成果物。配布物ではない <!-- boilerplate-only:line --> |
| `get-started/` | 手順。順序と人手の要る箇所しか持たず、テンプレートから作る前提が死ぬと使われなくなる |
| [`screens.md`](spec/screens.md) | サンプルの画面表。残す側の文書ではない <!-- sample:line --> |

**canonical はサフィックス無しのパスに置く英語の文書であり、その日本語のミラーは兄弟の `<name>.ja.md`、
canonical に追従する翻訳であって、別の置き場ではない。** サフィックスが名前空間であり、エージェントは
`*.ja.md` を読まない。知識を探すのも、判定を当てるのも、書き換えるのも canonical に対して行い、ミラーは
同じ変更でそれに追従する（[0140](adr/0140-documentation-operations.ja.md)）。
両方を読むと同じものを 2 回読むことになり、両方を書くと片方が遅れる。

**開発の経緯・移行の履歴・「なぜ X から切り替えたか」は `.github/release/` が受け取る。**
恒久文書に経緯を書かない。恒久文書が答えるのは「いま何が真か」であって、「どうしてそうなったか」
ではない。

## 捨てられる文書に一般形を書かない

前提がいずれ失効する記述は、**その場でマークせず、失効と同時に捨てられる 1 つの文書へ集める。**
散文の途中を切り取ると、切り口の両側を繕う必要が残り、その近くを編集するたびに壊す機会が増える。

**一般形は残る側の文書に置き、そこから 1 行の自己完結したリンクだけを張る。** 行ごと消せる形で
なければ、捨てるときに残る側を壊す。

消える側のマーカーは撤去マーカーで付ける。**行ごと落とせる `:line` をデフォルトにし、表の行をブロックの
`begin` / `end` / `replace-*` で囲まない** —— 表は表の行でない行に出会った時点で終わり、以降の行が
生のパイプの段落になる。表は 1 行 1 実体にし、消える実体は自分の行を持つ
（[`rules.md`](rules.ja.md#comments)）。
マーカーを足した / 消したら行数のベースラインを引き直す（[`scripts/README.md`](../scripts/README.md)「撤去マーカーを足したら数え直す」）。 <!-- boilerplate-only:line -->

## 文書の形 —— 冒頭・末尾・指し方

この README が各文書の中身を再掲せずに済むのは、どの文書も同じ形をしているからである。

- **冒頭が、持つもの・持たないもの・隣の文書を述べる。** 「X は `adr/` が、Y は `design/` が持つ
  のに対し、ここが答えるのは Z」の 1 段落で、読み手は開いた文書が自分の問いの家かを最初の数行で
  決められる。ADR から派生した文書（`design/` / `project/` / `rules.md` / `testing-conventions.md`）
  は、**食い違えば ADR が正**と冒頭に書く（[`AGENTS.md`](../AGENTS.ja.md) の *Instruction Priority*）
- **参照は末尾の「関連」セクションに集める。** 散文の中に散らすと、そこが受け口であることが読み手にも機械にも
  分からない。1 行に**指す先と、そこが持つもの**を書く —— 番号だけの列は、どれを開けばよいかを
  示さない
- **ADR は `[NNNN](path)` の番号だけで指し、セクション番号を添えない。** セクションを足す・並べ替えると番号は綴りを
  変えずに別のセクションを指す。どのセクションかは相手のセクション名をコピーせず、**自分が使っている中身を要旨として書く**
  （[0146](adr/0146-rule-reference-stability.ja.md)）
- **`rules.md` のセクションは見出しの直前の `<a id>` アンカーで指す。** 見出しから導いた slug は、訳したときと
  言い換えたときに消える（同 0146）
- **他リポジトリの issue / PR は `redirect.github.com` を通す。** 素のリンクは上流へ取り消せない
  痕跡を残す（[0159-1](adr/0159-1-cross-repository-references.md)）
- **私的な文書のセクション番号（issue の要件 `§30`・計画の工程番号）を焼き込まない。** 読み手が解決
  できない。公開標準のセクション参照は可（[`rules.md`](rules.ja.md#comments)）

リンク先の実在（アンカーを含む）は [`scripts/doc-links.gate.test.ts`](../scripts/doc-links.gate.test.ts)
が、ADR リンクの直後に置いたセクション番号は [`scripts/adr-reference.gate.test.ts`](../scripts/adr-reference.gate.test.ts)
が落とす。**リンクから離れた位置のセクション番号と、コピーしたセクション名は通る** —— そこは読む側が見る。
